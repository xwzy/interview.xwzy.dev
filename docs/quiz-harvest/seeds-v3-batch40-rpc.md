### S1. RPC 的私有协议报文怎么设计？协议头里该放什么，怎么做到可扩展且向后兼容？
- 来源：课程 A 第 02 讲（协议）、第 24 讲（多协议兼容）；课程 B 第 22 讲（Dubbo 帧格式）、第 23 讲文末（encodeResponse 帧字段）
- 核心素材：
  - 协议的本质是**消息边界**：TCP 是字节流，会拆包/粘包，没有边界接收端就把 ABCDEF 拼成 ABC/DEF 语义错乱；断句三种方案——固定长度、分隔符（内容含分隔符会被误切）、**定长头 + 变长体**（主流）。
  - 协议头定长、协议体变长。头里必须有：**魔数**（如 Dubbo 0xdabb，快速识别非法报文并丢弃）、**序列化方式标志**（没有它提供方拿到字节流也无法还原对象）、**消息类型/标志位**（请求/响应、twoway、心跳 event）、**请求 ID**（8 字节，单连接上多请求并发时把响应关联回发起方——RPC"请求-响应配对"就靠它，这是私有协议对 HTTP/1.x 无状态的核心超越）、**协议体长度**（4 字节，读满即一个完整报文）。
  - Dubbo 头实测 16 字节：magic(2) + flag(1，高 3 位 request/twoway/event + 低 5 位序列化 ID，hessian2=2/kryo=8/protobuf=22) + status(1，**通信层**错误码：OK=20、CLIENT_TIMEOUT=30、SERVER_TIMEOUT=31、线程池耗尽=100，不是业务码) + request id(8) + body length(4)。
  - 可扩展性的坑：**定长头直接加字段必炸**——老版本按 88bit 读头，新增 2bit 被当协议体前 2bit 解析、体尾 2bit 被丢弃，数据全错；正确姿势是三段式：固定部分（含"头部长度"字段）+ 可扩展的协议头 + 协议体，扩头先改头长度。
  - 为什么超时这类元数据要放协议头而不是 body：过期请求判定（收到时已超调用方超时）若放 body，必须先反序列化整个 body 才能拿到，白白消耗 CPU；放头里解码即可判。
  - 多协议共存：入口先解析 magic number → 路由到对应协议解析器，并把"协议相关对象"转成协议无关的内部通用对象（返回时再转回），RPC 内部逻辑才能与协议解耦——这是框架平滑升级支持多协议的关键。
- 建议追问：① 为什么不直接用 HTTP/1.x？（无状态无法关联请求响应、文本头冗余换行回车占体积、每请求重新建连）→ 那怎么与 gRPC 自洽？（gRPC 选 HTTP/2 用标准生态换紧凑性：多路复用解决连接复用后，header 冗余与建连成本已不是主要矛盾）② 协议头加字段线上灰度期新老并存怎么兼容？③ 请求 ID 出现重复/回绕怎么办？
- 建议难度：intermediate

### S2. 序列化选型为什么"安全性"要排第一？Java 反序列化漏洞在 RPC 场景是怎么回事？
- 来源：课程 A 第 03 讲（序列化）、第 18 讲（安全体系）；课程 B 第 22 讲（序列化 ID 列表）
- 核心素材：
  - 选型优先级：**安全性 > 通用性/兼容性 > 性能/体积**——稳定性与可用率比性能重要；JDK 原生序列化是漏洞重灾区（**readObject 反序列化过程中会执行目标类的 readObject/readResolve 链**，攻击者构造字节流即可触发 gadget chain 实现 RCE），仅限可信环境且不推荐。
  - Hessian/Protobuf 同理是"把字节流还原成对象"的过程，也有反序列化攻击面（Hessian 曾出多项 CVE，靠 serializer 黑白名单缓解）；Protobuf 类攻击面天然小：反序列化只做字段赋值，**没有多态类加载入口**。
  - 工程防护：禁用 Java 原生序列化；序列化框架开**类名白名单**（Dubbo 的 serialize check 就是被大量 CVE 教育出来的）；升级框架版本；内网也别裸奔——零信任。
  - 实操层还要防"用出来的坑"：入参对象别太复杂（深嵌套/复杂继承都翻性能与出错概率）、别传大集合（上兆入参直接拖垮 RT）、优先原生集合类（Hessian 不支持 Linked 系列、Byte/Short 反序列化变 Integer）、JSON 无类型靠反射性能差。
  - 内网 RPC 的另一半安全面（课程 A 第 18 讲）：拿到私服 jar 坐标就能冒充调用方（未授权调用压垮提供方）→ 调用方认证用 **HMAC 签名**在提供方本地验票，避免集中式授权平台成为全公司瓶颈；还要防**伪造提供方**——注册中心校验接口与应用绑定，一个接口只允许绑定应用注册。
- 建议追问：① 反序列化漏洞的完整触发路径？（恶意字节流 → readObject 自动执行链 → RCE）② 白名单为什么治本（切断"任意类可被实例化"这个前提）③ 内网系统为什么仍需要认证（jar 公开可取 + 调用量失控提供方不可见）。
- 建议难度：advanced

### S3. Dubbo 的集群容错策略有哪几种？failover 为什么是默认？
- 来源：课程 B 第 01 讲（cluster/loadbalance 基础与 "Tried 3 times" 异常解读）、第 23 讲（集群扩展与自定义转发）；课程 A 第 12 讲（可重试异常判定）
- 核心素材：
  - 六种策略语义：**failover**（默认：失败自动切换重试其他节点，retries 默认 2 次、总尝试 3 次——异常信息 "Tried 3 times" 即此；适合读操作，前提是接口幂等）；**failfast**（只发起一次，失败立即抛——非幂等写操作如新增记录）；**failsafe**（失败直接忽略不抛——写审计日志这类"失败无所谓"的场景）；**failback**（失败后台记录、定时重发——消息通知类，最终成功即可）；**forking**（并行调 N 个节点只要一个成功——实时性要求高的读，代价是浪费 N-1 倍资源）；**broadcast**（逐个广播全部提供者，任一失败则失败——更新所有节点的本地缓存这类"都要执行"的场景）。
  - 重试的异常判别：只有**框架异常**（超时、网络连接异常）才触发重试；**业务异常**原样抛给代理（业务语义不该框架兜底）；确实需要重试的业务异常走**白名单**配置。
  - 与超时的配合：连续重试会突破调用方超时设置（5s 超时 × 3 次重试实际 6s+），每次重试前要先判断整体是否已超时、并**重置剩余超时预算**。
  - "No provider available" 成因链（排查口径）：消费端 invoker 列表为空 ← 注册中心节点变更 ← 提供方注销/宕机/改接口名/加 group-version 不兼容——先查注册中心数据再查消费端缓存。
  - 定制出口：Cluster 是 SPI 扩展点，机房隔离等场景可继承 FailoverClusterInvoker 捕获无提供者异常，转发给桥接服务跨机房调用（四步：Invoker 子类 → Cluster 封装 → META-INF/dubbo 注册别名 → dubbo.consumer.cluster=别名 全局生效）。
- 建议追问：① failover 为什么强依赖幂等（原请求可能已达提供方并执行成功，重试造成重复写）② retries 的流量放大怎么控制（节点少时退化重试同一台、与熔断/retry budget 衔接）③ failover 选中已故障节点的窗口期怎么缩短（重试前剔除失败节点 + 健康检测摘除）。
- 建议难度：intermediate

### S4. Dubbo 的 SPI 比 JDK SPI 好在哪里？@SPI、@Adaptive、Wrapper 各自解决什么问题？
- 来源：课程 B 第 14 讲（SPI 机制）、第 15 讲（Wrapper）、第 17 讲（Adaptive）、第 19 讲文末（Adaptive 生成代码）；课程 A 第 07 讲（JDK SPI 不足与微内核架构）
- 核心素材：
  - JDK SPI（META-INF/services + ServiceLoader）三大问题：**一次性全量实例化**所有实现类（不能按需加载）；**load 每调一次就重新读文件反射建新实例**（高频调用拖垮 IO 与内存）；**只能 O(n) 遍历找想要的实现**；且无 IoC/AOP，扩展依赖其他扩展时无法自动注入。
  - Dubbo SPI 三步：接口加 @SPI 注解 → 实现类以"别名=类名"写进 META-INF/dubbo/… → ExtensionLoader.getExtension("别名") **按名 O(1) 取 + 缓存单例**；缓存 + Map 换 O(1) 正是冲着 JDK SPI 的两个痛点去的。
  - **@Adaptive 自适应**：编译期生成 Xxx$Adaptive 类，方法体内 `url.getParameter("geek", "dubbo")` **按 URL 参数在运行时决定用哪个实现**——URL 携带全部配置是 Dubbo 的总线，一个扩展点吃多家实现时靠它路由。
  - **Wrapper 两层含义**：①扩展点 AOP——@Wrapper 自动把实现包一层（包装类持原实现，前后插逻辑），Dubbo SPI 自带迷你 IoC（setter 注入其他扩展点）；②调用开销——生成 Wrapper 子类，invokeMethod 里生成 if-else 匹配方法名后**强转直调**，消掉反射开销（实测 1 万次调用：直调 8ms / 反射 2019ms / Wrapper 12ms）。
  - 微内核收束：核心流程固定 + 功能点全部抽象成扩展点接口（开闭原则），所以 Dubbo 的协议、负载均衡、容错、线程池、Filter 全部可换——与 Spring 的关系：Dubbo 不依赖 Spring 也能跑（自持 ExtensionLoader），集成靠 BeanDefinition 扫描把 @DubboService 变成 Spring Bean。
- 建议追问：① 为什么 Dubbo 不直接复用 Spring 的 BeanFactory（启动顺序强绑定容器、URL 驱动的运行时选择 Spring 做不到）② getExtension/getAdaptiveExtension/getDefaultExtension 的差别 ③ Adaptive 类的死循环案例（Wrapper 内再调 Adaptive 引用自身 → StackOverflowError，理解生成代码就看懂了）。
- 建议难度：advanced

### S5. 怎么实现"全异步"RPC？为什么异步能提升吞吐？
- 来源：课程 A 第 17 讲（异步 RPC）；课程 B 第 02 讲（异步化实践、RpcContext.startAsync 原理）、第 06 讲（事件通知）
- 核心素材：
  - 吞吐低的根因：业务耗时里 CPU 大部分在**等待不计算**（串行同步调 4 个下游各 10ms = 40ms；Future 并行发出统一 get = 10ms，吞吐近似 ×4）。
  - 消费端异步的关键认知：**RPC 框架内部本来就是异步的**——发送前创建 Future 并登记"请求 ID → Future"映射，响应回来按 ID 找到 Future 注入结果；所谓同步调用只是框架替你执行了 future.get()，异步就是把这个 Future 交给用户自己决定何时 get。
  - 提供端异步三要素（Dubbo 实现）：`RpcContext.startAsync()` 开启异步模式（CAS 创建 CompletableFuture 存进上下文）→ 异步线程里 `asyncContext.signalContextSwitch()` **把父线程上下文拷贝过来**（附件/隐式传参不丢）→ 业务完成后 `asyncContext.write(result)`（内部 complete 那个 Future，框架负责写回网络）。
  - 接口签名直接返回 CompletableFuture = 调用端/提供端**两端全异步且零侵入**（Java8 原生，优于回调对象与 RxJava 方案；gRPC 的 StreamObserver 入参是同一思想的另一种表达）。
  - 判据（什么该异步）：IO 耗时、异步结果不影响主流程、无严格时序要求；动机场景是**线程池耗尽**——200 线程被慢请求占满后快请求也饿死，让业务线程尽快释放比调大线程池根治。
- 建议追问：① 提供端方法已 return，框架怎么知道结果回来（Filter 链尾对 AsyncRpcResult 的等待/回调 + Future complete 触发写回）② Future → Callback → CompletableFuture 的 API 演进各解决什么（编排、回调地狱、链式组合）③ 异步化的代价（上下文跨线程拷贝、异常堆栈断裂、排障链路变长）。
- 建议难度：advanced

### S6. 一次 Dubbo 请求在提供端怎么从 IO 线程进业务线程池？线程池耗尽怎么发现与自保？
- 来源：课程 B 第 26 讲（四种线程池）、第 02 讲（线程池耗尽现象）、第 22 讲（响应码 SERVER_THREADPOOL_EXHAUSTED_ERROR）；课程 A 第 17 讲（IO 线程与业务线程分离）
- 核心素材：
  - 分工铁律：拆包、解码、反序列化在 **Netty IO 线程**做；业务逻辑必须丢**业务线程池**——慢业务占着 IO 线程会拖垮这个连接上所有请求的收发。Dubbo 业务线程默认 **fixed 200**（core=max=200，queues=0 时配 SynchronousQueue 不堆积）；单机吞吐粗算 = 线程数 ÷ 平均耗时（200 线程 × 1s 任务 ≈ 200 QPS），所以"200 不够用说明业务该优化"。
  - 拒绝策略是特制 AbortPolicyWithReport：抛异常的同时 **dump 线程栈**，线程池打满时能直接看到 200 个线程各自卡在哪。
  - 四种线程池选型：fixed（默认，稳）；limited（core=0 弹性涨到 max 200、线程不回收——量小怕浪费）；cached（非核心线程空闲 60s 自动销毁——突发后回落）；**eager**（重写 TaskQueue.offer：活跃线程 < max 时 offer 返回 false，利用 ThreadPoolExecutor"入队失败 → 尝试 addWorker"的机制**优先开新线程而不是排队**——适合"来了就要马上处理，不想在队列里等"）。
  - 自保与感知：线程池满时提供端直接回 **SERVER_THREADPOOL_EXHAUSTED_ERROR=100** 快速失败（消费方立刻换节点重试，而不是等到超时）；监控打点活跃线程/最大线程比例告警——耗尽不可预测但可提前预警。
- 建议追问：① 为什么默认"队列 0 + 快速失败"而不是大队列排队（排队只会把超时集中爆发，快速失败把压力转回调用方重新负载均衡）② eager 线程池"打破先入队后扩容"的原理 ③ IO 线程上哪些事绝对不能做（同步 RPC 下游、慢 SQL、大对象序列化——Dubbo 有 direct/message 等派发策略的取舍）。
- 建议难度：intermediate

### S7. 明明配置了 5 秒超时，为什么调用还按 1 秒超时失败？——RPC 框架的超时取值规则
- 来源：课程 B 第 11 讲（配置加载顺序/超时不生效）、第 01 讲（默认 1000ms）；课程 A 第 12 讲（重试与超时配合）、第 20 讲（超时检测靠定时扫描 Future）
- 核心素材：
  - 现象还原：提供方在接口上配了 5000ms、方法级 3000ms，消费方什么都没配，升级后消费方按 **默认 1000ms**（DefaultFuture DEFAULT_TIMEOUT）超时——因为**决定等多久的是发起调用的消费方**，取不到值就落默认。
  - 取值三层：**方法级 > 服务(接口)级 > 实例(应用)级**；每一层内部**先消费方后提供方**（消费方显式配置 > 提供方配置）；全取不到 → 框架默认。
  - 配置来源四层覆盖（优先级从高到低）：**-D JVM 系统参数 > 外部化配置中心 > API/XML/注解 > dubbo.properties 本地兜底**——排查"配置不生效"先问"更高优先级的地方是不是也配了"。
  - Dubbo3 特有坑：消费方走**应用级服务发现**（migration 默认 APPLICATION_FIRST）时，提供方通过 API 写在 ServiceConfig 里的超时**不在应用级元数据里**，消费方感知不到 → 显式配在注解/dubbo.properties，或 migration=FORCE_INTERFACE 回退接口级。
  - 超时的实现机制：每个请求建 Future 时登记创建时间与超时时间，**定时任务扫描**到期未完成的 Future 触发超时（异常栈 "by scan timer" 的由来；高并发下这类海量定时检测正是时钟轮的用武之地）；超时后**提供方通常还在执行**，结果只是被丢弃——所以非幂等接口超时 ≠ 未执行。
- 建议追问：① 超时预算为什么应逐层递减（入口 5s > 下游 3s，下游吃满预算上游必超时，白算）② 重试与超时怎么配合（每次重试前重置/扣减剩余预算，防止 3 次重试冲破总超时）③ 消费方超时 vs 提供方超时谁生效（都各自生效：消费方先放弃，提供方 SERVER_TIMEOUT 后到也作废）。
- 建议难度：intermediate

### S8. 节点"半死不活"时调用方为什么还在往它发请求？RPC 的健康检测怎么设计？
- 来源：课程 A 第 09 讲（健康检测）
- 核心素材：
  - 为什么心跳：TCP 连接没断 ≠ 应用活着（应用僵死/网络劣化时连接仍在健康列表里被负载均衡选中）——**连接状态和应用存活要分开检测**，业内方案就是应用层心跳（默认约 30s 一次：太短给服务端压力，太长摘除慢）。
  - 三态模型：**健康**（建连成功 + 心跳正常）/**亚健康**（建连成功但心跳**连续**失败达阈值，如 3 次）/**死亡**（建连失败）；状态可流转——亚健康连续心跳成功转回健康，死亡重连成功"复活"；发请求优先健康列表，健康列表为空时可用亚健康兜底保可用性。
  - 真实案例复盘：某机器接口十次坏几次——监控显示连接未断、心跳**间歇性**失败、TCP 重传高出正常 10 倍——"连续失败 N 次"永远到不了阈值，节点一直被当成健康；调低阈值治标不治本（网络抖动误判、负载高时心跳来不及响应造成误断连）。
  - 解法：健康检测增加**业务请求可用率**维度——时间窗口内 成功次数/总调用次数 低于阈值即挪入亚健康；用比例而不是次数/TPS，因为各接口调用频次（1s 百次 vs 半小时一次）与 RT（1ms vs 10s）差异巨大，不可直接比。
  - 检测方自身的误判（心跳仪坏了）：探测程序多点部署、跨机架/机房，**任一实例探测正常即视为存活**——多探测源冗余压低误判率。
- 建议追问：① 心跳间隔与失败阈值的权衡（摘除延迟 vs 误杀率，为什么不能只调参）② 连接级心跳与注册中心实例级健康检查的分工（本节点连接质量 vs 集群视角实例生死）③ 可用率窗口取多长合适（太短抖动误判、太长摘除迟钝）。
- 建议难度：intermediate

### S9. RPC 框架为什么把负载均衡做在客户端？自适应负载均衡怎么设计？
- 来源：课程 A 第 11 讲（自适应负载均衡）、第 08 讲（为什么不用 DNS/VIP）、第 14 讲（启动预热权重）；课程 B 第 01 讲（random/roundrobin 配置）
- 核心素材：
  - 客户端负载均衡 vs 中间设备（LVS/Nginx/F5）：省设备成本、少一跳转发延迟、**按接口/分组配置不同策略**（设备做不到）、节点增减随注册中心自动化无需人工维护后端列表——所以 RPC 把均衡做进调用方：与所有节点建长连接，每次调用本地选节点。
  - 核心洞察：负载均衡要均衡的是**负载不是请求数**——集群里有旧低配容器时均匀分发就是事故源；手动调权重是"事后救火"，业务提出的需求是**自动**根据节点状态调流量。
  - 自适应打分方案：调用方收集每个节点的指标（CPU 核数/负载/内存——常**搭心跳顺风车**回传、平均耗时/TP99/TP999、健康状态）→ 按指标权重加权打分（类比年终考核各项占比）→ 分数映射最终权重（10 分制 8 分 × 默认权重 100 = 80）→ 随机权重策略按新权重分流；指标收集器做成插件可开关。
  - 启动预热的落地：提供方把启动时间上报注册中心，调用方按"（now − 启动时间）/ 预热时长"把权重**线性爬升**到目标值——冷实例低概率接流，避免重启后 JIT/缓存未热被大流量打崩；批量重启时新实例权重一致低，存量机器靠自适应策略平抑。
- 建议追问：① 随机权重/轮询/最少活跃数（LAV：正在处理数少者优先，天然贴近真实负载）各自的适用场景与缺陷（LAV 的"活跃数"对耗时差异大的接口会失真）② 指标从提供方主动上报 vs 调用方本地统计 RT 的取舍 ③ 与一致性哈希负载均衡的分工（有状态路由场景）。
- 建议难度：intermediate

### S10. 泛化调用：不依赖接口包和 POJO，怎么发起一次 RPC？
- 来源：课程 A 第 23 讲（泛化调用）；课程 B 第 04 讲（泛化调用反射演进）
- 核心素材：
  - 需求场景：**统一测试平台**（在线选接口/分组/方法/参数直接调试）与**轻量级 HTTP 网关**（HTTP→RPC 转发）不可能依赖全公司每个服务的接口 jar——否则每有一个服务发布就要改平台代码重新上线。
  - 原理：RPC 的本质只是发一条"接口名 + 分组 + 方法名 + 参数类型 + 参数值"的请求消息；动态代理只是入口不是必需品。框架提供统一接口 **GenericService.$invoke(methodName, paramTypes, params)**（另有返回 CompletableFuture 的 $asyncInvoke），创建代理时指定真实接口名与分组。
  - 难点在序列化：没有接口 jar 就拿不到入参/返回值的 Class，无法正常序列化——调用端用 **Map 表示对象**，由**泛化专属序列化插件**序列化，服务端按接口元数据把 Map 还原成真实对象（请求里带泛化标志 generic=true，服务端据此分流）。
  - 演进对照（B04）：反射调用仍要依赖接口包（拿到对象和方法名反射 invoke），泛化连依赖都不要；代价是无编译期类型检查、错误推迟到运行期。
- 建议追问：① 服务端怎么识别泛化请求并还原对象（标志位 → 泛化反序列化 → 按接口元数据重建 POJO）② 泛化的安全边界（任何调用方可构造任意方法调用 → 必须叠加鉴权/白名单）③ 网关场景泛化 vs Sidecar/协议转换的取舍。
- 建议难度：basic

## 二、既有题增强素材（be-micro 及相邻题）

### E1. 目标题目：be-micro-rpc（RPC 的完整调用过程与序列化选型）
- 追问素材：「调用端拿到的只是接口，框架怎么把方法调用'偷梁换柱'成网络请求？反射开销怎么消？」——JDK 动态代理生成 $Proxy0（继承 Proxy + 实现接口，方法体统一转发 InvocationHandler），**只能代理接口**（Java 单继承，代理类已继承 Proxy）；反射调用慢 250 倍（2019ms vs 直调 8ms/万次），Dubbo 用 Javassist 生成 **Wrapper 类**：invokeMethod 里生成 if-else 匹配方法名后强转直调（12ms/万次）——代理层拦截调用、Wrapper 层消反射，两层配合才做到"像本地一样快"；选型三角度：生成速度、生成字节码大小、执行效率（Byte Buddy 后起、Spring/Jackson 在用）。

### E2. 目标题目：be-micro-rpc（RPC 的完整调用过程与序列化选型）
- 追问素材：「一次 HTTP 调用改成 RPC，报文会发生什么变化？」——HTTP/1.x 文本头（换行/回车等无信息量字符）体积远大于请求本身 + 无请求响应关联 + 每请求建连；私有协议 16 字节定长头 + 变长体，单长连接多路复用靠请求 ID 配对（素材同 S1，可作为该题协议环节的深化追问）。

### E3. 目标题目：be-micro-graceful-lifecycle（优雅上线与优雅下线）
- 追问素材：「注册中心摘流有传播延迟，RPC 框架层面怎么做到真正无损？」——三层兜底：① 提供方 ShutdownHook（Runtime.addShutdownHook 捕获进程信号）置**关闭标识** + 打开**请求挡板**：关闭期间新请求直接回 ShutdownException（"收到了但没处理"），调用方收到后把节点移出健康列表并**安全重试**到其他节点（未处理过所以可安全重试）；② 不能只依赖注册中心异步通知（最终一致，通知不全），靠**长连接主动逐个通知调用方** + 挡板被动兜底双保险；③ **引用计数器**等存量：开始处理 +1、完成 -1，计数归零才真正退出，整个 hook 包 10s 超时强制退出防挂死。上线侧：**延迟暴露**（Spring Bean 先注册进容器，启动完成后才注册到注册中心）+ 暴露前预留 Hook（预热 JIT、预载缓存）+ 调用方权重线性预热；手动上下线的框架机制：向注册中心写 override（disabled=true）摘除流量，上线时重新注册原始 URL。

### E4. 目标题目：be-micro-tracing（链路追踪原理与 TraceID 传播）
- 追问素材：「Dubbo 体系里 TraceID 具体怎么跨进程传？」——业务入参塞 traceId（显式传参）不可行：入参可能是 String/Integer 根本没法继承基类，上万个请求对象都要改；正确做法是**技术属性与业务属性分离**（类比 HTTP body 与 header）：traceId 放 **RpcContext attachments**，随请求消息传播；实现是 consumer/provider 各一个 Filter（@Activate(group=CONSUMER/PROVIDER, order) 控制顺序）：消费方 Filter 把 MDC/上下文里的 traceId 写进 invocation attachments，提供方 Filter 取出放进 ServerAttachment + MDC；与既有题"异步丢上下文"衔接：RpcContext.startAsync 的 signalContextSwitch 就是框架内置的跨线程上下文拷贝。

### E5. 目标题目：be-distributed-config-registry（配置中心/注册中心设计要点）
- 追问素材：「超大规模下服务发现还要考虑什么？」——① 为什么不用 DNS：多级缓存生效慢、JVM 默认 DNS 缓存**永久**，感知不到上下线；也不用 VIP/四层设备：成本、多一跳、摘节点要人工、策略不可按接口配。② ZooKeeper 作注册中心的规模天花板：集中上线瞬间写风暴 → CPU 飙升宕机 → 重启又被打垮（AP 选择的现实依据，补充既有题的 AP/CP 结论）；替代：注册数据全量内存缓存 + **消息总线广播 + 递增版本号丢弃旧消息** + 推拉结合保最终一致。③ 调用方缓存过期打到已下线节点：提供方做合法性校验直接拒绝，调用方收到拒绝异常**安全重试**到其他节点。④ Dubbo3 **应用级注册**（register-mode: interface/instance/all）把订阅数据从"接口 × 实例"降到"应用 × 实例"，就是为了扛十万百万实例与 K8s 体系互通（消费侧 migration 三档迁移）。

### E6. 目标题目：be-stability-limits-degrade（限流、熔断、降级协作）
- 追问素材：「限流熔断放进 RPC 框架时有什么工程细节？」——熔断器挂在**动态代理**（调用链第一关口，打开则直接走失败逻辑）；限流维度要有**应用级/IP 级**（大调用方单独限制）；单机限流的失真：阈值是单机的（1000/节点 × 10 节点），但流量不均会提前误限，扩容还要人肉重算——解法：配置中心下发**总阈值 + 节点数**由框架自算，或集中式限流服务（精确但每请求多一跳，性能换精度）；隔离先于限流：**业务分组**把核心/非核心调用方分池（分组注册+订阅），主分组全挂才借道次分组、恢复即切回；分组容量不够时**动态分组**——直接改注册中心里实例的分组名（追加/替换），秒级把富余机器借给出问题的分组，不用重启。

### E7. 目标题目：be-stability-deploy（灰度发布，若该题为发布/回滚主题）
- 追问素材：「RPC 层怎么做比灰度发布更小成本的试错？」——**IP 路由**：注册中心把路由规则下发到调用方，选节点前先按规则过滤（只有指定调用方 IP 能调到新上线实例——试错范围从"所有调用方"缩到"指定调用方"）；**参数路由**：节点打新老标签，按请求参数（如商品 ID）规则过滤——切流量期间保证同一商品 ID 的所有请求始终落在同一套节点上（切换完整性，IP 路由做不到）；规则放**调用方本地计算**而不是注册中心集中算：注册中心只存规则，避免它变成计算瓶颈。

### E8. 目标题目：be-network-io-multiplexing（Reactor 网络模型）
- 追问素材：「RPC 框架的零拷贝和 Kafka 的 sendfile 是一回事吗？」——不是：OS 级零拷贝（sendfile/mmap，减少用户态/内核态拷贝）已在该题覆盖；Netty 的"零拷贝"是**用户态数据操作优化**：CompositeByteBuf 合并多个 ByteBuf、slice 共享存储、wrap 包装数组——专治 TCP 拆包粘包后"拼接/切分消息"的内存拷贝；堆外直接内存（Direct Buffer）做 Socket 读写则对应 OS 级优化；RPC 选型收束：高并发场景选 IO 多路复用 + Reactor（Netty），低并发简单场景 BIO 反而更省。

### E9. 目标题目：be-micro-mesh（Service Mesh 与 SDK 框架取舍）
- 追问素材：「Dubbo3 的应用级服务发现和 Mesh 什么关系？」——接口级发现（每接口一份实例列表）在大规模下数据爆炸且与 K8s/native 注册体系不通；应用级发现（订阅应用实例 + 接口元数据按需映射）**与 Sidecar 的服务发现模型对齐**，是 Dubbo 保留 SDK 治理能力的同时向 Mesh/异构生态互通留的路——既有题已提"Dubbo3 应用级发现是折中路线"，本条给出机制级解释（register-mode/migration 配置位，见 E5）。
