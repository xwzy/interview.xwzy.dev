## 一、候选新题（现有题库未覆盖）

### S1. Redis 是单线程的，那哪些操作会把它卡住？哪些卡点能异步化，Redis 是怎么做的？
- 来源：16 _ 异步机制：如何避免单线程模型的阻塞？（辅：03 _ 高性能 IO 模型）
- 核心素材：
  - 五大阻塞点：① **集合全量查询与聚合操作**（HGETALL/SMEMBERS/SINTER/SUNION 等 O(N) 读操作）；② **bigkey 删除**——删除本质是释放内存并把内存块插回空闲链表，实测 100 万元素的 Hash 删除耗时可达 **1.98s**（正常响应是微秒级）；③ **清空数据库** FLUSHDB/FLUSHALL；④ **AOF 日志同步写**——一次同步写盘约 **1~2ms**，always 策略下大量写会阻塞主线程；⑤ **从库加载 RDB 文件**（文件越大越慢）。
  - 能否异步的判断标准：操作在不在**关键路径**上（客户端是否要等它返回数据结果）。读操作、从库加载 RDB 在关键路径上**不能异步**；删除、清库、AOF 落盘不返回数据，可以异步。
  - 异步子线程机制（**Redis 4.0+**）：主线程启动时 pthread_create 创建 **3 个后台子线程**（AOF 日志写、键值对惰性删除、文件关闭），主线程把操作封装成任务放入**任务队列**即返回 OK，由子线程实际执行——这就是 lazy free。对外命令：**UNLINK**、**FLUSHDB/FLUSHALL ASYNC**。
  - 4.0 之前的退化方案：用 SCAN 系列（如 HSCAN 每批取 ~200 条再 HDEL）把删除压力分摊到多次操作；集合全量查询同样用 SCAN 渐进遍历、客户端聚合。
  - 控制从库加载 RDB 时长的办法：主库数据量控制在 **2~4GB**。
- 建议追问：
  1. 为什么删除可以交给后台线程，而读不行？（→ 关键路径判断：客户端是否等待数据返回；删除只需回 OK）
  2. 用了 UNLINK 就零成本了吗？（→ 主线程仍要摘除键的引用、封装任务；内存不会立刻下降，监控内存时要理解惰性释放）
  3. 线上发现 bigkey 又必须删，你的完整操作预案？（→ 低峰期、SCAN 分批 / UNLINK、观察延迟与缓冲区、4.0 版本判断）
- 建议难度：intermediate

### S2. 生产环境 Redis 突然变慢，你的系统性排查思路是什么？
- 来源：18 _ 波动的响应延迟（上）、19 _（下）、17 _ CPU 结构影响性能、加餐（五）运维工具
- 核心素材：
  - 第一步先判断"真的变慢了吗"：测**基线性能**——`redis-cli --intrinsic-latency 120`（在**服务端本机**跑，排除网络影响，测低压力下最大延迟）；**运行时延迟 ≥ 基线 2 倍**才算变慢。反例：虚拟机里基线本身可达 ~9.9ms，10ms 的运行时延迟只比基线高 1.3%，不是变慢。
  - Redis 自身两查：① **慢查询命令**——SMEMBERS/HGETALL 换 SCAN 系列、SORT/SUNION/SINTER 挪到客户端做、KEYS 禁止上生产；② **过期 key 集中删除**——定期删除每 100ms 一轮、每轮采样 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP=20 个 key，若过期比例 **超 25%** 则持续循环删除形成阻塞；元凶常是**大量 key 用相同 EXPIREAT 时间戳**，修法是过期时间加 1~3 分钟随机抖动。
  - 文件系统（AOF）：everysec 的 fsync 由后台子线程做，但**主线程发现上一次 fsync 未完成时会阻塞等待**；AOF 重写大量抢磁盘 IO 时会连锁拖慢主线程。缓解：`no-appendfsync-on-rewrite yes`（重写期间不 fsync，宕机多丢数据换性能）；高可靠 + 高性能就换 SSD。
  - 操作系统两查：① **swap**——实例 5000 万次 GET 从 300s 涨到近 4 小时（延迟约 48 倍）的案例；排查 `cat /proc/<pid>/smaps | egrep '^(Swap|Size)'`，出现百 MB~GB 级 Swap 必须处理（加内存 / 拆集群 / 驱赶同机大内存邻居）；② **内存大页 THP**——大页 2MB vs 常规 4KB，持久化期间 COW 时改 100B 也要拷 2MB，`cat /sys/kernel/mm/transparent_hugepage/enabled` 应设 never。
  - 收尾检查：绑核与 NUMA（见 S8）、主库数据量 2~4GB、Redis 是否和大数据/采集类程序混部署（"吵闹邻居"）。
- 建议追问：
  1. 为什么基线要在服务端本机测？（→ 只考察软硬件本身，把网络变量剥离；网络另用 iPerf 单独测）
  2. swap 发生了，为什么不能只重启了事？（→ 根因是内存不足，不解决会复发；区分实例自身内存大 vs 同机进程挤占两种成因）
  3. 内存大页明明减少分配次数，为什么反而要关？（→ trade-off：收益在分配侧，代价在 COW 拷贝粒度，持久化场景代价远大于收益）
- 建议难度：advanced

### S3. Redis 里存的数据明明只有几个字节，为什么 top 看内存大好几倍？删除数据后内存也不降？
- 来源：11 _ "万金油"的 String，为什么不好用了？、20 _ 删除数据后，为什么内存占用率还是很高？
- 核心素材：
  - String 的内存账（课程案例：10 位图片 ID → 10 位对象 ID，有效数据 16B，实际占 **64B**）：**SDS**（buf + 结尾 \0 1B + len 4B + alloc 4B）+ **RedisObject**（8B 元数据 + 8B 指针）+ **dictEntry**（3 个 8B 指针 = 24B，jemalloc 向上对齐分配到 **32B**）。1 亿条记录 = **6.4GB，其中 4.8GB 是元数据**。
  - String 三种编码：**int**（Long 整数直接内嵌在指针位）、**embstr**（字符串 ≤44B 时 RedisObject 与 SDS 连续内存，省一次分配与碎片）、**raw**（>44B 时 SDS 独立分配）。
  - 省内存方案：**集合类型二级编码**——用 ziplist 布局省掉大量 dictEntry/指针开销。案例把图片 ID 前 7 位做 Hash key、后 3 位 + 对象 ID 做 field/value，每条降到 **16B（原来的 1/4）**；配套把 hash-max-ziplist-entries 设为 1000 保证不转哈希表（**一旦转哈希表就不可逆**）。
  - 内存碎片：**内因**是内存分配器（默认 jemalloc）按固定大小分桶分配（8B/16B/32B…），**外因**是键值对大小不一 + 反复删改造成不连续空闲块。后果：有总空闲但放不进连续数据，内存利用率低。
  - 度量与治理：`INFO memory` 的 **mem_fragmentation_ratio = used_memory_rss / used_memory**；经验阈值 **1~1.5 合理、>1.5 要处理、<1 说明发生 swap**（RSS 反而小于申请量）。治法：①重启（粗暴，有不可用窗口与恢复成本）；② **activedefrag 自动碎片清理（4.0-RC3+）**——"搬家让位、合并空间"，但内存拷贝会拖慢单线程，用 active-defrag-ignore-bytes（默认 100MB）、active-defrag-threshold-lower（10%）控制启动时机，active-defrag-cycle-min/max（25%/75%）限制清理占用的 CPU 比例。
- 建议追问：
  1. mem_fragmentation_ratio 小于 1 说明什么？（→ 操作系统分配的物理内存已小于 Redis 申请量，大概率发生 swap，读写要去慢速磁盘）
  2. 为什么不干脆用一个超大的 key 存所有数据？（→ bigkey 阻塞与倾斜，见现有大 key 追问；此处强调 ziplist 有 entries/value 阈值，超限退化）
  3. 碎片清理的代价是什么，怎么把影响压到最低？（→ 单线程内做数据拷贝，调低 cycle-max、避开业务高峰）
- 建议难度：intermediate

### S4. 要统计一亿用户的签到、UV、留存，分别该用 Redis 的哪种集合？内存能差多少个数量级？
- 来源：12 _ 有一亿个 keys 要统计，应该用哪种集合？
- 核心素材：
  - 四大统计模式对号入座：**聚合统计**（求交/并/差——日活新增与留存：累计用户 Set + 每日用户 Set，SINTERSTORE 求留存、SDIFFSTORE 求新增；注意聚合命令 O(N) 有阻塞风险，**放从库专做或拉到客户端算**）；**排序统计**（最新评论/排行榜：**List 不能用**——LRANGE 按位置取，新元素 LPUSH 插入后原有元素整体后移，翻页会读到重复元素；用 **ZSet 按权重 ZRANGEBYSCORE**，分页稳定）；**二值状态统计**（签到：**Bitmap**，SETBIT/GETBIT/BITCOUNT，1 亿用户 1 天 ≈ **12MB**，10 天约 120MB；**BITOP AND** 十个 Bitmap 求"连续 10 天签到"人数）；**基数统计**（UV 去重计数：**HyperLogLog** 固定 **12KB** 估算接近 2^64 的基数，标准误算率 **0.81%**；要精确数字退回 Set/Hash，但要接受 GB 级内存）。
  - 选型心法：先问"要不要精确、要不要去重、要不要排序"，再算内存账；Set 千万级 UV 单页面就要吃大量内存，页面多时不可行。
- 建议追问：
  1. 1 亿用户一天的签到用 Set 存要多少内存，Bitmap 又是多少？（→ Set 每成员几十字节、GB 级 vs Bitmap 12.5MB，差两个数量级）
  2. 为什么 List 做分页会串页，ZSet 不会？（→ 位置序 vs 权重序：List 靠下标，插入引起整体移位；ZSet 按 score 定位与位置无关）
  3. HLL 的结果能删元素、能精确吗？什么场景必须放弃它？（→ 不能；精确去重/预算留存明细时用 Set/Hash，或接受布谷鸟过滤器等替代）
- 建议难度：basic（点题进阶到 intermediate）

### S5. 主从架构下为什么可能读到旧数据、过期数据？脑裂是怎么把数据弄丢的？
- 来源：32 _ Redis 主从同步与故障切换，有哪些坑？、33 _ 脑裂：一次奇怪的数据丢失
- 核心素材：
  - **主从不一致的根因是异步复制**：主库本地执行完就回客户端，不等从库。缓解：保证主从同机房/低延迟网络；用 `INFO replication` 的 **master_repl_offset − slave_repl_offset** 差值做监控，超过阈值就把客户端从该从库摘除；slave-serve-stale-data 控制从库能否服务读。
  - **读到过期数据**：从库**不执行过期删除**（删除只在主库做）。3.2 之前从库会把过期数据原样返回；**3.2 起返回空但不删除**。更隐蔽的坑：**EXPIRE/PEXPIRE 是"相对当前时间"的 TTL**，从库在全量同步完成后才执行该命令，过期时间被推后（案例：同步花了 2 分钟，60s TTL 的 key 在从库上多活了一分多钟）——修法是用 **EXPIREAT/PEXPIREAT 指定绝对时间点 + 主从与同一 NTP 对时**。
  - **脑裂**：主库"假故障"（同机采集程序吃满 CPU、bigkey/swap 阻塞）→ 多个哨兵 ping 超时判**客观下线**并完成切换 → 假故障恢复后旧主继续收写 → 集群里两个主并存。**数据丢失机制**：切换完成后哨兵让旧主 slaveof 新主做**全量同步**，旧主要**清空本地数据**再加载 RDB——假故障期间写入它的数据全部丢失。
  - **防御**：min-replicas-to-write（N）+ min-replicas-max-lag（T）组合——至少 N 个从库的复制 ACK 延迟 ≤ T 秒，否则主库拒绝写入；经验值 N = 从库数 K/2+1（K=1 时取 1）、T = 10~20s。代价：牺牲一小部分可用性换数据安全。
  - 配置坑：哨兵 protected-mode=yes 会导致跨机哨兵无法互联、永远切不了主；cluster-node-timeout 太小 + 批量主从切换 → 超半数实例心跳超时判异常，整个集群挂掉（建议调大到 10~20s）。
- 建议追问：
  1. 主从复制是异步的，这和 CAP 里哪个取向对应？（→ 牺强一致保可用/分区容错，与 be-distributed 方向衔接）
  2. min-replicas-to-write 为什么不能设成"全部从库"？（→ 任一从库抖动就拒绝写入，可用性塌方；多数派是鲁棒性与安全的折中）
  3. down-after-milliseconds 调大能减少误判吗？代价是什么？（→ 能，但故障发现变慢、切换窗口拉长；且**所有哨兵实例必须配置一致**，课程实战坑：配置不一致导致哨兵始终无法形成共识）
- 建议难度：advanced

### S6. Redis 里有多少种缓冲区？它们分别是怎么把实例或同步搞挂的？
- 来源：21 _ 缓冲区：一个可能引发"惨案"的地方
- 核心素材：
  - **客户端输入缓冲区**：暂存客户端发来的命令；上限**硬编码 1GB，无参数可调**。写 bigkey、主线程阻塞导致命令积压会溢出 → 服务端直接断开连接。排查用 `CLIENT LIST` 看 qbuf / qbuf-free。
  - **客户端输出缓冲区**：16KB 固定缓冲（回 OK/错误）+ 动态缓冲（回大数据）；三类配置 `client-output-buffer-limit <class> <hard> <soft> <seconds>`：normal 默认 0 0 0 不限制（阻塞式发送天然安全）、**pubsub 必须设限**（订阅客户端是推模式，消费慢就积压——课程示例 8mb 2mb 60：超 8MB 或 60s 内持续超 2MB 即断连）、slave/replica（用于复制）。**MONITOR 命令持续输出会打爆输出缓冲区**，只能调试用。
  - **复制缓冲区**：全量复制期间主库为**每个从库单独**维护（本质就是从节点客户端的输出缓冲区），保存 RDB 传输期间的新写命令。风险：多个从库同时全量同步 = **同步风暴**，主库内存 ≈ 缓冲区 × 从库数；溢出则断连、全量复制重来。缓解：主库数据量 2~4GB、调大 client-output-buffer-limit slave、**控制从库数量**。
  - **复制积压缓冲区（repl_backlog）**：主库上**所有从库共享**的**环形缓冲区**，断线重连时从 offset 增量补发；写满会**覆盖旧命令** → 从库复制进度被覆盖就退化为全量复制。repl-backlog-size 按断线时长 × 写入速率调大。
  - 总结两类后果：断连型（normal/pubsub/复制缓冲区溢出 → 连接被关）vs 数据覆盖型（repl_backlog 溢出 → 退化全量同步）。
- 建议追问：
  1. 为什么输入缓冲区不给参数调？（→ 调大只会让单连接吃更多内存，多连接叠加把实例压垮；正确方向是治 bigkey 和阻塞）
  2. 为什么 pub/sub 客户端必须有缓冲区限制而 normal 可以 0？（→ 请求-响应是拉模式天然背压，订阅是推模式没有背压，必须靠上限兜底）
  3. 新上一批从库时主库内存为什么暴涨？（→ 复制缓冲区按从库数量线性放大，错峰接入 + 级联复制）
- 建议难度：intermediate

### S7. Redis 能当消息队列用吗？从 List 到 Stream 补了哪些课，还欠哪些债？
- 来源：15 _ 消息队列的考验：Redis 有哪些解决方案？
- 核心素材：
  - 消息队列三大需求：**保序**（库存先扣 5 再扣 2 不能反）、**重复消息处理**（全局唯一 ID + 消费端幂等）、**可靠性**（消费者宕机后消息不丢、可重取）。
  - **List 方案**：LPUSH + BRPOP 天然 FIFO 保序，BRPOP 阻塞读替代 while(1) 轮询省 CPU；可靠性靠 **BRPOPLPUSH**——读走的同时把消息塞进备份 List，宕机重启从备份重取。缺陷：List **不为消息生成 ID**（要业务自己造全局唯一 ID）、**没有消费组**（无法多消费者分担）、消息堆积全在内存。
  - **Streams（5.0+）**：XADD 自动生成全局唯一 ID（**毫秒时间戳-序号**，如 1599203861727-0）；XREADGROUP 按消费组读，组内一条消息只被一个消费者处理，实现负载分担；**PENDING List** 自动留存"已读取未确认"的消息，处理完 **XACK** 确认移除，宕机重启用 XPENDING 查到未确认消息继续处理。
  - 与专业 MQ 的差距：Redis 堆积吃**内存**（有上限），Kafka/RabbitMQ 落盘、可水平扩分区；Redis 也没有事务性投递那套保证。课程结论：消息量不大、想要轻量（一个进程 vs Kafka 还要 ZooKeeper）时 Redis 够用；大体量、高可靠场景用专业 MQ。
- 建议追问：
  1. Streams 的 XACK 机制和"取走即删"差在哪？（→ 读与确认分离，消息有 pending 态，天然支持失败重取）
  2. 消费组内怎么保证一条消息只被一个消费者处理？（→ 组内共享读取游标，XREADGROUP > 表示取"从未投递给本组"的消息）
  3. 如果消息量涨了 100 倍，你什么时候必须换 Kafka？（→ 堆积量逼近内存上限、消费端长期落后、需要多订阅者各自独立进度时）
- 建议难度：intermediate

### S8. 为什么 Redis 实例要绑 CPU 核？NUMA 架构下绑错核会怎样？
- 来源：17 _ 为什么 CPU 结构也会影响 Redis 的性能？
- 核心素材：
  - 硬件背景：L1/L2 是物理核私有缓存（访问 <10ns，仅 KB 级），内存访问约百 ns（慢近 10 倍），L3 共享（MB~几十 MB）。
  - 多核来回调度 = context switch → 运行时信息重载 + L1/L2 缓存冷启动。实测案例：24 核服务器上 Redis 关掉持久化、纯 String O(1) 操作，GET/PUT 的 **99% 尾延迟 504μs/1175μs**；`taskset -c 0` 绑核后降到 **260μs/482μs**。
  - **NUMA 架构**：每个 CPU Socket 有本地内存，跨 Socket 是**远端内存访问，延迟 +18%**。常见做法是把网络中断处理程序绑核提升网络性能——此时若 Redis 实例与中断程序**不在同一 Socket**，Redis 读网络数据要跨 Socket 总线，性能反而差。绑核要看 `lscpu`：逻辑核编号按"先各物理核第一个逻辑核、再第二个逻辑核"交错排（如 node0 = 0-5,12-17），想当然按 0-11 绑会绑错 Socket。
  - 绑核的风险：RDB/AOF 重写**子进程**和惰性删除**后台线程**会和主线程抢同一个核。两个方案：① 一个实例绑**一个物理核的两个逻辑核**（`taskset -c 0,12`，0 和 12 属同一物理核）；② 改源码用 sched_setaffinity 把子进程、后台线程绑到别的核；Redis 6.0 起支持配置化绑核。
- 建议追问：
  1. 平均延迟和尾延迟有什么区别，绑核改善的是哪个？（→ 主要压缩长尾：消除调度/缓存冷启动造成的偶发慢请求）
  2. 为什么绑逻辑核有风险、绑物理核好一些？（→ 同物理核的两个逻辑核共享 L1/L2 与执行端口，主线程与后台线程可共用而非互斥）
  3. 主从/多实例混部在一台 NUMA 机器上，你会怎么分配核？（→ 按 Socket 分组绑实例 + 网络中断同 Socket；避开 0 号核等中断密集核）
- 建议难度：advanced

### S9. 单实例数据量太大：加内存、上集群分片，还是换 Pika 这种 SSD 方案？
- 来源：28 _ Pika：如何基于 SSD 实现大容量 Redis？（辅：09 _ 切片集群）
- 核心素材：
  - **大内存实例的三宗罪**：fork 变慢阻塞主线程（RDB 生成）、RDB 恢复时间变长、主从全量同步更慢且**复制缓冲区易溢出 → 反复退回全量同步**。
  - **Pika**（360 开源）：① 用 **RocksDB** 把数据落 SSD（Memtable 双缓冲交替写盘，内存占用小；SSD 每 GB 成本约为内存的 1/10）；② 用 **binlog 机制**做主从增量同步——binlog 是 SSD 上的文件、可轮替，不受内存缓冲区限制，杜绝缓冲区溢出型全量同步；③ **Nemo 模块**把 Redis 集合类型转成 RocksDB 单值 KV：List 用 sequence 前后指针保序、Sorted Set 把 key+score+member 嵌入 key 使其按 score 有序——**兼容 Redis 协议，业务不改代码**；④ 多线程模型（分发线程 + 工作线程 + 线程池）弥补磁盘性能。
  - **代价**：读写走 SSD 天然慢于内存；写 binlog 让 SET/HSET 从 200K+ OPS 掉到 ~120K（**约 -41%**）。
  - 选型逻辑：容量优先、写多读少、能接受延迟上浮 → Pika 这类 SSD 方案；性能优先 → 大内存 + 分片；实例太多导致运维复杂 → 用大容量实例减少分片数（Pika 的动机）。微博同类实践也验证 SSD+RocksDB 扩容路线（加餐七）。
- 建议追问：
  1. 为什么 Pika 用 binlog 而不是 Redis 式内存复制缓冲区？（→ 文件不受内存上限约束、可轮替归档，同步期间不怕缓冲区溢出）
  2. Pika 怎么在"单值 KV 的 RocksDB"上实现 Sorted Set？（→ score 嵌入 key 参与排序、member 跟随，value 只存版本与 TTL——体现"存储模型决定结构实现"）
  3. 什么时候不该选 Pika？（→ 读多写少、延迟敏感的热数据；Pika 单次读可能落盘，无法承诺 Redis 的微秒级）
- 建议难度：intermediate

### S10. Redis 6.0 的客户端缓存（Tracking）是什么？普通模式和广播模式怎么选？
- 来源：39 _ Redis 6.0 的新特性：多线程、客户端缓存与安全
- 核心素材：
  - 动机：把数据缓存在应用进程本地，省网络 RTT；难点是**数据变更后如何通知客户端失效**——服务端协助的 Tracking 功能解决它。
  - **普通模式**：服务端记录每个客户端读过的 key，key 被修改时给对应客户端发 **invalidate 消息**；**同一个 key 只报一次失效**，客户端再次读取才重新跟踪——省服务端记录表的内存。
  - **广播模式**：客户端注册 key **前缀**（`CLIENT TRACKING ON BCAST PREFIX user`），该前缀 key 一有修改就广播给所有注册客户端；**不需要客户端读过该 key**、不占服务端记录表，代价是修改频繁时大量失效广播消耗带宽。与业务 key 命名前缀规范天然契合。
  - 协议依赖：两种模式需要 **RESP 3**；RESP 2 客户端走**重定向模式**——由另一个支持 RESP3 的客户端 CLIENT TRACKING REDIRECT，把失效消息转发到 `_redis_:invalidate` 频道供其 SUBSCRIBE。
  - 同讲顺带：多 IO 线程默认关闭（io-threads-do-reads yes + io-threads，建议小于核数，如 8 核配 6）；ACL 支持用户级 + 命令类别（+@hash -@string）+ key 前缀（~user:*）权限。
- 建议追问：
  1. 和业务自己写"本地缓存 + 短 TTL"相比，Tracking 好在哪？（→ 主动失效近乎实时，不用等 TTL 过期窗口内的脏读）
  2. 普通/广播模式各适合什么场景？（→ 读多改少、key 集中 → 普通模式省带宽；业务按前缀划分、可容忍多余失效消息 → 广播模式省服务端内存）
  3. 这套机制和现有题的"缓存一致性"如何衔接？（→ 它解决的是应用层多级缓存一致性，与 Redis-DB 间一致性（canal/延迟双删）是两层问题）
- 建议难度：advanced

### S11. 切片集群为什么有 Codis、Redis Cluster 两派？代理型和无中心型怎么选？
- 来源：35 _ Codis VS Redis Cluster：我该选择哪一个集群方案？
- 核心素材：
  - **Codis 架构**：codis proxy（兼容 RESP 协议，单实例客户端**无感接入**）+ codis server（二次开发的 Redis，支持迁移）+ **ZooKeeper 存路由表**（1024 slot，CRC32 取模）+ dashboard/fe 管理面；可靠性靠 server group（一主多从）+ 哨兵。
  - 与 Cluster 的四个对比维度：① **路由表**——Codis 集中存 ZK、proxy 缓存；Cluster 由实例间 Gossip 自传播（实例多时网络开销大）；② **客户端兼容**——Codis 免改造，Cluster 要 smart client 或支持 MOVED/ASK 重定向；③ **新特性**——Codis 基于开源 3.2.8，不支持后续新命令，且 BITOP/BLPOP/BRPOP/MULTI/EXEC 等未实现；④ **迁移**——Codis 支持**异步迁移**（bigkey 拆成逐元素指令、目标端设临时过期时间保原子性），Cluster 迁移是**同步的**，迁 bigkey 会阻塞源实例。
  - 选型建议：要成熟稳定、存量单机客户端多、迁移频繁 → Codis；要用新版本特性、不想引入 ZK/proxy 组件 → Cluster。组件越多风险点越多，Codis 的可靠性依赖 ZK（多数派存活）。
- 建议追问：
  1. 代理层会不会成为新瓶颈/单点？怎么解？（→ proxy 无状态可水平加、客户端从 ZK 拿 proxy 列表分担；对比 Cluster 无代理但客户端复杂）
  2. 为什么 Codis 迁 bigkey 要"拆成逐元素指令 + 临时过期时间"？（→ 整体序列化传输会阻塞源实例；拆分后故障中途可由过期时间清理半迁移状态，保原子性）
  3. 这套对比在今天还剩什么通用价值？（→ 代理型/客户端型/服务端型三种分片路线的权衡在各类中间件里都成立）
- 建议难度：intermediate

### S12. 物联网/监控这种时间序列数据要在 Redis 里怎么存？为什么不无脑一条一个 key？
- 来源：14 _ 如何在 Redis 中保存时间序列数据？
- 核心素材：
  - 读写特征：**写=纯插入要快**（记录后不变），**读=三种模式**——点查询（某时刻值）、范围查询（时间段）、聚合计算（窗口内 max/min/avg）。
  - 方案一（内置结构）：**Hash + Sorted Set 组合**——Hash 管**点查询**（HMGET 按时间戳直取），ZSet 管**范围查询**（时间戳做 score，ZRANGEBYSCORE）；两处写入用 MULTI/EXEC 保证原子；短板：**聚合要拉回客户端算**，且数据存两份费内存。
  - 量级对比案例：1 万台设备、33 个指标、每 3 分钟一算，客户端聚合要传 **~396 万条**；用 **RedisTimeSeries** 模块在服务端聚合（TS.RANGE + AGGREGATION avg/max，TS.CREATE 设 RETENTION 过期与 LABELS 标签）后只传 **~33 万条**（约 1/10）。RedisTimeSeries 短板：底层链表范围查询 O(N)，TS.GET 只能取最新值。
  - 选型：网络/内存充裕、点查和范围查为主 → Hash+ZSet；聚合频繁、带宽紧张、要按标签筛选 → RedisTimeSeries。
- 建议追问：
  1. 为什么两个结构要原子写？（→ 任一写失败会造成点查与范围查结果不一致，MULTI/EXEC 打包）
  2. 如果数据按"一个 key 存全部"会怎样？（→ 单 key 写热点压垮单实例、bigkey；应按设备/时间分片 key）
  3. 什么信号说明该上专用 TSDB？（→ 服务端聚合仍不够、保留期长、标签维度查询复杂）
- 建议难度：intermediate

## 二、既有题增强素材（对应现有 10 题的追问可加内容）

### E1. 目标题目：be-redis-datatypes（数据结构底层编码）
- 来源：02 _ 数据结构、11 _ String、13 _ GEO
- 追问素材：
  - "ziplist 为什么只给小数据用？" → ziplist 仅**首尾元素 O(1)**（靠表头 zlbytes/zltail 定位），中间查找 O(N)；entry 元数据 prev_len 1 字节（前项 <254B）或 5 字节——它是"省内存但慢查询"的连续布局。Hash/Set/ZSet 元素数或单值超限（hash-max-ziplist-*）后转 hashtable，**转过去不可逆**。
  - "全局哈希表为什么不会因扩容卡死？" → 两张哈希表 + **渐进式 rehash**：每次键值操作顺带迁一个桶，期间读新表查不到再查旧表。
  - "String 有哪几种编码？阈值是多少？" → int（Long 直接内嵌指针位）/ embstr（≤44B，RedisObject+SDS 连续内存）/ raw（>44B，SDS 独立分配）。
  - "GEO 的 nearby 原理？" → 经纬度分别做 N 次**二分区间编码**得二进制串，组合后作为 **ZSet 的 score** 存成员——所谓新类型 = 既有结构 + 编码方案。

### E2. 目标题目：be-redis-persistence（RDB/AOF/混合持久化）
- 来源：04 _ AOF 日志、05 _ 内存快照
- 追问素材：
  - "AOF 为什么是写后日志，和 MySQL 的 WAL 相反？" → 先执行命令、成功后才记录：① 避免记录错误命令阻塞恢复；② 不阻塞当前写操作。代价：命令执行后宕机才丢日志（最后一秒）。
  - "AOF 重写的完整流程？" → "**一个拷贝、两处日志**"：主线程 fork 子进程按当前数据生成最小命令集（多变一：6 次 LPUSH 归并成 1 条）；重写期间新写入**同时**进旧 AOF 缓冲和新重写缓冲，重写完成后追加进新文件再原子替换。
  - "fork 有代价吗？" → fork 本身**阻塞主线程**且与内存大小成正比；已有 bgsave 在跑就不会再起第二个 bgsave——所以大实例要控制 fork 频率（也解释了 auto-aof-rewrite-min-size 这类门槛存在的意义）。
  - "everysec 真的只丢 1 秒吗？有没有例外？" → fsync 在后台子线程做，但磁盘被 AOF 重写抢占时 fsync 变慢，主线程等上次 fsync 会连带阻塞（延伸到 no-appendfsync-on-rewrite，可与 S2 素材互通）。

### E3. 目标题目：be-redis-eviction（过期删除与内存淘汰）
- 来源：18 _ 变慢（上）、27 _ 缓存被污染了
- 追问素材：
  - "定期删除的循环条件是什么？" → 每 100ms 一轮，每轮采样 20 个（ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP），**过期比例 >25% 就再来一轮**——所以"大量 key 同一秒过期"会造成持续阻塞；EXPIREAT 相同时间戳是常见元凶，抖动 1~3 分钟可解。
  - "什么是缓存污染？哪种策略扛得住？" → 一次大扫描把海量"只访问一次"的数据灌进缓存，LRU 按最近访问时间评估，会被污染数据占满、热点被挤出；**LFU 按访问频率计数 + 衰减**才能把污染数据淘汰出去（allkeys-lfu/volatile-lfu）。
  - （配合现有"大 key/热 key"追问）"4.0 之前怎么删 bigkey？" → HSCAN 每批 ~200 条 + HDEL 分批删；4.0+ 用 UNLINK 异步。聚合统计（SINTER 等）也别在主库做。

### E4. 目标题目：be-redis-cache-3problems（穿透/击穿/雪崩）
- 来源：26 _ 缓存异常（下）
- 追问素材：
  - "布隆过滤器的实现细节？" → 初值 0 的 bit 数组 + N 个哈希函数；插入 = N 个位置全置 1，查询 = N 个位置**有一个 0 就一定不存在**；用课程例子（10 bit + 3 哈希，标记 X 置 1/3/7 位）讲清"可能误判存在、绝不误判不存在"。
  - "互斥锁重建缓存的流程要点？" → miss 后 SETNX 抢锁 → 拿锁者查库回填 → 未拿到者 sleep 重试；对比"逻辑过期"：value 内嵌过期时间、永不物理过期，发现逻辑过期后异步重建、请求先返回旧值——**一致性 vs 可用性**的取舍正好引申。

### E5. 目标题目：be-redis-lock（分布式锁与 Redlock）
- 来源：30 _ 如何使用 Redis 实现分布式锁？
- 追问素材：
  - "Redlock 的执行细节？" → N 个**完全独立**（非主从）实例依次 SET NX PX + 唯一值；单实例加锁设**短超时**快速失败换下一个；**多数派成功且总耗时 < 锁有效期**才算拿到；释放时要向**所有实例**发 Lua 释放（不只成功的那些）。失败后随机延迟重试避免合谋。
  - "锁的超时时间怎么定？" → 依赖业务执行时间评估（P99 预留余量），太短会误释放（引出续期/看门狗），太长则持有者崩溃后阻塞其他客户端——与现有三点经典问题闭环。

### E6. 目标题目：be-redis-cluster（主从/哨兵/集群概览）
- 来源：06 _ 数据同步、07 _ 哨兵机制、08 _ 哨兵集群、10 _ 答疑（buffer 区别）、37 _ 数据倾斜、38 _ 通信开销
- 追问素材：
  - "哨兵怎么挑新主库？" → "**筛选 + 打分**"：先过滤掉下线/断线的从库，再三轮打分取最高——① **从库优先级**（replica-priority，0 永不参选）→ ② **复制 offset 最大**（数据最全）→ ③ **runid 最小**（兜底随机）。
  - "客观下线和 Leader 选举怎么投票？" → 哨兵发 is-master-down-by-addr 征集 Y/N，**达到 quorum** 判客观下线；随后每个哨兵先给自己一票、**先到先得**，拿到**半数以上且 ≥quorum** 者当 Leader 执行切换；一轮无 Leader 则等故障转移超时的 2 倍再选。哨兵集群靠订阅主库 **__sentinel__:hello** 频道互相发现，切换后客户端订阅 **+switch-master** 事件拿到新地址。
  - "replication buffer 和 repl_backlog 什么区别？"（答疑篇）→ 前者：**全量复制期间**主库为**每个从库**单独建客户端 buffer；后者：**所有从库共享**的环形 buffer，长期接收写命令、供断线增量补齐。
  - "全量同步压力大会怎样？" → 主库 fork 生成 RDB + 传 RDB 双重压力；用"**主-从-从**"级联（选高配从库当二级主）分散 fork 与带宽。
  - "Cluster 规模为什么有上限？" → Gossip 的 PING/PONG 单条约 **12KB**（1/10 实例状态 × 104B + 2KB slot 位图）；实例每秒随机 5 选 1 发 PING，每 100ms 扫描并对 PONG 超 cluster-node-timeout/2 的实例**立即补发**；规模越大超时越频繁 → 心跳风暴挤占业务带宽。缓解：cluster-node-timeout 调大（15s → 20~25s，用 tcpdump 抓 16379 端口对比）；官方上限 1000 实例，实践建议 400~500。
  - "集群数据倾斜怎么查怎么治？" → 三大成因：bigkey、Slot 手工分配不均（CLUSTER SLOTS 查看，SETSLOT/GETKEYSINSLOT/MIGRATE 迁移）、Hash Tag 把业务 key 粘到同 slot；访问倾斜用**只读热点多副本**（key 加随机前缀打散到不同 slot/实例），读写热点不能多副本（一致性开销），只能升级实例配置。

### E7. 目标题目：be-redis-lua-pipeline（事务/Lua/Pipeline）
- 来源：31 _ 事务机制、36 _ 秒杀、29 _ 原子操作
- 追问素材：
  - "Redis 事务到底满足 ACID 几条？" → **A 不满足**（运行时错误不回滚）；**C 不保证**（前述错误可能留下不一致中间态）；**I 满足**（单线程串行，EXEC 执行期间不插入其他命令；WATCH 提供 check-and-set 乐观锁）；**D 看配置**（RDB 会丢快照间数据、AOF everysec 最多丢 1s）——"Redis 事务是打包执行，不是原子失败回滚"这句话的逐项展开。
  - "Lua 原子扣减库存怎么写？" → Hash 存 {total, ordered}，脚本 HMGET 读两值 → 判断 ordered + k ≤ total → HINCRBY ordered——"查验 + 扣减"原子化防超售；库存 key **不设 TTL**（防击穿，等价于热点 key 永不过期）；多商品秒杀用切片集群按商品分 slot，锁与库存甚至可以分实例保存（抢不到锁的请求根本不碰库存实例）。
  - "Lua 脚本要短，短到什么程度？" → 单线程执行脚本期间全程阻塞；**不需要并发控制的逻辑（纯计算、纯判断）别塞进脚本**（29 讲原则），脚本里只放必须原子的读-判-写。

### E8. 目标题目：be-redis-hotspot（限流器）
- 来源：29 _ 无锁的原子操作
- 追问素材：
  - "INCR 和 EXPIRE 分开写，竞态具体长什么样？" → 线程 1 INCR 后、设置 EXPIRE 前，线程 2 也 INCR 并抢先判断"次数 >1 不设过期" → 该 key 永远没有 TTL，计数只增不清 → 用户被永久封禁。修法正是现有题的"Lua 原子化"或 EXPIRE NX，把竞态窗口讲成具体时序更有说服力。

### E9. 目标题目：be-redis-consistency（缓存双写一致性）
- 来源：25 _ 缓存异常（上）
- 追问素材：
  - "删除缓存失败了怎么办？" → 把目标 key 投入**消息队列重试**，删除成功才出队，超次数上报业务；对比 canal 订阅 binlog（现有 followUp）——重试机制是业务内兜底，binlog 是旁路兜底，两者可组合。
  - "什么时候用同步直写？" → 读写缓存（写穿）场景要求强一致时用"同步直写"（缓存与库一起更新，需业务事务保证原子性），异步写回（淘汰时才落库）只适合容忍丢失的非关键数据——把现有题的"只读缓存"视角补上"读写缓存"另一半。
