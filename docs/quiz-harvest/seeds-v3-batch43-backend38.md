## 一、候选新题（现有题库未覆盖）

### S1. 一个系统从单机到亿级并发，架构是怎么一步步演化的？每一步在解决什么瓶颈？
- 来源：第 21 讲（分布式架构）、第 04 讲（网络编程，CDN/两级 LB 串联视角）
- 核心素材：
  - 先答总纲：**垂直伸缩 vs 水平伸缩**——垂直（换更强 CPU/小型机→大型机）是银行电信传统路线，成本与算力非线性（越强越贵）、受硬件天花板限制；互联网选**水平伸缩**（多台廉价服务器组集群），代价是必须做分布式架构设计。
  - 演化路径每步的瓶颈-方案对应（背这条主线）：单机（应用+DB+文件同机）→ **应用/数据/文件分离** 3 台（几乎零技术成本）→ 加**缓存**（DB 是磁盘 IO 瓶颈：内存更快 + 缓存的是计算结果对象省 CPU + 卸载 DB 压力）→ **负载均衡 + 应用集群**（应用层并发瓶颈）→ **读写分离**（写也要落库，读压力转从库）→ **分布式存储/NoSQL/搜索引擎/CDN+反向代理**（海量数据与带宽）→ **消息队列**（子系统解耦）→ **微服务**（模块独立开发部署）。
  - 关键判断：这些技术全部是"**应用需求驱动**"逐级演化出来的——能按瓶颈倒推出方案，比背架构图值钱；分布式缓存/MQ/NoSQL 早期是大厂专属，云计算普及后中小系统也普遍使用。
  - 收束话术：互联网系统与传统 IT（超市收银/银行柜员——用户量有限确定）的本质差异就是用户量可能成千上万倍增长，高并发是互联网架构的核心驱动力。
- 建议追问：① 为什么数据库总是最后瓶颈、缓存总排在集群前面加？（磁盘 vs 内存数量级差 + DB 强一致约束最难水平化）② 读写分离后"写后立读"不一致怎么处理？③ 你的项目处在哪个阶段、为什么不需要更复杂的架构？（防背题的反向验证）
- 建议难度：intermediate

### S2. 负载均衡有哪些实现层次？从 HTTP 重定向到链路层 DR，各自原理与瓶颈是什么？
- 来源：第 24 讲（负载均衡架构）、第 04 讲（链路层 DR 与数据中心链路）
- 核心素材：
  - 五种实现按网络层次从高到低：**HTTP 重定向**（302 发回真实服务器 IP——实现最简但请求翻倍 + 应用服务器暴露公网 IP 有安全问题，实践少用）；**DNS 负载均衡**（域名解析返回不同 IP——解析结果本机缓存所以无每次请求开销，但需容忍 DNS 缓存导致的流量不均与故障切换延迟；大厂用法：DNS 解析到 LB 集群做第一级，LB 再做第二级）；**反向代理**（工作在应用层，HTTP 协议重、转发效率低，适合十几台小规模，Nginx 是代表）；**IP 负载均衡**（内核改 IP 包地址转发，比应用层高效得多，但**请求和响应都过 LB**——响应远大于请求，LB 出口带宽成瓶颈）；**数据链路层 DR**（不改 IP 改 **mac 地址**，LB 与真实服务器配同一虚拟 IP，响应**不经过 LB** 直接回客户端——三角传输，大型互联网标配，LVS 的 DR 模式）。
  - 记忆主线：**层次越低效率越高，关键是响应流量要不要经过 LB**——IP 层解决不了响应带宽，DR 用"改 mac + 虚 IP"把响应流量摘出去。
  - 负载均衡算法：轮询、随机、最少连接（课程只列三类，答的时候可带权重/一致性哈希衔接既有题）。
  - 高可用视角：LB 对后端做**心跳检测**摘除故障节点，这同时是实现"升级不停机"的基础（滚动发布的原理，衔接 be-stability-deploy）。
- 建议追问：① DR 模式为什么要求 LB 和真实服务器同局域网？（改的是二层 mac 地址，跨子网 mac 不可路由）② DNS 负载均衡怎么做故障快速切换？（TTL 调短 + 健康检查拨测，本质是分钟级 vs 秒级的权衡）③ 四层 LB 和七层 LB 的分界在哪、各举一个代表？（LVS vs Nginx）
- 建议难度：intermediate

### S3. 性能优化只能改代码吗？给出性能指标体系、压测曲线与分层优化框架
- 来源：第 28 讲（高性能架构）、第 22 讲（缓存 = 架构层优化核心）
- 核心素材：
  - 指标体系及关系：**响应时间**（最重要、最直接反映快慢）、**并发数**（同时处理的请求数 = 压测线程数）、**吞吐量**（TPS/QPS/HPS）、**性能计数器**（System Load/CPU/内存/IO——设阈值告警的监控指标）；三者关系式：**吞吐量 ≈ 并发数 / 响应时间**（并发 1、RT 100ms → TPS=10）。
  - 压测三阶段与性能特性曲线（并发数逐步加大）：**性能测试**（吞吐随并发线性涨、RT 基本不变——设计预期负载区）→ **负载测试**（吞吐增幅变小到峰值后回落、RT 开始上升——安全临界点）→ **压力测试**（超过安全负载继续加压直到崩溃——最大承受能力）；另配**稳定性测试**（一定压力长时间跑，压力可波动）。这条曲线就是"压到拐点而不是压到峰值"的理论出处（衔接 be-stability-capacity）。
  - **七层优化模型**（从宏观到微观）：① 数据中心（多机房就近服务——光速限制了单数据中心全球 RTT 130ms+）② 硬件（Spark 实战：1G 网卡换 10G，通信 50s→10s，比软件压缩有效且不耗 CPU）③ 操作系统（关 transparent huge page 降系统 CPU 占用）④ 虚拟机（GC 调优）⑤ 基础组件（容器/连接池/MVC 框架）⑥ 架构（**缓存提升读、消息队列提升写、集群提升并发**——三件套一句话）⑦ 代码（数据结构/SQL/异步 IO/池化，以及清晰代码才可优化）。
  - 方法论闭环：**性能测试 → 找瓶颈 → 优化 → 再压测验证**迭代；前提是懂指标 + 懂系统内部结构。
  - 加一层**主观性能优化**：进度条/流式渲染——同样 500ms，体验完全不同（与 MQ 异步化的"订单处理中"交互衔接）。
- 建议追问：① 为什么优化要以"拐点"为目标而不是吞吐峰值？（拐点后弹性耗尽、RT 雪崩，容量规划口径）②给你一个慢接口，七层模型里先排查哪几层、依据是什么？（从⑥⑦层入手性价比，对应 be-stability-rt-triage）③ "加缓存"在什么情况下无效？（无热点数据，见 E11）
- 建议难度：intermediate

### S4. 领域驱动设计（DDD）的核心是什么？贫血模型和充血模型差在哪？
- 来源：第 20 讲（领域驱动设计）
- 核心素材：
  - 出发点（先讲为什么）：事务脚本模式（Controller→Service→Dao）是**贫血模型**——对象只有数据没有行为，业务逻辑全堆 Service；后果是同类业务在多个 Service 重复实现、加产品类型就改 Service、越改越难维护。真实案例：统一运维系统因"没有领域模型、需求多方冲突"整个推倒。
  - **领域模型 = 合并了行为和数据的对象模型（充血模型）**：收入确认是合同的职责，calculateRecognition 方法长在 Contract 对象上；新增产品类型只需扩展新产品类与策略类，不改存量（开闭原则在业务层的落地）。
  - DDD 概念链：**领域**（组织业务范围）→ 拆**子域**（用户/商品/订单/库存…）→ 强相关子域组成**限界上下文**（≈子系统/模块边界）→ 上下文之间用**上下文映射图**描述协作。
  - 实体 vs 值对象：**实体**有唯一标识且标识不随状态变化（订单会流转状态但订单 ID 不变）；**值对象**只做度量或描述、**不可变**（地址变了就是新地址）；DDD 建议能用值对象就不用实体。
  - 架构落位：领域层放实体，应用层包装、接口层暴露；**六边形架构**——领域模型居中，HTTP/RPC/MQ 等外部交互全走适配器。收束口径：DDD 的核心是**领域对象及其交互承载业务逻辑**，用了没有 CQRS/事件溯源不是判断标准。
  - 附加判断力：与领域模型冲突的需求很可能是**伪需求**——模型可以反过来校验需求。
- 建议追问：① 为什么说"微服务拆分应该按限界上下文"？（限界上下文就是天热的拆分边界——衔接 be-micro-split）② 充血模型有什么代价？（对象职责重、与 ORM/序列化摩擦、团队心智成本——小业务事务脚本反而务实）③ 实体和值对象的边界拿捏：金额、收货地址该是哪个？
- 建议难度：advanced

### S5. SQL 注入和 XSS 的原理是什么？为什么参数化查询能防注入？
- 来源：第 30 讲（安全性架构）、第 06 讲（PrepareStatement）
- 核心素材：
  - **SQL 注入机理**：用户输入被拼进 SQL 语句改变了语句结构——输入 `Frank';drop table users;--` 让一条 select 变成两条 SQL 执行（查询 + 删表）。本质：**数据越权成了代码**。
  - **防注入正解 = 预编译（PrepareStatement）**：带占位符的 SQL 模板**先提交数据库生成执行计划**，参数后置填入——无论用户提交什么字符串都只能作为参数进入既有执行计划，**不可能再改变 SQL 结构**；MyBatis 等 ORM 底层就是它。工程纵深：最小权限 DB 账号、入口过滤、错误信息不回显 SQL 细节。
  - **XSS 机理**：攻击者把恶意脚本存进服务器（如发微博带 script），其他用户浏览时脚本在其浏览器执行（存储型）。**防御 = 消毒**：HTML 转义危险字符（`>` → `&gt`），让脚本无法执行；入口统一过滤。
  - **WAF（Web 应用防火墙）**：HTTP 攻击必经 HTTP 请求入口，可在统一过滤器或 ModSecurity 类 WAF 拦截危险请求（drop table、script 标签），把防护从各业务点收拢到入口。
  - 与既有密码学题的衔接：拖库场景下敏感数据要**加密存储**（密码单向散列加盐、信用卡对称加密）——"泄露不可怕，能解密利用才可怕"。
- 建议追问：① ORM 用了 PrepareStatement 就绝对安全吗？（拼接场景 ` ${}` 与 `#{}` 的区别、like/order by 无法参数化的白名单处理）② 存储型/反射型/DOM 型 XSS 的差异与 CSP 的作用？③ 为什么"过滤特殊字符"不如参数化治本？（黑名单永远有漏，白名单结构化才是根本）
- 建议难度：basic

### S6. 软件要拆成组件，边界怎么定？组件的内聚与耦合原则有哪些？
- 来源：第 19 讲（组件设计原则）
- 核心素材：
  - 理论前提：软件复杂度与规模成**指数**关系——100 复杂度拆成两个无关子系统，每个是 25 不是 50，所以必须模块化/组件化。
  - **内聚三原则**：**复用发布等同**（复用粒度 = 发布粒度，配 semver 版本号：主版本不兼容/次版本兼容新功能/修订号修 bug）；**共同封闭**（会为同一目的同时修改的类放一个组件——变更局部化）；**共同复用**（不被一起依赖的类别塞进同一组件，否则你的升级强迫别人跟着动）。三原则互相冲突（复用 vs 维护），要按场景权衡。
  - **耦合三原则**：**无循环依赖**（循环依赖的 system "头一天好好的第二天启动不了"，团队在焦油坑里编程；循环多是演进中缺乏依赖评审逐渐形成）；**稳定依赖**（依赖方向指向更稳定的一侧，不稳定的组件不该被大量依赖）；**稳定抽象**（越稳定的组件越抽象——抽象接口独立成组件，JDBC 接口在 JDK、驱动实现各自发布，就是依赖倒置的组件版）。
  - 落地视角：组件边界不只是技术问题，还牵涉业务场景与组织职责（康威定律的伏笔——衔接 be-micro-split 的拆分依据）。
- 建议追问：① 项目里怎么实际发现循环依赖？（架构测试/依赖分析工具 + CI 门禁）② "稳定抽象"和依赖倒置是什么关系？（接口的所有权归高层——与 be-general-design-patterns 的 DIP 追问互通）③ 这六原则和微服务拆分怎么衔接？（组件内聚原则就是服务边界的预演）
- 建议难度：intermediate

### S7. 倒排索引是什么？搜索引擎为什么能在亿级文档里瞬间检索？
- 来源：第 26 讲（搜索引擎架构）
- 核心素材：
  - 正排 vs 倒排：找"文档里有什么词"是正排；搜索引擎要的是"**词出现在哪些文档**"——单词 → 文档列表（posting list）就是倒排索引。
  - 构建流程：爬虫（种子 URL → 抓页面 → 解析超链接入队去重）→ 文档编号 → **分词**（中文要分词器）→ 统计词-文档矩阵 → 按单词组织成倒排。规模直觉：文档万亿但**单词数有限**，索引远小于原文。
  - 查询执行：搜索词分词 → Hash 表定位单词 → 取各自文档列表 → **求交集**（多关键词 AND）→ 结果极快；高频查询再把"搜索词 → 结果"整体缓存，挡掉倒排访问与集合运算。
  - 排序三思路：**PageRank**（超链接 = 投票，权重按链接数均分迭代到收敛——被重要网页推荐才重要）；UGC 站内没有超链接就用**点赞数等集体智慧**信号；要"内容相关性"用**词频 TF**。同一套索引，排序信号决定产品体验（淘宝搜索 = 商品倒排 + 排序即商业模式）。
  - 与既有知识衔接：单词定位用 Hash 表 O(1)（衔接 be-java-hashmap）；MySQL 模糊匹配 `%kw%` 走不了 B+ 树，全文检索要交给倒排（衔接 be-mysql-index-failure 的"前导模糊"）。
- 建议追问：① 为什么 B+ 树做不了全文检索而倒排可以？（B+ 树按前缀有序组织，无法回答"包含某词的所有文档"这一集合问题）② 两个千万级 posting list 求交集怎么优化？（跳表指针/按长度小的遍历/预先按 doc_id 排序）③ 实时新增文档怎么进索引？（分段 + 后台合并——Lucene 段模型一句话）
- 建议难度：intermediate

### S8. 一个 100TB 的文件怎么在 1 分钟内遍历完？从单机文件系统讲到 HDFS 与 MapReduce
- 来源：第 05 讲（文件系统原理）、第 31 讲（大数据架构）
- 核心素材：
  - 单机天花板：Linux **inode** 固定 15 个索引（12 直接 + 1/2/3 级间接），4K 块下单文件上限约 70G；机械盘随机读写受磁头移动（毫秒级）制约——单机文件系统到不了 100T。
  - 递进方案一：**RAID**（多盘当一个用）——RAID 0 条带并行（容量/速度 ×N，一块坏全坏）、RAID 1 镜像、RAID 10 兼得但利用率 50%、RAID 5 N-1 数据 + 1 校验（利用率 N-1/N，坏一块可算回）、RAID 6 双校验防坏两块；单机插盘数有限（8 盘 ≈ 7 倍），仍不够。
  - 递进方案二：**分布式文件系统 HDFS**——设计同构性是答题主线：**inode → NameNode**（元数据：路径/权限/块 ID 与位置），**数据块 → DataNode**（块分布存储），默认 3 副本跨服务器甚至跨机架；客户端可**并行读多个数据块**——数千台集群上并发遍历，1 分钟绰绰有余。元数据与数据分离、数据永不经过 NameNode，与"单机 inode 索引数据块"是同一设计。
  - 存下来还要算得快：**MapReduce 移动计算不移动数据**——计算程序启动在数据所在节点读本地块（数据本地性），map 输出 `<k,v>`，**shuffle 把相同 key 聚到同一 reduce** 完成关联（WordCount 例）；**Hive = SQL 编译成 Operator DAG 再映射到 map/reduce**；**Spark 用内存存中间结果 + RDD 算子链**，复杂计算一个 DAG 完成，性能提升可达百倍；分钟级批处理不够用再上流计算（Spark Streaming 微批 / Flink）。
  - 收束口径：大数据就是**分布式技术在计算领域的应用**，与缓存/MQ/存储同一思想（用更多机器换算力）；差别是数据有关联性，需要中心元数据节点（NameNode/JobTracker）管理。
- 建议追问：① NameNode 是单点怎么办？（元数据快照 + EditLog、HA 双 NameNode + QJM 多数派——衔接 be-distributed-brain-split 已有 HDFS HA/QJM 素材）② 校验数据 P 为什么要螺旋式散在不同盘上？（防某盘坏时同时丢数据+校验）③ 为什么大数据系统都把计算搬到存储侧而不是反过来？
- 建议难度：intermediate

## 二、既有题增强素材（be-general / be-stability / 其他 backend 既有题）

### E1. 目标题目：be-stability-monitoring（监控告警体系怎么搭？SLI/SLO 和黄金指标是什么？）
- 追加素材（第 29 讲）：
  - **可用性 n 个 9 的数量级换算**（SLO 讨论的度量底盘）：2 个 9 = 年不可用 88 小时（基本可用）；3 个 9 = 9 小时；4 个 9 = 53 分钟（有自动恢复能力）；5 个 9 = 5 分钟（极高）。淘宝/百度/微信约 4 个 9。可用性不是越高越好，按产品定投入产出平衡点（金融 > 微博）。
  - **故障分管理**：年初把系统总故障分（如 10 万分）按责任逐层下发到团队和个人，故障定责扣分、负分影响绩效——可用性指标的治理化落法；可与现有点的"错误预算"对照：一个是预算刹车，一个是事后考核，各有适用与副作用（考核可能诱发瞒报——与 blameless 复盘文化张力，答出这层是加分）。

### E2. 目标题目：be-stability-limits-degrade（限流、熔断、降级三者如何协作？）
- 追加素材（第 29 讲 + 第 01 讲）：
  - 降级的**具体判例**：电商"确认收货"是重操作（改订单状态 + 支付确认 + 评价联动，DB 压力大）但非核心（超时自动收货兜底）——大促整天高压时直接关闭，把资源让给交易主链路。降级对象选择的判据：**有系统兜底路径的非核心功能**。
  - **失败隔离靠 MQ 的机理**：消费者故障时生产者照常发消息进队列，故障恢复后续消费——从用户视角系统一直可用；削峰填谷同时是"把压力隔离在队列外"，保护 DB 这类压力敏感服务（现有点讲降级开关，这里补 MQ 作为隔离设施）。
  - 崩溃链条的第一性解释（第 01 讲）：高并发下线程阻塞在锁/DB 连接上 → 阻塞线程一边等待一边占资源 → 超过资源极限宕机——限流降级保护的对象就是这个链条，答题时先画链条再给手段更有说服力。

### E3. 目标题目：be-stability-multi-active（异地多活怎么设计？）
- 追加素材（第 29 讲）：
  - **入口层怎么就近分流**：异地多活的流量分发在 **DNS 域名解析**时按就近原则/策略完成（与 E/S2 的 DNS 负载均衡衔接——DNS 是异地多活的入口地基）。
  - **数据冲突的工程化简化**：易冲突的关键数据不搞双向写，采用"**类主主**"模式——任一时刻仍有逻辑主机房，该类请求只能路由到主机房处理，其余机房不接这类写——用路由纪律规避冲突仲裁的复杂度（与现有点的"单元内闭环是设计纪律"互相印证）。

### E4. 目标题目：be-stability-deploy（重要版本的发布流程怎么设计才能安全兜底？）
- 追加素材（第 29 讲思考题）：
  - **预发布验证的独有价值**：预发机与生产同库同配置、只是外部用户不导入——它能发现测试环境发现不了的 bug：**线上数据量级触发的问题、真实配置/缓存行为、对真实下游依赖的兼容**。答题口径：测试环境验证逻辑、预发验证"生产同构性"。
  - "升级不停机"的原理一句话（作者阿里面试真题）：应用多副本 + LB 心跳摘除——升级时每次只停一部分实例，集群始终有活节点在服务（"飞机飞行中换发动机"）；与现有点的灰度放量形成"物理层（摘实例）× 流量层（按比例）"两个粒度。

### E5. 目标题目：be-stability-capacity（容量规划怎么做？全链路压测的关键设计是什么？）
- 追加素材（第 28 讲）：
  - **压测三阶段的正式定义**（现有点讲"压到 P99 拐点"，这里补曲线的全称术语）：性能测试（预期负载内，吞吐线性涨、RT 平稳）→ 负载测试（加压到安全临界，吞吐见顶回落、RT 上升）→ 压力测试（超过安全负载直到崩溃，得最大承受能力）；稳定性测试（恒定/波动压力长跑）。"拐点"就是负载测试的安全临界点——术语对齐后答题更专业。
  - **吞吐量 = 并发数 / 响应时间**的关系式：压测报告三指标互相验算，能识别"并发数没加上去导致吞吐虚低"这类假数据。

### E6. 目标题目：be-stability-rt-triage（线上接口突然变慢，你的排查路径是什么？）
- 追加素材（第 01/18 讲）：
  - "慢=等"的**系统级放大机理**：一个下游慢 → 阻塞式容器（一请求一线程）的线程被钉死在等待上 → 线程池耗尽 → **无辜接口也被拖死**（未调慢依赖的请求一样排队）。压测对照证据（第 18 讲）：阻塞式网关下服务 1 延迟飙升时，走同一网关的服务 2 错误率同步飙升；非阻塞网关下服务 2 完全不受影响——"故障是否传染"取决于线程模型，这给现有的"依赖层逐一排除"提供了机理解释。
  - 排查时可加一问：容器线程模型是什么（阻塞式/异步非阻塞/虚拟线程）？同样的慢依赖在不同模型下的爆炸半径完全不同。

### E7. 目标题目：be-mq-why-and-choose（为什么要用消息队列？怎么选？）
- 追加素材（第 23 讲）：
  - 三大价值之外的**两个收益**：① **隔离失败**（消费者异常不向生产者传播，故障半径缩小）；② **独立伸缩**（图片处理这类重功能做成消费者集群，单独扩缩容——同步架构下只能扩整个应用集群，代价大）。
  - **异步化的交互设计**（被追问"用户要立刻知道结果怎么办"时的标准答案）：提交订单发消息后立即返回，App 展示"订单处理中"进度态，消费完成后推送最终结果——异步架构的产品层配套，能答出这层说明真用过。

### E8. 目标题目：be-mysql-replication（主从复制的原理是什么？）
- 追加素材（第 25 讲）：
  - **主主复制的定位澄清**：两台互为 binlog 复制，但**只提升写可用性、不提升写性能**——任意时刻只能有一个主库承接写（应用全部连同一主），故障时才切换；双向都能写必然数据冲突。与现有点的切换/脑裂话题互补。
  - **一主多从的角色分工**：不同从库按用途分化——实时分析、批任务报表、纯备份——读压力分型承载，从库宕机读流量迁其他从库保证读高可用（写高可用才需要主主/MGR）。

### E9. 目标题目：be-mysql-sharding（什么时候需要分库分表？）
- 追加素材（第 25 讲）：
  - **混合部署阶梯**（现状点讲单库到分片，这里补"分库"与"分片"的两级）：单库 → 主从复制（读扩展 + 可用性）→ **业务分库**（类目库/用户库按业务域拆到不同实例——数据量与访问量差几十倍时先做这级）→ 热点库（如用户库）再**数据分片**，每个分片内部还可以继续主从/主主。能区分"业务分库（垂直）"与"数据分片（水平）"两级是基础功。
  - **分片中间件的透明化原理**：硬编码分片（偶数用户→库 1）导致扩容要改业务代码、分片逻辑与业务逻辑耦合互坑；MYCAT 类中间件让应用像连单机 MySQL 一样提交 SQL，中间件**解析 SQL 提取分片键（如 prov=wuhan）→ 路由到目标库**——分片逻辑配置化、对应用透明（与现有点 ShardingSphere 同族，可作演化脉络补充）。

### E10. 目标题目：be-mysql-query-execution（一条 SQL 在数据库里是怎么执行的？）
- 追加素材（第 06 讲）：
  - **连接器与连接治理**（现有四步流程的第一站展开）：建立连接对 DB 是重操作（分配专用会话内存），连接**即使空闲也占内存**——应用集群规模 × 连接池大小会打爆 DB；治理两手段：**连接池**及时释放空闲连接 + **微服务化减少连接数**（把用户访问收敛到独立部署的用户服务小集群，只有这几个实例连用户库）。这是"微服务为什么能顺便救 DB 连接"的冷门考点。
  - **PrepareStatement 两个好处**（第 06 讲核心论点，S5 的原理版）：预提交模板提前生成执行计划，执行时省解析（性能）；参数后置无法改变执行计划（防注入）——与 S5 分工：S5 讲攻击面，这里补执行链路视角。

### E11. 目标题目：be-redis-consistency（缓存与数据库的双写一致性怎么保证？）
- 追加素材（第 22 讲）：
  - **脏读治理的两条路线**（现有点讲删除时序，这里补课程的总纲）：**过期失效**（写缓存时标 TTL，读时检查过期回源——实现简单，代价是窗口内脏读；实践中更多用它，因为多数业务可容忍分钟级不一致）vs **失效通知**（更新数据源同时删缓存，更及时但要处理通知失败）；现有点的"先更库再删缓存"就是失效通知路线的具体化。
  - **缓存适用的前提是热点**：缓存内存有限，只有**会被重复读取的热门数据**值得放；无热点的数据写进缓存只会挤占空间、命中率趋零——"加缓存"前先看访问分布，这是现有题谱系没点破的前置判断。
  - 缓存三大收益的完整表述（答题开场的价值陈述）：更快（内存+更近距离）、更省 CPU（缓存的是计算结果对象）、**卸载下游**（DB/源站压力转出，释放的资源给写路径——间接提升整系统吞吐）。

### E12. 目标题目：be-general-design-patterns（常见设计模式的使用时机？SOLID 里哪条最有实战价值？）
- 追加素材（第 10-12/16/17 讲 + 设计模式答疑）：
  - **设计腐坏五特征**（Robert Martin 的 design smells，判断"这段设计烂在哪"的词表）：**僵化**（小改动牵连大范围）、**脆弱**（改动引发无关联处崩溃）、**牢固**（无法拆分复用——"没解决牢固性就硬上微服务只会放大问题"）、**粘滞**（烂方案比好方案更容易实施，软件向烂漂移）、**晦涩**（代码难读导致维护者以设计者未预期的方式改）。五词给"怎么答'你见过什么烂代码'"提供结构。
  - **开闭原则的速判法**："看到 switch/case 或 if/else 判类型，基本可以判断违反开闭原则"；实现开闭的关键是**抽象**（依赖抽象接口 + 多态扩展），策略/适配器/观察者/模板方法是同一个原则在不同扩展场景下的形态（课程用同一个 Button-Dialer 例子依次演进四个模式——讲清"模式是开闭原则的解法族"这条主线，比背二十三个模式高一个层次）。
  - **多态是模式精髓**：封装和继承 C 语言都能模拟，唯独受语法约束的多态是 OOP 独有——设计模式 = 对多态的灵活应用。
  - **依赖倒置的精髓 = 接口所有权倒置**：不是"依赖接口"就算 DIP——接口要由**高层定义、低层实现**（Service 定义接口 DAO 实现，而不是反过来）；好莱坞原则"别调用我，我会调用你"就是框架的原理（应用实现 Servlet 接口被 Tomcat 调用）。
  - **框架中的模式实证**：Tomcat×Servlet = 策略模式、HttpServlet.service 按 method 分发 doGet/doPost = 模板方法、JUnit 的 runBare（setUp→test→tearDown）= 模板方法、TestSuite 递归包含 = 组合模式遍历树。被问"模式在哪用过"时，用框架源码级例子替代背书。
  - **过度设计的边界**（设计模式答疑）：预期中的变更没发生 = 设计过度；变更发生了还在硬编码打补丁 = 设计不足——**是否用灵活设计看场景**，场景变了（第一次出现复用需求）就立刻重构，别等 hold 不住。

### E13. 目标题目：be-micro-split（微服务应该怎么拆？）
- 追加素材（第 27 讲）：
  - **单体五痛点**（答"为什么要微服务"的实证清单，全部出自阿里 2008 年实践）：编译部署慢（几 G war 包改一行编译半小时）、分支 merge 冲突集中爆发在发布夜、**应用实例太多耗尽数据库连接**（微服务化顺带救 DB，与 E10 互证）、新人半年难上手、全部门陪绑值班发布。
  - **微服务失败的根因判定**：微服务与缓存/MQ/NoSQL 不同，**和业务强相关**——单体时代模块边界就没拆清（牢固性），服务化只会把混乱放大到网络上；"重点全在微服务框架上"是失败团队的共性。
  - **倒三角决策模型**（现有点讲怎么拆，这里补"要不要拆"的决策序）：需求（要用微服务达到什么）→ 价值 → 设计原则 → 最佳实践 → **最后才是工具选型**；从工具倒推需求是典型的本末倒置（与 be-micro-modular-monolith 的"默认不拆"口径互相支撑）。

### E14. 目标题目：be-java-jvm-memory（JVM 内存区域是怎么划分的？）
- 追加素材（第 03 讲）：
  - **报错 → 参数/工具的映射表**（把 OOM 分类落到处置动作）：`OutOfMemoryError` → 先判断堆不足还是泄漏——调 `-Xmx` 或 `jmap` 看堆对象分布找"容器持有不再使用对象"的泄漏；`StackOverflowError` → 栈帧过深，先从栈信息查错误递归，正常再调 `-Xss`；运行卡顿部分请求延迟高 → `jstat` 看 GC 状况、重点看 Full GC 时长，再调收集器参数。
  - **JIT 一句话**：字节码解释执行慢，JVM 把热点代码编译成本地指令缓存（`-server` 启用 C2）——Web 长时运行应用受益明显；能解释"为什么 Java 服务预热后更快"。

### E15. 目标题目：be-java-threadlocal（ThreadLocal 的题，或 Spring Bean 相关题）
- 追加素材（第 01/03 讲）：
  - **"Web 开发天然是多线程开发"**：不管你是否有意识，容器（Tomcat）就是多线程执行你的代码——每请求一线程调 Servlet/Controller。由此推出 Service/DAO 惯例设计的理由：**无状态对象**（不写成员变量、方法只操作局部变量与入参）天然线程安全，这是"为什么单例 Bean 不加锁也能用"的原理级答案。
  - 反面判例：Servlet 里写可变成员变量（如计数器/临时状态）就是共享可变状态事故源；需要状态时正解是 ThreadLocal（线程内隔离）或外部化到 Redis/DB。这条与 be-java-virtual-thread 的"ThreadLocal 在虚拟线程下反而更干净"形成新旧对照。
