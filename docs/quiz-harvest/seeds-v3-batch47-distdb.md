## 一、候选新题（现有题库未覆盖）

### S1. 分布式数据库的分片元数据存在哪？路由信息过期了怎么办？
- 来源：06 分片机制（思考题）、07 数据复制、08 基础篇大串讲（容量上限推算）
- 核心素材：
  - 元数据的特殊地位：路由每个请求都要先查元数据（分片范围/数据量/读写流量/副本分布/副本状态），**它既是性能瓶颈点又是高可靠短板**；动态分片下元数据还在不断变化（分裂/合并/迁移），叠加了多副本一致性问题。
  - 三种方案谱系：**静态分片**（元数据不变，直接多副本放工作节点，TBase 放协调节点——副本多但无需一致性协议）；**集中式小集群**（TiDB 的 PD：TiKV 心跳**主动全量上报**元数据，PD 把调度指令放在心跳返回里，因此 **PD 甚至可以不落盘元数据、做成无状态服务**——宕机新主无需状态衔接，一个心跳周期即恢复；etcd 只持久化少量缓存性信息）；**去中心化 P2P**（CockroachDB：Gossip 协议传播，每个节点存全量元数据）。
  - **协议选择法则：副本/节点少用广播（Paxos/Raft），节点多用 Gossip**——广播的成本 O(N) 随节点数爆炸，Gossip 是"谣言式"小范围传播、最终一致。
  - **元数据最终一致为什么能撑住强一致数据库（关键反直觉点）**：CockroachDB 寻址时若按本地旧元数据打到节点 B，B 会回复"该 Range 现在在节点 C"，A 据此**二次路由并顺手更新本地元数据**——读路径本身成了元数据的收敛机制（"No Stale Reads" 靠纠正回路而不是元数据强一致）。
  - 容量上限推算（好的量化追问素材）：CRDB 元数据是两层索引 Meta1→Meta2，两者都是 18 位、Meta1 不分裂保稳定 → 最多 2^36 个分片，默认分片 64M → **总容量上限 ≈ 4EB**。"水平扩展"也有上限，上限由元数据结构决定。
- 建议追问：① 为什么动态分片不能把元数据放所有工作节点？（更新同步代价 = 副本数 × 写放大）→ ② PD 无状态化省掉了什么、付出什么？（省主备状态衔接，付每请求心跳上报开销 + 单点写瓶颈仍在）→ ③ Gossip 收敛窗口内用户请求会失败吗？（不会——二次路由纠正，代价是一次额外跳转）
- 建议难度：advanced

### S2. 分布式数据库的全局时钟有哪些实现？TSO、TrueTime、HLC 怎么选？
- 来源：05 全局时钟、02 强一致性、29 产品图鉴
- 核心素材：
  - 分析框架三要素：**时间源单/多、物理时钟/混合逻辑时钟、授时点单/多**——8 种组合里工程上只剩 4 类：TrueTime（Spanner，多源+物理+多点）、HLC（CockroachDB/YugabyteDB，多源+混合逻辑+多点）、TSO（TiDB/OceanBase/GoldenDB/TBase，单源+单点；PGXC 里同角色叫 GTM）、STP（巨杉，单源+多点，介于两者之间）。
  - **TrueTime**：GPS+原子钟硬件授时，误差 ≤7ms（均值 4ms）；多点授时完全去中心化、客户端与时间服务器距离可控——**全球化部署的唯一解**；代价是依赖硬件，开源产品拿不到。
  - **TSO 细节（TiDB PD 的工程实现，可背诵）**：时间戳 = 高位物理毫秒 + 低位 18 位逻辑值（1ms 内可发 2^18≈26 万个）；多个 PD 构成 Raft 组选主；**预申请时间窗口**——PD 主向 etcd 申请"3ms 可分配窗口"（如 103~106ms）后才对外发号，因此 etcd 里存的最大时间戳永远 ≥ 已发时间戳高位，**新主读取 etcd 最大值再申请新窗口，保证新主发的时间戳必然大于旧主**（避免了每个时间戳落盘的性能灾难）；客户端可一次批量取多个时间戳摊薄 RTT，但缓存期间多客户端不再严格单调。
  - **HLC**：Lamport 逻辑时钟的物理混合变体，(L,C) 二元组——本地事件取 max(上一事件 L, 本地物理时间)，跨节点调用把 HLC 随消息传递、收方取三方 max；**纯软实现、不依赖硬件、单调递增、不受本地时钟回拨影响**；但对无调用关系的并发事件无法精确排序（本质是偏序），且仍依赖 NTP 保证本地时钟大致准确——所以 CRDB 定位"接近因果一致性"而非线性一致。
  - 选型逻辑一句话：**TSO 简单且能给严格全序，但单点授时限制集群部署范围与性能上限；TrueTime/HLC 支撑全球化部署，但要专门处理时间误差**（引出 S3）。
- 建议追问：① PD 宕机切换时时间戳为什么不会回退？（etcd 时间窗口预申请机制，逐条讲清）→ ② 为什么不用 NTP 直接当全局时钟？（误差大且不保证单调）→ ③ 客户端缓存时间戳破坏了什么性质？业务上可接受吗？
- 建议难度：advanced

### S3. 时钟有误差，Spanner 怎么保证外部一致性？"TPS 只有 125"是怎么回事？
- 来源：12 隔离性（看不见的读写冲突）、15 分布式事务串讲
- 核心素材：
  - 问题本质：任何时间读数都是**置信区间**（Spanner TT.now() 返回 [earliest, latest]，ɛ≤7ms）；"事务 T2 已提交"与"事务 T6 已启动"的两个时间窗口若**重叠**，就无法判定先后——这是**看不见的读写冲突**，比显式冲突更隐蔽。
  - 解法总纲：**"waiting out the uncertainty"，用等待把不确定性熬过去**。两种流派：**写等待**（Spanner commit-wait——所有写事务受影响）vs **读等待**（CockroachDB——只读操作受影响但可能反复触发）。
  - Spanner commit-wait 的精确账本：事务拿提交时间戳时取 TT.now() 的 **latest**（保证大于所有参与者的预备时间戳，这里已消耗一个 ɛ），再等待直到 TT.after(s) 为真（再消耗一个 ɛ）——**实际等待 2ɛ，均值 8ms**；"Spanner TPS=125"就是把 1s/8ms 用在**数据重叠的事务**上算出的极端值，不重叠的读写事务可完全并行——能纠正这个误读是深度得分点。
  - CockroachDB 读等待：读时间戳若与某已提交数据的提交时间戳间隔 < max clock offset（默认 250ms，NTP 同步误差），**重启读事务拿更晚时间戳**；重启后可能又落入下一个写事务的不确定窗口，**需要多次重启才能跳过所有窗口**——偶发但单次等待可能更长。
  - 免等待的两个理论出口（串讲篇答案）：① 用 TSO 单点授时，事件发生时已按全序记录，无需等待；② Lamport 偏序视角——两地距离/光速 > 时间戳间隔+误差（X>Y+Z）时两事件物理上不可能有因果，本就是并发、无需等待。
  - 权衡收束：写等待影响面大但等待时间确定（适合误差小的系统，7ms）；读等待影响面小但等待时间不可控（适合误差大的系统，250ms）——**误差量级决定了机制选型**。
- 建议追问：① 为什么 Spanner 实际等 2ɛ 而不是 ɛ？（2PC 预备时间戳 + latest 取值各吃一个区间）→ ② CRDB 250ms offset 设小一点行不行？（offset 小于实际 NTP 偏差会破坏正确性——这是"拿正确性赌时钟"）→ ③ TSO 系统为什么完全不用等待？
- 建议难度：advanced

### S4. 2PC 有三大问题，分布式数据库是怎么把它优化到能用的？
- 来源：09 原子性（2PC/Percolator/GoldenDB）、10 原子性（延迟优化）、15 串讲（Paxos Commit）
- 核心素材：
  - 问题的量化起点：2013 年 Percona Live 数据——**MySQL XA 事务延迟是单机事务的 10 倍以上**（跨两个节点）；结论先立住"2PC 不能裸用"。
  - **Percolator 模型（NewSQL 阵营的标准答案）**：前提是存储支持 MVCC；Prepare 阶段每条参与记录写私有版本 + 锁，**随机选一条记录持主锁（Primary Lock），其余记录的锁存指针 primary@row**；Commit 阶段**协调者只与主锁所在分片通讯**，该提交动作本身原子——第二阶段"多参与者通讯不一致"的问题被结构性消除；从锁记录被读到时按指针查主锁状态即可判定可见性，再由异步线程把从锁版本"转正"；单点故障靠事务日志多副本化（协调者无状态化）+ 异步清理线程兜底。TiDB 完全照此实现；CockroachDB 变体是不随机选主锁，改为**全局事务表**，所有记录指向事务表中该事务的记录。
  - **GoldenDB"一阶段提交"（PGXC 阵营的答案）**：第一阶段不碰数据节点，协调者在 **GTM 全局事务列表**中把事务标记为活跃（用全局列表申请资源、提前暴露竞争），第二阶段才拆子事务下发——本质是**并发控制从锁调度换成时间戳排序**，正常路径协调者与数据节点只通讯一次。
  - **Paxos Commit（Gray & Lamport 2006，两人分别是 2PC 和 Paxos 的提出者——冷知识得分点）**：每个参与者把 Prepared 消息发给**所有 Acceptor**，Leader 基于多数派汇总**投票裁决**事务命运——协调者不再有独立判断；2F+1 个 Acceptor 给每个 RM 提供 2F+1 条通讯路径，容忍 F 条路径故障；代价是消息数大增 + 多一跳延迟，产品中很少用。
  - **延迟优化的递进（可推导，不是背结论）**：延迟公式 L_txn = (W+1)×L_c（W 个写各一轮共识 + 提交一轮）；① **缓存写提交**（TiDB）——攒所有写 SQL 到 commit 才执行 → 2×L_c，副作用是**交互语义变了：MySQL 的 First Write Win 变成 First Commit Win**，且长事务+高并发会撑爆缓存；② **管道 Pipeline**（CRDB）——写操作不等返回连续下发，准备阶段≈最慢一个写 → 仍 2×L_c 但悲观协议下也适用；③ **并行提交 Parallel Commit**（CRDB）——意向写的同时以 STAGING 状态落事务记录、记录 Writes key 清单，客户端收齐意向写成功即可返回，**异步线程事后按线索确认并落盘终态** → 压缩到 1×L_c。"只做最少的工作、留下可倒推的线索"是 Percolator 一脉相承的设计哲学。
- 建议追问：① Percolator 第二阶段只联系一个分片，为什么是原子的？（主锁记录上的提交标记即事务终态）→ ② 并行提交异步落盘前宕机，事务状态怎么恢复？（Writes 清单倒推）→ ③ 缓存写提交在什么并发场景下行为和 MySQL 不一致？（同 key 竞争时获胜方从"先写"变"先 commit"）
- 建议难度：advanced

### S5. TiDB 和 CockroachDB 为什么都把默认并发控制从乐观改成了悲观？
- 来源：13 隔离性（乐观协议）、14 隔离性（悲观协议/SSI）
- 核心素材：
  - 理论框架（比"乐观=不加锁"准确得多）：并发控制统一为 V-R-C-W 四阶段，悲观 = **VRCW**（先验证后读写）、乐观 = **RCVW**（先读写提交前验证）；区分**全局有效性验证 vs 局部有效性验证**是关键——TiDB 的"乐观锁"（Percolator）每个 key 上有锁、局部看是悲观的，但**没有全局验证，整体仍是广义乐观**；狭义 OCC（严格 RVW + 基于时间戳的验证算法，学术文献所指）生产级分布式数据库只有 FoundationDB 在用。
  - 改回悲观的两条硬理由：① **乐观的前提"冲突少"在金融场景不成立**——代发工资类长事务批量更新上万账户，期间任何一条冲突就整体回滚重试，可能永远跑不完；② **遗留应用兼容**——单体数据库全是悲观协议，`select for update` 这类显式加锁语义在乐观协议下没有对等实现，生态迁移成本不可接受。
  - TiDB 悲观化的实现：在原有局部验证前增加**全局有效性验证**——锁以占位符形式随 SQL 执行**即时**发往 TiKV（严格 VRW）；副作用：从"攒批提交"变回交互式事务，**必须新增死锁检测**（原本几乎无死锁）。
  - CockroachDB 的路线不同：它的目标隔离级别是 **SSI（可串行化）**，核心是**串行化图检测 SGT**——事务为节点，WR/WW/RW 反依赖为边，**成环即不可串行化**；RW 反依赖是锁无法记录的（PostgreSQL 论文用 SIREAD 标识读集合，但读范围太大、跟踪成本反超 S2PL）；CRDB 的优化是**读时间戳缓存 RTC**——按 key 范围记录读时间戳（where 范围读整段记录，类似间隙锁的效果），写前查 MRT（最大读时间戳）判断是否形成 RW 依赖，LRU 淘汰 + 低水位线兜底；无锁管理成本使可串行化第一次达到生产级性能；后来同样加了**全局锁表**做前置全局验证（与 TiDB 同方向收敛）。
  - 经典反直觉素材：**只读事务也会破坏可串行化**——PostgreSQL 论文的批次号例子（记账 T2/关批 T3/日报 T1），T1 纯读却让 T2、T3 形成 RW 环，一笔收入"神秘消失"；写倾斜 = "不易察觉的更新丢失"（黑白球例子）。
- 建议追问：① 为什么 Percolator 本质是 S2PL？（主锁不放从锁全不放）→ ② RTC 怎么覆盖"读之后插入范围内新行"的场景？（按 key 范围而非具体 key 记录）→ ③ S2PL 实现可串行化为什么性能不行？（锁持有时间贯穿事务，并发度崩塌；TDSQL 要用 SS2PL 才够）
- 建议难度：advanced

### S6. 单机 MVCC 天然读写不阻塞，为什么到了分布式数据库反而不灵了？
- 来源：11 隔离性（MVCC 与快照）、03 强一致性（Critique/隔离级别）
- 核心素材：
  - 单机原理一句话版本：MVCC 记历史版本消读写阻塞；**快照 = 事务启动时申请的"活动事务列表"**（配合最小活跃 ID/最大已提交 ID 两个边界快速排除）——**RC 是每条语句取一个新快照，RR 是整个事务复用同一个快照**，这就是两者可见性差异的全部来源（MySQL 叫 ReadView、PG 叫 SnapshotData，组织方式相同）。
  - MVCC 三种历史版本存储：**Append-Only**（PG，新旧同表，回滚快、查询随版本数变慢）；**Delta**（MySQL/Oracle，回滚段增量，省空间但旧版本要逐段追溯计算，Oracle ORA-01555"快照过旧"= 回滚段循环使用被覆盖）；**Time-Travel**（HANA，全量独立存储，读得快、费空间）。
  - 分布式化的两个新依赖：RR 快照要跨节点工作，需要 **① 单调递增的全局事务 ID + ② 全局活动事务列表（全局快照）**——所以 PGXC 架构必须有一个 **GTM（全局事务管理器）**集中发号与维护事务状态，它同时就是"全局时钟"，也顺理成章成为单点瓶颈。
  - **TiDB 的取舍（考点）**：没有设计全局事务列表（避免 GTM 单点），代价是 Prewrite 与 Commit 之间的读会被阻塞——**看起来退回了 MVCC 之前的读写阻塞**，这是"读写并行能力 vs 全局事务列表维护代价"的显式权衡，不是疏忽。
  - **CockroachDB 的取舍（考点）**：有全局事务表却同样读写阻塞——因为目标是 SSI：先读后写会产生 **RW 反向依赖**，任何等价串行顺序下结果都不同，快照隔离无法消化；做法是冲突时**重启其中一方拿新时间戳**，按事务**优先级**裁决谁让路（高优先级继续），被重启方优先级提升防饿死。
  - 收束：**MVCC 是底层技术不是协议**——它与乐观/悲观正交，组合出 MVTO/MV2PL/MVSGT；"分布式数据库没有普遍用快照解读写冲突"是高频认知差，根因都在全局快照的代价。
- 建议追问：① RC 和 RR 的快照差异用活动事务列表怎么解释？→ ② GTM 为什么既是全局时钟又是快照提供者？（事务 ID 单调递增 ≈ 时间戳）→ ③ 想要全局快照又不想单点，有什么思路？（HLC 时间戳定序 + 延迟清理水位线，CockroachDB/CRDB 实际演进方向）
- 建议难度：advanced

### S7. 在数据库内部，Range 分片为什么比 Hash 分片更"高级"？
- 来源：06 分片机制、08 串讲、17 自增主键
- 核心素材：
  - 概念对照表：分片在各系统的名字——Spanner/YugabyteDB 叫 **Tablet**、HBase/TiDB 叫 **Region**、CockroachDB 叫 **Range**；分片机制两要点 = **分片策略（Hash/Range）+ 调度机制（静态/动态）**，两要点与架构风格强相关。
  - PGXC = 静态分片：Hash（本质是一致性哈希+虚拟节点，GoldenDB 默认、TBase 仅 Hash）写分布均匀但**查询扫描 I/O 差、无法消化业务热点**；Range 可按业务预估切（京沪按区县、海外按国家），但受限于单体数据库实现、**不能随数据与负载变化自动调整**。
  - NewSQL = 动态 Range：**自动分裂/合并**（单分片超阈值一分为二、小分片周期合并）+ **按访问压力调度**（热点分片挪到空闲节点）——存储均衡与压力均衡双目标；TiDB 仅支持 Range、CRDB/YugabyteDB 两者都支持。
  - **Spanner 独有的 Directory 设计（其他产品无工程化实现）**：在 Tablet 之下再设目录作为调度最小单位、调度范围可跨 Tablet——把**频繁参与同一事务的数据聚到同一 Tablet 下，把分布式事务变本地事务**（减少分布式事务），还能把 Directory 挪到**靠近用户的数据中心**（缩短延时）；代价是分片内记录不再连续、扫描变贵，调度器要在存储/压力/事务/延时**四个目标间权衡**。
  - 高可靠单元的差异（架构题眼）：NewSQL 以**分片为单位组 Raft/Paxos 复制组（Group）**，主副本可散布在所有节点、故障影响面小；PGXC 以**节点为单位主备复制（Set，TDSQL 术语）**，半同步为主、备机不提供有效服务、资源浪费——Group 比 Set 高可靠单元更小、资源利用率更高。
  - 尾部热点（与 be-distributed-id 呼应的量化案例）：CockroachDB 官方对比测试，三节点跨机房集群跑单调递增主键 insert，**TPS 34,587 且负载集中单节点**；改 Hash 分片后 **61,113（1.77 倍）**——Range 分片下单调主键会把写入压缩进最新 Range，集群退化为单机写。
- 建议追问：① 为什么说"解锁了数据与节点的绑定"是 NewSQL 架构先进性的根源？（数据可移动 → 调度空间）→ ② 分片是不是越小越好？（CRDB 512M 上限 vs TiDB 96M——越小阻塞概率越低但扫描成本越高）→ ③ Spanner 的 Directory 为什么没人抄工程化？（四目标权衡的调度器复杂度）
- 建议难度：advanced

### S8. 分布式数据库的异地多活怎么部署？"两地三中心五副本"为什么是主流？
- 来源：24 全球化部署、01 定义（RPO/RTO）
- 核心素材：
  - 单体时代的进化链（对比垫底）：**异地容灾**（异地库冷备，资源浪费、异地应用仍访问远端库）→ **异地读写分离**（异地只读、不保证一致）→ **双向同步**（两地读写不同数据 = 单元化，仍未解决"两地操作同一份数据"）。共同缺陷：异地机房永远进不了主服务。
  - **两地三中心五副本**：同城双机房各 2 副本 + 异地 1 副本；**同城 4 副本即过半 → 写延迟不被跨城 RTT 拖累**；同城一机房挂掉时异地副本的选票与另一机房凑成多数派（容灾成立，但提交要走异地通讯、延迟上升）；异地是异步备份 → **RPO 不为零**。
  - **三地五副本**：两个"同城"换成相邻城市（如北京-天津，RTT 10ms 内），牺牲一点延迟换**城市级 RPO=0**；再往上还有三地五中心七副本。核心公式：**只要坚持低延迟，真异地就做不了 RPO=0**——这是物理规律不是工程不足。
  - **为什么 TiDB/OceanBase 做不到全球化部署（根因链）**：TSO 单时间源 → 授时节点不能离 Leader 远 → **所有分片主副本必须钉在主机房** → 其余机房 3/5 的节点长期低负载；还引出"**远端写入时间戳异常**"：远端节点取时戳后因通讯慢，携带更旧时间戳的写入晚到，被存储节点拒绝（时间线倒挂）——高并发高冲突场景（如抢付商户账户）会频繁写失败。
  - 全球化部署形态：TrueTime/HLC 多点授时下主副本按需分布、主副本可漂移，异地机房提供**全服务**（读写都在本地完成）——"时刻运行着的系统比三个月演练一次的系统更让人放心"是对异地容灾演练模式的根本否定。
  - 两个进阶讨论点：① **Raft 降级机制**——从恶意攻击视角（挖断机房间光缆）看，多数派协议反而让"三中心同时通讯"成为致命弱点；少数派保数据完整时是否该继续服务？由此出现允许放弃多数派投票的降级设计（RPO=0 是手段、持续服务才是目标，别为手段牺牲目标）。② **Follower Read 的一致性难题**——CRDB 的 Follower Read 不保证一致、TiDB 的 Follower 尚不支持跨机房；课程给出的思路：利用 Raft **日志无空洞**特性等"日志时间戳 > 查询时间戳"再读，冷分片靠多 Raft 组**合并发包携带时间戳**判断新鲜度。
- 建议追问：① 五副本为什么不是异地对半放？（过半派必须落在低延迟域）→ ② 主副本钉死主机房的方案损失了什么、换来了什么？→ ③ Raft 降级服务和脑裂防御怎么共存？（降级要显式配置 + fencing，不能是静默行为）
- 建议难度：advanced

### S9. 为什么说 Aurora 不算分布式数据库？共享存储和 shared-nothing 是两条什么路线？
- 来源：01 定义（思考题答疑）、08 串讲、04 架构风格、26 容器化
- 核心素材：
  - 判据一句话：**Aurora 存储水平扩展（S3 之上的分布式存储 + 6 副本日志落盘），但计算（写）仍是单主垂直扩展**（1 写 15 读）——而分布式数据库的定义要求**写入能力可水平扩展**（写多读少、海量并发 OLTP），所以它是"云原生数据库"而非 NewSQL。同路线：PolarDB、CynosDB、华为 Taurus。
  - 两条路线的账本：**共享存储（Share Storage）**——计算无状态可秒级漂移、存算独立扩容、对象存储便宜；**代价**是计算与存储间网络延迟税、写不可水平扩展、主备元数据缓存有 <100ms 延迟（备节点读不保证严格一致、不能接写）。**Shared-nothing（NewSQL）**——数据副本与节点绑定、本地盘性能高、写随节点扩展；代价是运维复杂度、共识延迟税、弹性差。
  - WAL 视角看持久性三级方案（第 3 讲素材）：本地同步/半同步复制（传统）→ **日志落共享存储**（Aurora：日志即数据库，6 副本 4/6 多数派）→ Paxos/Raft 共识同步（NewSQL）——三者都在解决"硬件损坏时本地之外有一份完整日志"。
  - 演进动态：NewSQL 也在向存算分离回拨（TiFlash 支持 S3 存算分离部署）——**两条路线按负载形态选，云原生 ≠ 必胜**；Aurora 式多租户化后还能"一个集群服务多实例"，降低小用户运维复杂度（第 28 讲：城商行把分布式数据库当 Aurora 用）。
  - 与容器化的接口（第 26 讲）：分布式数据库本地盘模式与 K8s 远程 PV 冲突 → **Local PV**（1.14 转正）+ **StatefulSet**（拓扑状态：DNS 稳定标识 + 序号顺序；存储状态：PV 跟随重建）+ **Operator**（把"Kubelet 活着但应用挂了"这类产品特定的运维知识代码化，etcd Operator 是鼻祖，TiDB/CRDB 都有自己的 Operator）——判断一个 NewSQL 云原生成熟度就看这三件套。
- 建议追问：① Aurora 为什么 15 个只读副本不能承接写？（单主写路径 + 元数据缓存延迟）→ ② 给定业务：读弹性大、写稳定 TB 级，选哪条路线？→ ③ 数据库上 K8s 最大的技术阻力是什么？（有状态 + 高 IO vs 远程存储性能损失）
- 建议难度：intermediate

### S10. 把分布式数据库的数据同步给下游（CDC），为什么比单机难？
- 来源：25 容灾与备份（逃生通道）
- 核心素材：
  - 场景定位：分布式数据库作为新技术需要**逃生通道**——向用户信任的单体数据库（逃生库）异步复制全量数据，兜底异构高可用；CDC（读 redo/raft log 生成变更流）是唯一业务零侵入的方案（对比数据文件导出、ETL 都要表结构侵入），对源端资源占用仅 5%~10%（Oracle OGG、DB2 Infosphere 是老牌实现）。
  - 两个工程适配点：**日志格式适配**（PGXC 用 MySQL 内核 → binlog 天然兼容；NewSQL 靠兼容协议输出，TiDB 兼容 MySQL、CRDB 兼容 PG）；**性能悖论适配**（选分布式就是嫌单体慢，逃生回来单体扛不住 → 加 Kafka 缓冲削峰）。
  - **核心难题：跨分片事务的变更顺序**。单分片的 WAL 天然有序；但一个分布式事务的变更散在多个分片、各分片独立发流——下游"收到更大时间戳"不能推出"上一时间戳的事务已收全"。经典错误案例：转账事务（扣 5 万 + 买理财 + 扣手续费跨两分片），逃生库先执行了收到的一半 → **暴露了对外不可见的中间态（余额 1 万），连 RC 都不满足**。
  - **CockroachDB 的 Resolved 时间戳（标准答案）**：每个节点在变更流中插入"ts:Resolved"标记，承诺**此后不再发出 ≤ts 的任何变更**；下游见到某时间戳在所有相关节点都 Resolved，才执行该事务——用"封闭标记"替代"猜测收全"，这是流式系统中 watermark 思想的同构实现（可迁移到任何多流合并场景）。
  - 延伸：CDC 对单体数据库是边缘工具，对分布式数据库却是核心组件（TiCDC/CockroachDB changefeed/GoldenDB 均官方出品）——同一技术在不同架构里的地位反转，是很好的架构观察素材。
- 建议追问：① 单分片变更流在新方案里就一定有序吗？（分片迁移/合并时顺序仍会乱，思考题）→ ② Resolved 与 Flink watermark 的异同？→ ③ 为什么逃生库选型要选"用户最熟悉的"而不是"性能最强的"？（逃生通道要的是信任与运维确定性）
- 建议难度：advanced

## 二、既有题增强素材（be-distributed 10 题 / be-mysql-sharding）

### E1. be-distributed-cap（CAP 定理）
- 追问素材：**"分布式数据库的强一致"和 CAP 的 C 是一回事吗？**——不是：分布式数据库的强一致性 = **数据一致性（副本读写）+ 事务一致性（ACID 隔离）** 的融合，最高点是**严格串行化（Strict Serializable）**，两条路径各自实现难度叠加，"少有产品在顶端汇合"；Spanner 的外部一致性 ≈ Strict Serializable，且它仍提供有界旧一致（Bounded Staleness）做性能档位。另一个高频混淆：**"一致性协议"的"一致"是 Consensus（共识），数据一致性的"一致"是 Consistency——翻译事故**；Paxos 本质是复制协议（副本同步策略），数据一致性模型还要叠加"读写策略"才算完整。一致性模型强弱排序可作加分：线性 > 顺序 > 因果 > {写后读、单调读、前缀}（后三者互不可比）。MySQL 全同步复制的可用性算术：单机 95% × 三台串联 = 85.7%——"状态视角的强一致与可用性不可兼得"的具象化。

### E2. be-distributed-consistent-hash（一致性哈希）
- 追问素材：**数据库语境与缓存语境的差异**——缓存场景一致性哈希是主角（无主、数据归属由环决定）；数据库里它只是 PGXC 的静态分片手段，NewSQL 主流反而选动态 Range（可自动分裂/合并 + 按压力调度，Hash 分片过滤掉了业务属性、永远解不了热点 key）。回答时能给出产品事实更佳：GoldenDB 默认 Hash、TBase 仅 Hash、TiDB 仅 Range、CRDB/YugabyteDB 双支持；CRDB 官方 benchmark 中同一集群 Range→Hash 把单调主键写入 TPS 从 34,587 提到 61,113（1.77 倍）——"Hash 防倾斜、Range 好扫描好调度"的两难是真实存在的工程取舍。

### E3. be-distributed-id（分布式 ID / 雪花算法）
- 追问素材：**数据库内部视角的三层递进**——① 单机自增主键连"连续递增"都保证不了：计数器不与事务绑定，回滚即留空洞，回补就意味着表级锁（MySQL 选择性能放弃连续）；② 高并发下单机自增也撑不住，Oracle 的经典解法是 **Sequence 发高位 + 应用实例拼低位**——每取一次号可本地发 10 万个，但主键从此不再单调递增（号段模式的雏形，可反向印证现有题的 Leaf-segment）；③ 分布式下绝对单调递增的复杂度**等价于 TSO 全局时钟**（单点+高可用+性能上限），且 Range 分片下单调主键必然**尾部热点**（CRDB benchmark 案例，见 E2）——所以 CRDB 推荐 UUID、TiDB 4.0 出 AutoRandom（64 位 = 符号位 + 事务时间映射 + 自增序列，保唯一且随机化）。雪花算法时间回拨在本课程中再次出现，与全局时钟的时钟误差主题（S2/S3）同源——**ID 生成的时钟问题和事务定序的时钟问题是同一个物理限制的两个投影**，能把这句说出来就串起来了。

### E4. be-distributed-newsql（TiDB/OceanBase 架构概览）
- 追问素材（本题为架构概览，以下做机制深挖）：① **TiDB 分层 vs CRDB P2P 的实质差异**——TiDB 的 TiKV 自身不支持事务、靠 TiDB 层协调 Percolator；CRDB 无中心、只要坏节点不过半就能活。② **Multi Raft 与分片大小**：etcd 是单 Raft 组（写性能受限）所以两者都改 Multi Raft；分片大小 TiDB 默认 96M、CRDB 上限 512M——越小事务阻塞概率越低、越大扫描越高效。③ **存储引擎演进**（22 讲）：两者早期都用 RocksDB，后来 TiDB 出 **TiTan**（WiscKey 论文启发：value 出 LSM 单独存降写放大，前提是 SSD 随机读≈顺序读）、CRDB 出 **Pebble**（纯工程原因：CGo 每次调用 70ns × 高频 KV 调用 + RocksDB 代码从 30k 膨胀到 350k+ 的变更风险，Pebble 仅 45k 行）；OceanBase 自研 LSM 用**宏块/微块复用**（未变数据块级拷贝）+ **轮转合并**（Follower 先 compact、Leader 照常服务，用多副本解耦 compaction 与查询）。④ **HTAP 同步机制**：TiFlash 是 Raft **Learner**（不参与投票、不拖慢写），每次读前拿读时间戳向 Leader 查最新 Commit Index、等本地 apply 追平才服务——**用一次确认换准实时一致**，这与 Raft 题的 ReadIndex 是同一机制（见 E6）。⑤ **PGXC 的商业隐患**：MySQL GPL 协议对修改后闭源商业分发的约束，是 GoldenDB/TDSQL 类产品的长期法律风险点。⑥ 产品冷知识：Spanner 2017 年后自带 SQL 引擎（Ressi 行列混存、对标 HTAP），F1 转为独立查询引擎；OceanBase 有 Proxy 层所以常被质疑"是不是 PGXC"，但整体归 NewSQL。

### E5. be-distributed-tx（分布式事务方案全景：2PC/TCC/本地消息表/SAGA）
- 追问素材：现有题讲"应用层选型"，可下钻"数据库内部怎么改良 2PC"——三大问题与工程解法的对应表：**同步阻塞/高延迟** → 缓存写提交/管道/并行提交（L_txn 从 (W+1)L_c 压到 1L_c，见 S4）；**协调者单点** → 事务日志共识化（协调者无状态化）+ Paxos Commit（Gray & Lamport 2006，多数派投票裁决事务命运）；**第二阶段不一致** → Percolator 单点提交（只与主锁分片通讯）。另有语义级差异素材：TiDB 缓存写提交使冲突裁决从 **First Write Win 变 First Commit Win**（同 key 并发 update 的获胜方改变）——面试说得出这个差异，说明真理解"应用层事务框架与数据库内核事务"不是一回事。3PC 被弃用的理由可补：通讯开销更大且分区时仍不安全。

### E6. be-distributed-raft（Raft 选主与日志复制）
- 追问素材：**Raft 的性能缺陷与数据库级优化（高频深挖）**——① **顺序投票的代价**：日志不允许空洞，未过半的 T3 必须等明确失败信号，**无关的 T5 也被阻塞**；Follower 侧同理（缺 T2 日志时收到 T3 也不能 append）。这是设计取舍：换来"两节点比对一条日志即可确认之前全部一致"，Follower 一致性读因此容易实现。② **四项工程优化**（TiDB 文档口径，SOFA-JRaft 同款）：Batch（攒批发送）、Pipeline（不等返回连发，NextIndex 出错再回调）、**并行 Append**（Leader 本地落盘与发 Follower 并行，多数派 Follower 成功即可判 Committed）、**异步 Apply**（Apply 不是提交的必要条件，Committed 状态即不丢，读侧配合改造）。③ **Follower Read 的一致性版本**：利用日志无空洞，等本地 apply 追到查询时间戳对应的 Commit Index 再读（TiFlash Learner 同款，见 E4）——把"读走 Leader 不够"的现有追问推进到工程实现层。

### E7. be-distributed-quorum（Quorum W+R>N）
- 追问素材：**Quorum 在数据库部署形态里的落地差异**——现有题讲 Dynamo/Cassandra 的 N/W/R 参数，数据库视角是"**副本放置如何同时满足多数派与低延迟**"：两地三中心五副本里同城 4 副本 > 半数 → 写提交不必跨城（延迟免税）；异地 1 副本的价值是"同城损一机房时凑多数派选票"而非承担流量；三地五副本把"同城"换成相邻城市（10ms 内）才能城市级 RPO=0。这组数字（5 副本、4+1、同城过半）是 Quorum 知识最具体的应用题，也解释了"**低延迟与 RPO=0 在异地不可兼得**"的必然性。

### E8. be-distributed-brain-split（脑裂）
- 追问素材：**真实系统里对"少数派要不要继续服务"的两难**——两地三中心部署下若机房间链路全断（恶意挖缆场景），标准 Raft 结论是全体不可用；但有观点认为"主机房数据完整，凭什么停服"——由此出现 **Raft 降级机制**（允许配置少数派继续服务），这是对现有题"防脑裂三件套"的高级追问：防脑裂是默认正确，降级是显式权衡，**两者共存的前提是降级必须显式配置 + 依赖 fencing**，不能是故障时的自动行为（自动降级 = 静默脑裂）。另可补"远端写入时间戳异常"（S8）作为"非分区但类似脑裂的时间线混乱"案例。

### E9. be-distributed-config-registry（配置中心/注册中心）
- 追问素材：**PD 是什么性质的"注册中心"？**——TiDB 的 PD 与 TiKV 的交互模式：TiKV **主动心跳上报全量元数据，调度指令搭心跳返回的顺风车**（被动接收），PD 无状态化、宕机新主一个心跳周期即可工作。对比微服务注册中心：推送方向相反（注册中心推变更给消费方）、PD 同时承担 TSO 发号这种强一致职责——所以 PD 是"AP 心跳面 + CP 发号面"的混合体。CRDB 的 Gossip 元数据 + 寻址纠正回路（S1）则是"注册信息最终一致但请求不失败"的范例——这两个案例能把注册中心题从中间件层拔高到"元数据一致性设计"层。

### E10. be-mysql-sharding（分库分表）
- 追问素材：**从分库分表到分布式数据库的连续谱（本题现有内容止步于"换 TiDB 的路线对比"，可展开）**——四级演进：客户端组件（Sharding-JDBC，侵入应用）→ 代理中间件（MyCat/DBLE，独立进程 + 分布式事务组件雏形）→ **PGXC**（代理升级为协调节点 + 新增分片信息管理与全局时钟/GTM 两个角色，GoldenDB 分列两个节点、TBase 合并为一类）→ **NewSQL**（分片从"相对固定"变为"可自由移动"——数据与节点解绑是两种架构的根本分野，存储引擎差异只是表象）。分片信息管理独立出来的原因（元数据多副本一致性问题）直接引出 S1。现有题的"翻倍扩容 + 双写迁移"是应用层为静态分片付的税；动态 Range 把它内化成自动分裂/合并——这个对照能同时答"什么时候还该用分库分表"（业务模型简单统一、无复杂分布式事务诉求，光大火大云缴费案例：5.49 亿用户系统用自研分库分表）。

### E11.（相邻领域）cs-db-lsm（LSM 树）——来自 22 讲 RUM 猜想
- 追问素材：**给现有 LSM 题补理论骨架与量化数字**——① **RUM 猜想**（SIGMOD/EDBT 2016）：Read/Update/Storage 三个开销**最多同时优化两个**，B+Tree 与 LSM 只是选了不同的角；② **量化对比**：B+Tree 插入一条记录牵动 3 页 7 条索引记录（WAF=7），随机写致存储碎片化（逻辑连续物理不连续），填充因子是两难参数；**Tiered 合并 SAF=2**（新旧两份并存）vs B+Tree 1.33，读放大 O(M·logN)、compact 后 O(log(M·N))——"LSM 写放大比 B+Tree 还严重（Tiered 时）"是反直觉点；Leveled 每层 10 倍容量、配布隆过滤器后读复杂度 O(X+L-1+logN)；③ **WiscKey**（FAST 2016）：compact 的本质是整理 key，value 重写纯属浪费 → value 分离存储，前提是 SSD；TiDB TiTan 的理论来源；④ Pebble/TiTan/OB 宏块微块/轮转合并/TiFlash Delta Tree（Delta Layer≈L0、Stable Layer≈L1，列存也要 LSM 化保写入）——见 E4。现有题的"三放大"框架可以无痛吸收这些数字。

### E12.（相邻领域）bd-mr-shuffle（MapReduce）——来自 6.824 LEC01
- 追问素材：少量可补的课堂细节——① **straggler 处理**：coordinator 对最后几个慢任务**再起一个副本对赌**（speculative execution 的原始出处场景）；② **重复任务的正确性**：Map/Reduce 必须**纯确定性函数**（只准读入参），否则任务重跑时不同 Reduce 可能读到两次运行的混合输出——重执行容错的前提是确定性；③ **Reduce 输出防重复写**：两个重复 Reduce 同写一个输出文件，靠 **GFS 原子 rename** 保证只暴露一个完整文件——"文件系统原子操作兜底协议重复"的通用手法；④ 2004 年论文瓶颈在网络根交换机（shuffle 半数流量过根，55Mb/s/机）——"先算清楚哪个资源是瓶颈再优化"的方法论案例。现有题已覆盖 shuffle 落盘/本地磁盘设计，以上四点均为增量。
