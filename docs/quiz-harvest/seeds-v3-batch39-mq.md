### S1. 主题和队列有什么区别？队列模型和发布-订阅模型怎么演化到今天的消费组模型？
- 来源：课程 A《03 消息模型：主题和队列有什么区别？》《08 答疑解惑（一）§2 详解 RocketMQ 和 Kafka 的消息模型》
- 核心素材：
  - 队列模型：FIFO、出队即删除，多消费者竞争一条消息只被一个消费；一份消息要给多个系统（风控/分析/支付）就得为每个消费者建队列由生产者发多份——浪费且让生产者感知消费者，违背解耦初衷。
  - 发布-订阅模型：容器变为主题（Topic），「订阅」是主题在消费时的逻辑副本，每份订阅都能收到全量消息；单订阅者时与队列模型等价，两者无本质区别（RabbitMQ 靠 Exchange 路由到多队列变相实现发布订阅）。
  - RocketMQ/Kafka 在主题下引入队列（Kafka 叫分区）：因为「请求-确认」机制下，一个队列只能串行确认，无法水平扩展消费——多队列实现多实例并行生产消费；只在队列级保证顺序。
  - 消费组 = 一份订阅：组内消费者竞争（每队列同一时刻至多被组内一个消费者占用），组间互不影响互不感知、消费进度独立；积压只影响自己组。
  - 消费位移按「消费组 × 队列」在服务端维护，是一组整数——**与消费者实例无关**（消费者宕机换人位移不丢），丢消息多半是位移处理不当。
- 建议追问：
  - 原理：为什么队列里的消息「消费」后不删除？（多消费组各要一份全量，删除时机只能靠过期；位移之前=已消费）
  - 边界：为什么队列内的串行确认导致无法并行消费？出现「消息空洞」怎么办？（A08：空洞消息复制进重试队列、位移越过空洞前移——见 S8）
  - 权衡：RabbitMQ 坚持队列模型换来什么、失去什么？（路由灵活 vs 多订阅要复制多份存储）
- 建议难度：basic

### S2. Kafka 和 RocketMQ 的存储结构有什么本质差异？分区存储 + 稀疏索引 vs Broker 级 CommitLog + 稠密索引
- 来源：课程 A《35 答疑解惑（三）：主流消息队列都是如何存储消息的？》、课程 B《14 性能之道》
- 核心素材：
  - 共同底座：现代 MQ 本质是分布式存储系统，每个分区是一段 WAL（只尾部追加、按索引定位后顺序读）。
  - Kafka 以分区为存储单位：每分区一组 segment 消息文件 + 一一对应的索引文件（文件名=首条消息序号）；**稀疏索引**（隔几条建一条），查找=文件名定位→二分找最近索引→顺序遍历；省存储、查稍慢。
  - RocketMQ 以 Broker 为存储单位：所有主题的消息混写进同一组 CommitLog；每队列一组 ConsumeQueue **定长稠密索引**（每条 20 字节），按序号×20 直接算出索引位置，两次绝对位置寻址；查更快、写时多主题合成一批更顺。
  - 粒度权衡：分区粒度细→数据迁移/扩容灵活；Broker 粒度粗→上千活动主题时仍是纯顺序写，写入性能占优（Kafka 分区多时 IO 零散退化为准随机写，性能随分区数先升后降）。
  - 实践数据点（丁威）：SSD 同配置下 Kafka 吞吐常优于 RocketMQ（单文件顺序写难压满磁盘）；但 Kafka 扩容要分区重分配（数据搬家），RocketMQ 扩容只影响新数据，运维成本低。
  - 小消息海量条数的场景，Kafka 稀疏索引节省大量索引存储。
- 建议追问：
  - 原理：稀疏索引如何定位一条消息？为什么查找后可以「顺序读一大段」？
  - 边界：什么时候 RocketMQ 的 CommitLog 设计明显占优？（单 Broker 千级主题）；什么时候 Kafka 占优？（少分区大吞吐、需要迁移弹性）
  - 权衡：让你自研 MQ 存储引擎，主题数会动态涨到几万，选哪种布局，为什么？
- 建议难度：advanced
- 注：Kafka 存储细节部分与 Kafka 专项批次撞车，交整合者裁决（本题主轴是「两种存储布局的对比与取舍」，建议留在 MQ）。

### S3. 消息队列的副本复制与选主怎么做？RocketMQ 主从/Dledger 与 Kafka ISR 的取舍
- 来源：课程 A《22 Kafka和RocketMQ的消息复制实现的差异点在哪？》《28 答疑解惑（二）§2》
- 核心素材：
  - 复制的天然矛盾：写副本数越多→可靠性/一致性越好、写入性能越差；复制只增加写开销，消费读单副本无差别。没有方案能同时最优（性能、可用性、一致性三角）。
  - RocketMQ 传统主从：主从关系配置固定、不支持动态切换；异步复制/同步双写两档。异步复制在主宕机时也不丢消息——未复制的数据还躺在主磁盘上，主恢复后继续补复制，只是期间不能写（**牺牲可用性换一致性和性能**）；顺序场景主挂了从不能顶（顶了乱序），顺序与高可用二选一。
  - Dledger（RocketMQ 4.5+）：至少复制到**半数以上**节点才返回成功 + Raft 投票选举动态切主；选举时会把数据最新的从节点选为主，保证不丢且严格顺序；代价：选举期间不可服务、最少 3 节点只容忍 1 台宕机、性能低于主从异步。
  - Kafka：复制单位是分区，副本散在不同 Broker（Leader 读写、Follower 只同步，Leader 尽量均衡）；ISR 数量可配、含主节点，等「足够多」副本写入才确认——把取舍权交给用户（灵活性高、学习成本高）；ISR 全挂默认拒绝服务，也可配 unclean 选举换可用性丢一致性。
  - 两种选举哲学：Kafka 分区 Leader 由 Controller「指定」（Controller 本身靠 ZooKeeper `/controller` 临时节点**抢占**产生——抢玉玺模式，简单快速，任何一致性存储皆可充当）；Dledger 靠 Raft **投票**自选举（无外部依赖，但算法复杂、多轮投票慢、几秒到几十秒不可用）。
- 建议追问：
  - 原理：为什么一致性必须主从复制、且任一时刻主不超过 1？
  - 边界：「一主二从、写入 2 副本算成功」能容忍几台宕机？（1 台；缩到 1 则可用性最好但主挂未复制即丢）
  - 权衡：什么业务该选 Dledger、什么业务用主从异步就够？（资金/顺序类 vs 可重推日志类）
- 建议难度：advanced
- 注：ISR/Controller 细节与 Kafka 专项批次撞车，交整合者裁决。

### S4. RocketMQ 的 NameServer 为什么不用 ZooKeeper？两种协调/寻址服务怎么选
- 来源：课程 A《23 RocketMQ客户端如何在集群中找到正确的节点？》《24 Kafka的协调服务ZooKeeper》
- 核心素材：
  - NameServer 设计：独立小进程（核心只有 RouteInfoManager 一个类 + 5 个内存 Map），**节点间零通信、互不感知**，每节点独立提供完整服务；路由信息只存内存、不持久化。
  - 一致性来源：Broker 向**所有** NameServer 主动注册 + 定时全量上报（上报兼做心跳），靠「数据源单点 + 全量覆盖」收敛，而非分布式共识；心跳超时即摘除 Broker，客户端通信失败后重新拉路由自动切换。
  - 客户端：定时（30s 级）拉路由缓存本地；长连接由客户端侧心跳维持。本质是「最终一致 + 客户端容忍短暂脏路由」。
  - ZooKeeper 路线：一致性存储 + 临时节点（会话断开自动删除，天然的存活检测）+ Watcher 推送；Kafka 把 Broker 列表和主题分区两棵树存 ZK，每个 Broker 缓存全量元数据，客户端**不直连 ZK**，向任意 Broker 发 MetadataRequest 取路由。
  - ZK 的两个告诫：不要存大量数据（几百 MB 后性能稳定性骤降，它不是存储系统）；不要让业务可用性绑死在 ZK 上（选举慢、对网络抖动敏感）。Kafka 集群因此建议拆小、每组独立 ZK；后续 KIP-500 自研元数据 Quorum 替代。
  - 选型本质：元数据量小、变更不频繁、能容忍秒级不一致→NameServer 这种无共识镜像复制极简且无单点；需要强一致协调（选主、分布式锁、临时节点语义）→才需要 ZK 这类共识服务，付出运维与可用性代价。
- 建议追问：
  - 原理：NameServer 各节点数据不一致（Broker 只向部分节点注册成功）会怎样？客户端如何自愈？
  - 边界：为什么 Kafka 客户端不直接连 ZooKeeper？（客户端数量大、ZK 连接与写入撑不住；Broker 中转 + 本地缓存削峰）
  - 权衡：与注册中心通用设计的关联（be-distributed-config-registry 的推送 vs 轮询在这里如何体现——NameServer 是拉，ZK+Watcher 是推）
- 建议难度：intermediate
- 注：与 be-distributed-config-registry 相邻，差异化点在于本题聚焦「MQ 元数据的量级与一致性要求」这一具体选型场景。

### S5. 消息队列的 Push 和 Pull 消费模型各有什么优劣？长轮询是怎么实现「伪 Push」的？
- 来源：课程 A《21 Kafka Consumer源码分析》、课程 B《16 案例§第二阶段》《19 案例§消费模型》
- 核心素材：
  - Pull 的本质（Kafka/Consumer#poll）：客户端主动拉，速率自主、天然背压（消费不动就少拉），服务端无 per-consumer 状态堆积；缺点是延迟（轮询间隔）与空轮询浪费。
  - Push 的两难：服务端推可以低延迟，但速率失控会打垮慢消费者（背压难做），还要维护每消费者的推送状态。
  - RocketMQ 的答案是「Pull 实现的 Push」：PullMessageService 线程拉完一批就把 PullRequest 塞回队列尾部**循环再拉**，消费方代码完全无感，表现如 Push；拉不到时不是立刻重试（空转），而是**长轮询**——请求在 Broker 挂起 hold 住，该队列一旦有新消息立即唤醒返回，超时才返回空，兼顾低延迟与不空转。
  - 消费端两组件：ProcessQueue（每队列一个，TreeMap 存已拉未确认消息，最小 offset 用于提交位移）+ 消费线程池；拉取与消费解耦，位移按 ProcessQueue 最小位点提交（保证不跳过未完成消息）。
  - Kafka Consumer 的补充设计：poll() 驱动一切——订阅、入组（Coordinator）、拉取、位移提交都在 poll 心跳里完成；完全异步网络客户端（请求暂存 unsent、响应暂存 completedFetches，poll 时择机批量收发），省线程但复杂度高（李玥：不推荐业务代码这么写，可维护性优先）。
  - rebalance：消费组内每个分区同一时刻只归一个消费者；消费者靠心跳保活，增减实例/分区触发重新分配（顺序消费还涉及 Broker 端锁移交，见 S8）。
- 建议追问：
  - 原理：长轮询和「客户端定时轮询」「服务端纯推」三者，延迟与开销怎么排？
  - 边界：Push 模型下消费端处理不过来，服务端如何知道该减速？（RocketMQ 客户端本地限流三条件：缓存 1000 条 / 最大最小 offset 跨度 2000 / 100MB，触发即暂停拉取）
  - 权衡：为什么 Kafka 干脆不做服务端 Push？（吞吐优先、消费速率自治；Kafka 撞车 Kafka 专项批次裁决）
- 建议难度：intermediate

### S6. 只用消息队列怎么做「请求-应答」？以秒杀为例：网关发出异步消息后如何拿到结果同步返回
- 来源：课程 A《08 答疑解惑（一）§1 网关如何接收服务端的秒杀结果？》《01 为什么需要消息队列（秒杀案例）》
- 核心素材：
  - 场景：网关把秒杀请求发进 MQ 就返回会让用户端无法拿到「成功/失败」；需要 MQ 异步链路上叠一层同步等待。
  - 方案骨架：网关为每个请求生成全局唯一请求 ID，消息里携带「请求 ID + 网关实例 ID」；发送后在本实例的 results Map 登记等待项，用 mutex.wait(timeout) 阻塞限时等待。
  - 结果回传：后端秒杀服务完成后以网关 ID 找到原网关实例（RPC 回调），携带请求 ID；网关 onResult 把结果放进 results Map 并 mutex.notify() 唤醒等待线程，取出结果返回 APP；超时未回则按失败处理，迟到结果因等待项已清理而直接丢弃。
  - 关键细节：等待必须带超时；Map 的清理放 finally 防泄漏；「按网关实例路由结果」依赖消息中带网关 ID（有状态回传路径）；多实例网关各自只等自己的请求。
  - 权衡：这是「半同步」方案，处理线程被占住；更彻底的做法是全异步化（CompletableFuture/Servlet 异步上下文），或客户端轮询结果接口。秒杀本身先做风控+库存扣减两步同步、其余（订单/短信/统计）全部异步进 MQ。
- 建议追问：
  - 原理：这套机制和 RPC 框架「单连接多请求 requestId+Future」是同构的（呼应 B18，见 S7），说出对应关系。
  - 边界：网关在 wait 期间宕机，用户侧和后端侧各发生什么？如何兜底（幂等 + 结果可查询）？
  - 权衡：什么时候该放弃同步返回、改成「受理成功 + 结果推送/轮询」？（超时预算 vs 用户体验）
- 建议难度：intermediate

### S7. 线上案例：RocketMQ 消息发送偶发超时（万分之一），完整的排查与兜底思路是什么？
- 来源：课程 B《18 案例：如何排查RocketMQ消息发送超时故障？》
- 核心素材：
  - 日志入手：`invokeSync: wait response timeout`（等响应超时）+ `receive response, but not matched any request`（超时后响应才到达、已找不到对应请求）——说明网络通、响应慢，矛头指向 Broker 或传输链路。
  - 背景原理：单一长连接并发多请求靠 requestId + Future Map：发送前注册 Future，响应带原 requestId 唤醒；超时后 Future 已被移除，迟到响应即 "not matched"。
  - 排除法链路：① 查 store.log 的 PAGECACHERT 指标——写 PageCache 耗时 <100ms，排除磁盘/缓存写入瓶颈；② netstat 看 **Recv-Q/Send-Q**（接收/发送缓冲区积压）——客户端 Recv-Q 大量积压=服务端写网络慢或客户端读慢；③ 改客户端加 Netty 读事件统计，一次读事件大多 2 次读就抽干，排除客户端读瓶颈；④ 剩下唯一没监控的环节=服务端写网络。
  - 定位与解法：读源码发现 RocketMQ 网络参数偏小——`serverSelectorThreads`（Netty IO/Selector 线程，默认 3）与 `serverWorkerThreads`（编解码工作线程，默认 8）；48 核机器上调到 16/32 后，超时率降到十万分之一。
  - 兜底策略（无法做到 0 超时）：Broker `maxWaitTimeMillsInQueue=1000` 增加快速失败等待；客户端**减小单次超时（如 500ms）+ 增加重试次数**——局域网抖动是瞬时的，快速失败快速重试（RocketMQ 重试自带故障规避，换 Broker 发），4.3+ 客户端超时是所有重试的总预算，需自行包装循环重试。
- 建议追问：
  - 原理：为什么「减小超时 + 加重试」反而降低整体失败率？（抖动瞬时性 + 故障规避；总耗时预算可控）
  - 边界：Recv-Q 积压在客户端侧和服务端侧分别说明什么？（对端不读 / 本端写不动）
  - 权衡：这类「参数默认值不适配大机器」的坑，如何在新集群上线前避免？（容量压测 + 关键参数 review，可关联 be-stability-capacity）
- 建议难度：advanced
- 注：与 be-stability-rt-triage（通用慢排查）相邻，本题差异化在 MQ 网络链路的专用指标与参数。

### S8. 顺序消费为什么吞吐上不去？RocketMQ 的三把锁，以及基于「关联顺序性」的并发度优化
- 来源：课程 B《16 案例：如何提升RocketMQ顺序消费性能？》、课程 A《08 答疑解惑（一）§3/§4》
- 核心素材：
  - 真实案例：订单状态机用顺序消费，64 个队列积压上千万条，消费者扩到 64 台后**无计可施只能等**——顺序消费积压几乎没有补救手段。
  - 实现原理三阶段：① 队列负载（rebalance 20s 一轮）：新分配的队列必须先向 **Broker 申请队列锁**成功才能拉取；丢弃旧队列前要拿到 ProcessQueue 锁否则不放手（防两边同时消费）。② 拉取：拉到即放 ProcessQueue（TreeMap）并提交消费线程池，PullRequest 循环实现 Push。③ 消费：申请 MessageQueue 锁→按 offset 从小到大取一批→申请 ProcessQueue 锁→才调业务监听器。
  - 代价：三把锁让**并发度被队列数上限锁死**，单消费者加线程无效。
  - 优化洞察「关联顺序性」：银行余额变更短信场景——同一账户的变更必须有序，**不同账户之间无需有序**；RocketMQ 内置模型做不到（整队列串行）。
  - 改进模型：拉取后按 **消息 Key 的 hash 对线程数取模**投递到 N 个任务队列，每个队列绑定单线程串行消费——同 Key 串行、异 Key 并行；并发度只随线程数涨，与队列数无关；位点提交取处理队列最小 offset。落地：基于 DefaultLitePullConsumer 自建线程模型（丁威开源代码）。
  - 单队列并行消费的另一解法（JMQ，A08）：位置 5 未响应而 6/7 已完成→把 5 复制进重试队列、位移直接推进到 8，后续优先消费重试队列——「位移跳跃 + 空洞入重试」；开销大，不作为常规手段（要并发优先扩队列）。
- 建议追问：
  - 原理：三把锁各自防住什么竞态？（Broker 锁防 rebalance 后双消费；ProcessQueue 锁防丢弃队列时消息还在消费；消费锁保证单线程）
  - 边界：Key hash 到线程的方案，失败重试如何不破坏顺序？（同 Key 重试仍路由到同一线程队尾；跨线程时退化为至少一次+幂等）
  - 权衡：业务上能识别「关联顺序性」时，为什么优于盲目加队列？（队列数受分区规划约束、全局重排代价大）
- 建议难度：advanced

### S9. Pulsar 的存储计算分离架构是什么？Broker 无状态化解决什么、又付出什么
- 来源：课程 A《27 Pulsar的存储计算分离设计》《28 答疑解惑（二）§3》
- 核心素材：
  - 传统 MQ 的 Broker 是**有状态节点**：各自存不同数据，故障后只有「持有相同数据的副本」能接替，故障转移需要选举+同步，慢且复杂。
  - Pulsar：Broker 不存元数据（ZooKeeper 管）也不存消息（BookKeeper 集群管），变成纯无状态计算节点；分区与 Broker 的归属是**动态**的，LoadBalancer 按负载随时调整，任一 Broker 可替代故障节点，故障转移秒级。
  - BookKeeper 的存储单元 Ledger≈一段 WAL（连续若干 Entry）；**一次性写入（单写者）设计**：Ledger 只允许创建它的 Broker 写，关闭（含宕机）后永久只读，续写新建 Ledger——用「不共享资源」替代「分布式锁」，巧妙回避了分布式写锁的性能与复杂度。
  - 优点：无状态节点集群调度/扩缩/转移极简；开发分工清晰（存储层只专注「安全高效存数据」）。
  - 代价（「背着抱着一样沉」）：问题没消失只是转移到 BookKeeper（一致性、复制、选举照样要做）；一个集群变两个集群，总体复杂度上升；消费读要多一跳网络（Broker→BookKeeper）+ 多次内存拷贝，性能有损。
  - 为什么大多数 MQ 不这么做：现代 MQ 本质已是分布式存储系统，把存储职责剥离后计算节点就「没东西可算」；且消息存储性能要求高，套现成存储系统达不到。
  - 为什么说它是方向：MQ（能存不能算）与流计算平台（能算不能存，Storm/Flink/Spark 节点无状态）互补，Kafka 在做 Streams、Pulsar 在做 Functions，都指向「存算一体 + 计算」的新形态，届时存算分离恰好匹配。
- 建议追问：
  - 原理：Ledger 单写者设计如何等价于「免锁」？类比单线程写 WAL。
  - 边界：Broker 宕机时它正在写的 Ledger 怎么办？（立即关闭、数据已在 BookKeeper 副本中，新 Broker 新开 Ledger 接管分区）
  - 权衡：什么业务场景值得引入 Pulsar？（海量 topic/多租户、频繁扩缩、跨地域复制 geo-replication；吞吐极致型仍选 Kafka）
- 建议难度：advanced

### S10. 发布期间的消息怎么隔离？在 MQ 链路上实现蓝绿/灰度的两种机制
- 来源：课程 B《15 案例：消息中间件如何实现蓝绿？》《12 案例：如何实现蓝绿发布（相邻）》
- 核心素材：
  - 本质：蓝绿发布在 MQ 层 = 消息分类隔离——蓝消息只被蓝消费者消费；只有微服务层蓝绿不够，消息链路（上游生产→MQ→下游消费）必须整体隔离，否则灰度验证失真。
  - 方案一「基于消息属性」（逻辑隔离）：同一主题，消息带 color 属性；消费端按环境改写消费组名（`_BLUE_dw_test_consumer_group`）实现组级隔离，消费前解码属性，颜色不匹配直接返回「消费成功」跳过。
  - 方案一的坑：① 不带颜色的消息（未接入蓝绿的上游发的）会被两个环境都跳过→**丢消息**；必须额外约定「无色消息归属」，归属组随蓝绿状态动态切换（切换=关一个默认组、在另一环境开同名组）。② 每个消费组都全量拉取再过滤——开启蓝绿后读流量放大近 3 倍，压服务端。
  - 方案二「基于主题」（物理隔离）：发送端拦截器按系统参数改写 topic 名（`_BLUE_topicA`），消息从物理上分主题存储；消费组只订阅本环境主题，拉取全是有效流量，无放大。
  - 方案二的边界：要防拦截器嵌套改写（发送链路里 topic 名被改两次）；主题数量翻倍、运维面变大；适合主题数可控的大链路蓝绿，属性方案适合轻量灰度/全链路压测的影子流量。
  - 通用沉淀：MQ 侧流量染色 = 生产端拦截器注入标 + 消费端按标过滤/路由 + 元数据（消费组命名）承载环境语义，与全链路压测的影子 topic 思路同构（关联 be-stability-capacity）。
- 建议追问：
  - 原理：为什么「消费成功但跳过」在属性方案里不等于消息被消费？位移照常推进的后果是什么？（未归属环境的消息被跳过且不可重放→必须靠归属约定兜底）
  - 边界：蓝绿回切（BLUE→所有）怎么做才不丢消息？（先把无色归属组恢复、再摘颜色组，过渡期双组并存）
  - 权衡：属性过滤 vs 主题隔离，读放大 vs 管理成本，怎么选？
- 建议难度：intermediate

### S11.（可选，中低频）MQTT 为什么能支撑海量 IoT 设备在线？接入层怎么设计？
- 来源：课程 A《26 MQTT协议：如何支持海量的在线IoT设备？》
- 核心素材：
  - 场景特点倒逼协议设计：终端便宜（KB 级内存、可能无 OS）→报文极简、功能只留发布订阅；无线弱网常态→心跳探活 + **服务端会话**（重连恢复现场，复杂度转移到服务端）；不支持点对点→客户端订阅以自己 ID 命名的专属主题，**主题数≈客户端数**，百万千万级。
  - 传统 MQ 直接支持 MQTT 的瓶颈：RocketMQ 元数据在 NameServer 内存、Kafka 在 ZK，都撑不了海量主题/连接；开源 MQTT Server 集群能力普遍弱或收费。
  - 自建集群架构：域名/LB → **Proxy 集群**（承接海量连接、维护会话、代转发）→ 多组 Broker 小集群（按主题分片，Proxy 用一致性哈希路由到小集群）。Proxy 把百万客户端连接收敛为「Proxy 与 Broker 各一条连接」，Broker 连接数 ≤ Proxy 节点数。
  - 会话两种放法：Proxy 本地（要求 LB sticky session）vs 外置存储（Redis/MySQL，Proxy 无状态、对 LB 无要求，但要求外置存储千万级性能）。
  - 选型经验：接入 <10 万级可用开源方案；之上基本只能云服务/商业版或自建。
- 建议追问：
  - 原理：为什么「连接收敛 + 会话外置」是海量长连接的通用解？（连接数≈内存/句柄成本，会话状态决定能否无状态扩容）
  - 边界：Proxy 本地会话 + sticky session 的故障面在哪？（Proxy 挂→其上会话全失效重连）
  - 权衡：什么场景直接用云 MQTT 服务比自建划算？
- 建议难度：intermediate（偏架构题；若嫌 niche 可弃，其中「海量长连接接入层」素材可转介 be-network）

### E1. 目标题目：be-mq-why-and-choose（为什么要用消息队列？怎么选？）
- 来源：课程 A《01/02》、课程 B《13 技术选型》《02 中间件生态选型》、课程 A 期中测试解析
- 追问素材：
  - 「哪些问题不适合用 MQ 解决？」——分布式锁、任务调度不是 MQ 所长；期中题解析：MQ 三大场景=异步处理、流量削峰、服务解耦。
  - 选型判据（李玥版，比现有答案更可背）：① 必须开源（出 Bug 能自己改源码救火）；② 近年流行、社区活跃（坑别人踩过、生态兼容如 Flink-Kafka）；③ 及格线三特性=可靠传递、Cluster、性能。
  - RabbitMQ 补充短板：堆积设计理念是「管道」，大量积压性能急剧下降（对照 Kafka/RocketMQ 的存储型设计）；Erlang 学习曲线极陡（“编程语言中的汉语”），二次开发维护性差；Exchange 灵活路由是独有优势。
  - 「送积分/优惠券」反例的表述（丁威）：不用 MQ 时需求变更要改主流程并发版；引入 MQ 后「对新增开放、对修改关闭」——把开闭原则落到架构层。
  - 边界辨析：流水与余额严格一致**不适合**事务消息——先在库事务里记流水、再异步更新余额，不一致时用流水校正余额（余额无法反推流水）。

### E2. 目标题目：be-mq-no-loss（如何保证消息不丢失？）
- 来源：课程 A《05 如何确保消息不会丢失？》《20 Producer源码分析》《22 消息复制》《06 QoS 部分》
- 追问素材：
  - 「怎么证明没丢？」——利用有序性做**序号连续性检测**：Producer 端拦截器给每条消息注入分区级递增序号（多 Producer 各自编号带 Producer 标识），Consumer 端拦截器校验连续性，断号即丢并可定位到具体消息；检测代码零侵入、稳定后可下线。
  - 三阶段框架已有，补充「请求-确认」机制的准确定义：服务端收到写入才回确认，超时/失败生产端重试；消费端先业务后确认，Broker 未收到确认会重发同一条（这同时是重复消息的来源，衔接 be-mq-idempotent）。
  - 异步发送的正确姿势（源码级）：RocketMQ 同步/异步/单向统一走同一底层流程，异步只是丢给 asyncSenderExecutor 线程池，**回调里必须检查 SendResult/异常**——很多丢消息就是异步发送不检查回调。
  - 集群档位对应的代码事实：RocketMQ `flushDiskType=SYNC_FLUSH`（同步刷盘）；同步双写=写 2 副本才确认；Kafka acks 组合现有答案已有，可补「业务允许重推的数据可用 acks=1 换性能（如 Binlog 同步到 ES 的任务支持回溯）」。

### E3. 目标题目：be-mq-idempotent（消费端幂等的正确实现）
- 来源：课程 A《06 如何处理消费过程中的重复消息？》《28 答疑解惑（二）§1》、期中测试解析 7
- 追问素材：
  - 理论锚点：`At least once + 幂等消费 = Exactly once`（从「对系统的影响」角度成立）；主流 MQ 全部只承诺 At least once。
  - 幂等三法（李玥版阶梯，与现有答案互补）：① 数据库唯一约束（转账单 ID+账户 ID 联合唯一，重复 insert 失败）；② **前置条件更新**（“余额为 500 时才 +100”/版本号 CAS）；③ 记录并检查（Token/全局 ID）。
  - 方法③的并发陷阱（可作为高阶追问）：「查状态→更新数据→置状态」三步必须**原子**，否则两个消费者同时查到“未处理”→双花；必须同事务或加锁——这正是现有答案「去重和业务同库同事务」的原理级解释。
  - ABA 边界：前置条件用「余额判等」有 ABA 问题（100→200→100 后旧消息仍通过校验重复扣款）——版本号单调递增才是安全前置条件。

### E4. 目标题目：be-mq-order（如何保证顺序消费？）
- 来源：课程 A《08 答疑解惑（一）§3/§4》、课程 B《16》前三阶段、期中测试解析 3
- 追问素材：
  - 发送端选队列的算法选型追问：「相同 Key 同队列 + 支持分区水平扩容」→ **一致性哈希**；简单取模能满足前者但扩容时 Key→队列映射大面积漂移、顺序破坏。
  - 全局严格顺序的代价定量表述：队列数=1、生产者/消费者都单实例——完全放弃并行，仅审计流水类极端场景可用。
  - 顺序与高可用互斥的原理补充：顺序消息必须指定队列→队列固定在特定主从组→主挂后其他主无法接管（接管即乱序），传统主从下「顺序 vs 高可用二选一」，Dledger 可兼得（选数据最新的为主）。
  - 顺序消费失败的保序重试：RocketMQ 顺序消费是**本地阻塞重试**（ suspense 队列，不跳过、不进重试 topic），重试风暴会放大积压——与现有答案「本地阻塞重试保序」呼应，可补「积压场景下顺序消费几乎无解」的实战结论（见 E5 案例）。

### E5. 目标题目：be-mq-backlog（消息大量堆积怎么办？）
- 来源：课程 A《07 消息积压了该如何处理？》、课程 B《19 排查消费积压》《17 运维亿级集群》《16》案例
- 追问素材：
  - 「先定位」的具体指标（RocketMQ 控制台）：**Delay = BrokerOffset − ConsumerOffset**（积压条数）；**LastConsumeTime**（最后成功消费消息的存储时间，若为 1970 说明消费位点对应消息已过期被删）。
  - 快速判因口诀（李玥）：只有两种粗因——发送变快 or 消费变慢；监控显示收发速率都没变却积压→查「一条消息反复消费失败」；jstack 连打 5 份对比同一 ConsumeMessageThread_ 状态，**RUNNABLE 也要看**（HTTP 无超时、等 DB 时线程就是 RUNNABLE，不是 BLOCKED）。
  - 反模式警示（现有答案未覆盖）：「OnMessage 收到消息丢内存队列就 ack，另起线程池慢慢处理」是常见错误——宕机丢内存里的消息；正确方向是扩队列 + 扩实例，且 **Consumer 实例数 ≤ 分区数**（超过即空转）。
  - 客户端限流证据：日志出现 `so do flow control` 说明消费端自身瓶颈（三触发条件：缓存 1000 条 / offset 跨度 2000 / 缓存 100MB）。
  - 最小位点提交机制的连带效应：一条消息卡住（如 HTTP 不超时）→同队列位点永不推进→整队列积压；修法常是给消费逻辑内所有外部调用加超时。
  - 顺序消费积压的无奈（丁威真实案例）：64 队列扩 64 消费者后无计可施只能等——顺序 topic 的容量规划要按峰值留足队列。
  - 运维级兜底：位点回溯重放——RocketMQ `resetOffsetByTime` 可不停消费组；Kafka 必须先停组再 reset（RocketMQ 如何做到：位点在 Broker 侧，客户端定期拉取位点自然生效）。分区扩容对比：RocketMQ 读写队列分离、缩容先收写等过期；Kafka 只能扩不能缩、扩容走 reassignment。

### E6. 目标题目：be-mq-delay-tx（延迟消息和事务消息的实现原理）
- 来源：课程 A《04/25》、课程 B《18》（半消息代码级细节）
- 追问素材：
  - 半消息的**存储级实现**（比现有答案深一层）：Broker 收到带 `PROPERTY_TRANSACTION_PREPARED=true` 的消息→把原 topic/queueId 存进 `REAL_TOPIC/REAL_QUEUE_ID` 属性→消息实际写入内部主题 `RMQ_SYS_TRANS_HALF_TOPIC`（queue 0，对消费者不可见）；commit 时复制回真实 topic，rollback 时仅标记已处理。
  - 回查机制细节：`TransactionalMessageCheckService` 定时扫描半消息→对每条发反查 RPC；生产者实现 `checkLocalTransaction` 按 orderId 查库——**存在即 COMMIT，不存在返回 UNKNOW**（可能失败也可能还在执行），UNKNOW 下次继续查；反查不依赖发送节点本地内存（查的是 DB），节点宕机其他实例可代答；producer 的 commit/rollback 本身是 oneway RPC，丢了靠回查兜底——「每个环节都可能失败，靠状态可查 + 重试收敛」。
  - 对比 Kafka 事务（实现哲学差异）：Kafka 引入**事务协调器**（Broker 内角色，多实例并行、靠事务日志主题 `__transaction_state` 持久化状态）；消息**直接写业务分区**，不做暂存，由消费者端配合「控制消息」过滤未提交批次；两阶段：prepare→所有分区写 control batch→提交。Kafka 无事务反查，提交失败业务自行补偿。
  - 「两种事务解决的问题不同」可作追问：RocketMQ 事务=本地事务与发消息的原子性；Kafka 事务+EOS=**流计算 read-process-write 链路**内（源和汇都在 Kafka）恰好一次，不是通用的传输层 EOS——与 be-mq-idempotent 的「跨系统无传输层 EOS」互相印证。
  - 撞车标注：Kafka 事务/EOS 部分与 Kafka 专项批次撞车，交整合者裁决。

### E7. 目标题目：be-mq-kafka-throughput（Kafka 为什么吞吐高？）
- 来源：课程 A《15/16/19》、课程 B《14》
- 追问素材：
  - 批消息全链路不拆包（比现有「批量」更具体）：Producer API 只有单条 send，客户端攒批；Broker 写盘/复制/读全程把一批当**一条批消息**处理，消费端才拆包——构建与解包都在客户端，Broker 每批只处理 1 次请求。李玥压测参考值：单节点接近 2000 万条/s、600MB/s。
  - 压缩即批（A19）：Kafka 压缩以批为单位，**服务端不解压整批存储转发**，解压在消费端——省服务端 CPU 又享受带宽/存储收益；压缩分段（批大小）要在压缩率与解压浪费间权衡；算法选择：要速度选 LZ4/Snappy，要压缩比选 GZIP/XZ。
  - 客户端组装消息格式（B14）：Kafka 在**客户端**按存储协议组织数据，Broker 直接落盘不重排——省 Broker CPU（类比 ShardingJDBC vs MyCat 的算子下推）；linger.ms 攒批类似 TCP Nagle——延迟换吞吐。
  - 「多主题退化」边界补充（B14）：分区级顺序写在主题/分区多时 IO 零散化，性能随分区数先升后降；SSD 下单文件顺序写（RocketMQ）反而难压满磁盘带宽——所以「Kafka 一定更快」不成立，与现有题「代价与边界」互补。
  - 撞车标注：本题素材整体与 Kafka 专项批次相邻，但目标题已是现有题库成员，此处仅增强不新增。

### E8. 目标题目：be-mq-kafka-throughput 的追问「页缓存会带来什么运维坑？」
- 来源：课程 A《16 缓存策略：如何使用缓存来减少磁盘IO？》
- 追问素材：
  - 定性框架：PageCache 是**读写缓存**，天然不可靠——写进缓存即对应用返回成功，掉电丢；`sync` 强刷会失去缓存意义。Kafka 敢用的三个前提：MQ 读写比≈1:1（只读缓存无加速价值）、可靠性靠**多副本而非 fsync**、PageCache 由内核实现无需自己写缓存代码。
  - 命中率优化维度：消费紧随写入→LRU 天然高命中；**「挖坟」问题**——某客户端从很旧的位置批量拉历史数据，缓存被历史页填满，其他客户端命中率骤降；JMQ 的解法：LRU 加「距尾部距离」权重（改进型 LRU/2Q 思想），旧页优先淘汰。
  - 对应现有答案「内存紧张、页缓存被挤」：可补理论解释——内核用 LRU 变种（2Q）管理页缓存，冷数据扫描类负载会把热页挤出（与挖坟同构）。

### E9. （转介）be-network-io-multiplexing / be-java-gc / be-micro-rpc 的可用素材
- 来源：课程 A《10-14》《31-34》、课程 B《05-08、加餐》
- 追问素材（建议落点标注，供相应批次收割）：
  - 单长连接多请求并发（requestId + Future Map + 响应带回原 ID）——既是 B18 排查案例的原理（本批 S7 已收），也是通用网络编程素材，可转介 be-network。
  - RocketMQ 网络层参数语义：`serverSelectorThreads`=Netty Selector/IO 线程（默认 3，建议 CPU 核数），`serverWorkerThreads`=编解码工作线程（默认 8，建议 2×核数）；IO 线程只做网络读写、业务转线程池——Reactor 职责分工的实例，转介 be-network。
  - 高并发 GC 恶性循环（A14）：对象迅速占满堆→被迫 Full GC 长暂停→请求积压→GC 后更多请求涌入→再 GC；对策=少造一次性对象、大对象复用（对象池）、必要时堆外/自主内存管理（Flink 自研内存管理的教训）；Netty 的 Area-Chunk-Page 池化 + 对象池（B 加餐）——转介 be-java-gc。
  - 传输协议「断句」三法（定长/分隔符/前置长度字段）与**双工通信**提升吞吐（A13/A32：单工一问一答 vs 双工两收两发，10 万次 RPC 从分钟级到 5 秒）——转介 be-micro-rpc 或 be-network；与 RPC 专项批次撞车，交整合者裁决。
  - 异步设计 CompletableFuture（A10）——通用 Java 并发，转介 be-java。
