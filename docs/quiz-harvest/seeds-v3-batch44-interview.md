## 一、候选新题

### S1. 一场完整的招聘有哪些环节？每一轮面试分别在考察什么？
- 来源：面试现场 ·《02 想要成功面试，先要弄懂面试过程》《07 考官面对面：面试经验谈之校招与社招》
- 真题标记：否
- 核心素材：
  - 招聘全流程：确定职位空缺 → 收集筛选简历 → （笔试）→ 多轮面试 → 签 Offer → 试用转正。「补坑岗」职责明确、有前任样板但会被对比；「新增岗」职责模糊、难上手但容易校准期待、易获好评——面试前搞清是哪种，能预判考察重点。
  - 面试官三类角色分工：HR 不熟业务细节，看动机/价值观/潜力等基本面；部门大牛最懂工作细节，看解决问题的能力；部门经理两者兼顾、对人选负责，结论分录用 / 不录用（可能推荐别的岗）/ 候选（留待比较）/ 再面一次（没看清）。
  - 一面最重要：通过率最低且不可挽回；一面结论影响后续轮次的面试策略；一面面试官的强支持能顶住后续面试官想 fail 的压力。
  - 校招四阶段：实习转正（述职评审）→ 提前批（7~8 月，业务部门自主组织、内推简历为主、HC 更足，别因准备不足放弃）→ 正式批（9~10 月，1 笔试 + 3 面试）→ 春招（补招，别押宝）。社招四轮：两面技术 + 主管面 + HR 面；T6+ 加跨团队 Review（招聘委员会定级）。
  - 招聘方视角的弹性：岗位招不到人会调整预期降级招人（「面完一个月没消息又来二面通知」真实存在）；口头 Offer 在招聘审批未过/冻结时可能失效，签正式 Offer 才算稳。
  - 简历投递细节（同一篇）：邮件标题写清职位与姓名、PDF 防乱码、稍正式的邮箱防进垃圾箱、官网职位注意发布时间；内推是公司成本最低、候选人通过率最高的渠道。
- 建议追问：
  1. 「技术面和 HR 面的考察目标有什么不同？为什么不能在技术面跟面试官谈薪？」
  2. 「补坑型岗位和新增型岗位，面试准备策略有什么区别？」
  3. 「提前批和正式批的精力怎么分配？」
- 建议难度：basic
- 建议落点：career-hr（与 career-hr-self-intro / career-hr-overtime-stability 形成流程视角互补，题库尚无「流程认知」题）

### S2. 现在的你，到底该不该换工作？
- 来源：面试现场 ·《04 现在的你，到底该不该换工作》（辅：《05 喜欢或擅长的工作》《01 择业疑惑》）
- 真题标记：否
- 核心素材：
  - 工作满意度三指标：**钱**（物质保障）、**心**（精神满足）、**路**（能力发展通道）——「钱没给到位、心委屈了、路堵住了」；路是决定未来前两项的先行指标。
  - 别只比薪水：工作性价比 = 工作所得（薪水、培训、资源、能力提升）÷ 工作付出（强度、加班、出差、下班后的压力）——新手误区是只比薪水，入职才发现强度承受不了。
  - 精神满足 ≠ 舒服：驾轻就熟的稳定团队是舒适区；精神满足来自持续成就感和协作氛围。
  - 换工作首先换的是「事」：能内部换岗就不必换公司；大公司内部同时存在夕阳/成熟/创新三种业务，像几家不同的公司——评价平台要落到团队与业务阶段。
  - 是不是螺丝钉与公司大小无关，取决于：能接触到多大的工作面、有没有持续且适度的新挑战、有多大决定权和自由度。
  - 好团队的最基本条件是**信息共享**（信息透明 → 配合好 → 协作成本低）；好老板 = 有利于你发展的老板，不只是好相处的老板。
  - 阶段权重：职业早期发展权重最高；稳定期重回报与自我实现——先想清「我现在最缺哪一项」再评估现状。
- 建议追问：
  1. 「哪些信号说明『路堵住了』、留下已无成长？」
  2. 「涨薪 30% 但业务在下行，怎么权衡？」
  3. 「不满的到底是事还是人？哪些问题其实内部换岗就能解决？」
- 建议难度：intermediate
- 建议落点：career-growth（与 career-hr-multiple-offers 的决策打分、career-path-30 的方向选择互补，题库无「跳槽决策」正面题）

### S3. 架构师/资深岗位的面试和普通工程师有什么不同？系统设计轮怎么答到点子上？
- 来源：面试现场 ·《06 考官面对面：我们是如何面试架构师的》（京东架构师面试官亲述）
- 真题标记：否
- 核心素材：
  - 考官的体系：能力模型（一个核心「诚信、担当、品格」+ 硬实力与软能力 7:3）、面试地图（基础技术/架构能力/发展能力）、内部题库——硬实力占时最多，但品格是一票否决项。
  - 面试主线：从候选人「最近参与的、自己认为做得最好的项目」出发 → **边讲边画架构图**（一图三用：帮面试官理解、考结构化思维与表达、为后续细粒度追问提供挂点）→ 沿方案逐层下钻（应用层组件 → Java 基础/JVM → OO 建模与设计模式 → 存储层选型/分片/缓存 → 高并发高可用）。
  - 所有技术点都从候选人自己的方案里带出来：讲不清楚自己方案里的组件等于没懂；高可用必问服务粒度、依赖是否合理、分组/动态管理/限流/降级/监控、强依赖有没有降级方案。
  - 软能力与品格在过程中顺带考察：讲方案的逻辑闭环即表达力；故障场景题看担当（主动分析原因、协同开发测试、指导落地，而不是甩锅）；**问到不会的点支支吾吾找理由 = 诚信问题，不懂就承认的人更受青睐**。
  - 对候选人迁移到系统设计轮的启示：主动画图、沿自己方案守土、把每个技术点挂到项目上下文里讲。
- 建议追问：
  1. 「为什么架构师面试坚持让候选人画图？没有图的表达缺什么？」
  2. 「你负责的系统出了线上故障，作为架构负责人你怎么处理？」（协作与担当场景题）
  3. 「能力模型里的『发展能力』指什么？怎么在面试里证明自己在持续发展？」
- 建议难度：advanced
- 建议落点：career-project（备选落点：并入 sd-methodology-framework 作「考官视角」增强，与 S17/E17 素材联动）

### S4. 面试紧张、大脑空白怎么办？怎么避免发挥失常？
- 来源：面试现场 ·《10 面试紧张怎么办？》
- 真题标记：否
- 核心素材：
  - 紧张是本能：陌生环境/挑战性气氛/一时语塞触发杏仁体「战斗或逃跑」，前额叶供能被挤占 → 听不到问题、忘词、自我否定；目标是降低触发强度，不是消灭紧张。
  - 权力重构：面试是双向选择（相亲比喻——你也在挑「姑娘和她妈」）；企业招到合适的人越来越难，面试官同样怕招错、年轻面试官面资深候选人时更紧张——能力被看见后权力关系立即反转。
  - 紧张程度 ∝ 对结果的期待 ÷ 自信（自信 = 能力自评 × 准备程度）：用耶基斯-多德逊定律调期待——动机过强绩效反降，把「必须通过」改成「攒一场真实考点采样」反而发挥更好（与 career-project-interview-retro 的「热身局」策略互证）。
  - 充分准备消不确定性：从 JD 区分关键技能与加分技能、通过内推人打听面试官角色与考察重点、接到预约电话时澄清面试内容、用能力故事预演高频问答。
  - 场景脱敏练习：去朋友公司/陌生环境模拟面试、做面试官或旁听熟悉氛围、把前 1~2 场面试当练手。
- 建议追问：
  1. 「当场大脑空白，有哪些即时恢复动作？」（复述问题争取时间、先给结论框架）
  2. 「视频面/电话面和现场面的紧张源有什么不同，分别怎么准备？」
  3. 「紧张导致第一题答砸了，怎么止损？」
- 建议难度：basic
- 建议落点：career-hr（题库软技能侧完全没有「临场心态」题，与 unknown-questions 的「不会怎么办」互补）

### S5. 面试官问「你学习能力怎么样」，怎么证明？
- 来源：面试现场 ·《22 怎样体现你的学习能力强？》
- 真题标记：否
- 核心素材：
  - 面试官测两件事：学习过程是否高效 + 学习效果好坏；知识 ≠ 技能（懂乐理不等于会弹琴）——工作学习强调动手运用与「灰度问题只有优劣没有对错」的处理。
  - 学习四环节：接收（基于工作需要选内容，不为应付工作停止学习）→ 理解（新知识与已知建立连接，连接越多理解越深）→ 练习 → 运用（结果反馈修正认知结构）。
  - 六个可展示的学习要素：**好奇心**（遇不懂先自己研究而不是等人喂、追问「为什么」的深度）、**逻辑性**（考官真实考法：10 分钟读完材料按逻辑复述，如「10 分钟学冰壶规则讲制胜策略」）、**操控力**（把方法放进真实场景做出来，如「15 分钟上网找方案让 20 人全球团队做头脑风暴」）、**挑战**（拆大挑战各个击破）、榜样、反馈。
  - 85% 原则：练习中新知识占 ~15% 效率最高——答「怎么学」时体现「温故 + 适度新知 + 刻意练习」的节奏感，比「我天天熬夜学」专业。
  - 展示套路：讲「不会 → 怎么学会 → 做出了什么」的完整故事，用产出物说话（专栏案例：零 Java 基础实习生两天写出多线程程序、一周自设计生产消费模型）。
- 建议追问：
  1. 「你最近在学什么？学到什么程度、怎么验证学没学会？」
  2. 「被扔进完全陌生的领域（新业务/新语言），你的第一周方法论是什么？」
  3. 「你怎么学一个没有文档的东西？」
- 建议难度：basic
- 建议落点：career-project（行为面试「软素质证明」类，题库空白；与 ai-coding 的「用 AI 学习」可互相引用）

### S6. 你不是 leader，怎么体现领导力？
- 来源：面试现场 ·《25 不是领导，怎么体现你的领导力？》
- 真题标记：否
- 核心素材：
  - 领导力 ≠ 职位：是「影响关键决策、推动事态进展」的力量（《十二怒汉》8 号陪审员）；产生因素有职位权力、专业权威、个人魅力——无职位时靠后两者。
  - 领导 vs 管理分工：领导 = 赋予目标和动力、指出方向、促成决策；管理 = 按既定流程执行——任何角色都能做前者。
  - 影响圈三圈模型：**决定圈**（前瞻与决策）、**影响圈**（无决定权但相关的事，用建议/协商/数据影响负责人；发现架构不合理就去找架构师讨论）、**适应圈**（明智适应而不是抱怨对抗）——领导力发生在前两圈，且三圈随能力与职位动态变化。
  - 五种带人方式：榜样带动、权威指导（领域问题大家想到你）、教练启发（用问题促思考）、朋友鼓励（认可成果、树立自信）、知人善任；情境领导 S1~S4（指导/教练/支持/授权）按成员能力×意愿阶段切换——面试官借此评估你的带人上限。
  - 面试官真实问法：「培养/指导别人哪方面最困难」「除了技能还帮过什么」「团队讨论怎么达成一致」「你培养过别人的学习能力吗」「如果给 Offer，回去怎么做项目交接」（顺带考责任感）。
  - 考官心理：技术实力证明你是好兵，技术 + 领导力证明你将是将才——答题目标是给出「可复用的带头证据」，不是贴「有领导力」标签。
- 建议追问：
  1. 「讲一个你没有决定权却推动了跨团队决策的例子。」
  2. 「影响圈里的事推不动怎么办？」（带 tradeoff 上报、做 POC 用事实说话——与 conflict 题方法同构）
  3. 「你带过实习生/新人吗？按什么风格带，为什么？」
- 建议难度：intermediate
- 建议落点：career-project（与 career-growth 的 eng-to-lead 形成上下游：先证明「非职位领导力」，再谈要不要转管理）

### S7. 「讲一个你解决过的最难的问题」——解决问题能力题怎么答出层次？
- 来源：面试现场 ·《26 你解决问题的能力有多强？》《23 怎么体现你能把工作越做越好？》
- 真题标记：否
- 核心素材：
  - 问题的三层定义：错误（修复）、提高（现状不错但有上升空间）、未知机会（新领域）——面试官问「项目有什么待提高的」时，「没什么要提高」「工期紧有点技术债」都是低分；「活跃度半年不涨，调研后定位是缺级联回复，难点在 XX」才是一针见血。
  - 能力三步法：**找到问题**（症状 → 本质的由表及里定位；把问题定义出目标/边界/验收标准，切出低耦合高内聚的工作块）→ **解决方案**（技术/流程/组织三层发散找多方案 → 在业务、组织、技术约束下对比决策 → 分步实施：先止血再根治）→ **验证复盘**（持续监控 + 用户反馈验证，沉淀进流程）。
  - 展示公式：技术选型讲出技术能力、结果验证讲出业务 sense、组织流程考虑讲出管理意识——「扎根技术、着眼业务、懂得管理」是这道题的评分维度。
  - 高手与菜鸟的分界：流于表象 vs 直达本质——背后是技术感知力与业务沉淀的差距，答题时要展示「从日志/数据/闲聊信息里抓关键线索」的推理链。
  - 精益能力补充（越做越好）：找提高点四法——梳理产品问题抓大放小、**识别重复动作做自动化**（热敏打印机自动抄看板案例）、识别等待（跨团队构建部署的等待是浪费）、建立指标体系找平庸点；被面试官说「你这里没考虑到」时的反应是成长型思维测试——陷入思考补方案 > 辩解「考虑到了」。
  - 提升是阶梯不是直线：一个方法吃透后只有量变，跳变靠引入新变革——讲改进故事时说清「哪次是质变的引入」。
- 建议追问：
  1. 「如果只给你一半的时间和资源，怎么解？」
  2. 「你的方案有什么代价或次生问题？」
  3. 「这个问题后来复发过吗？为什么？」
- 建议难度：intermediate
- 建议落点：career-project（题库有 deep-dive/failure，但没有「最难的问题/解决问题方法论」这一最高频行为题的正面对应）

### S8. 提了离职，老板坚决不放人、疯狂挽留画饼，怎么办？
- 来源：面试现场 ·《29 合同都签了，老板却不放你走，怎么办？》
- 真题标记：否
- 核心素材：
  - 不放人的真正原因：离职对**工作**（招人空窗、新人成长期）、对**团队**（关键角色断层、士气与连锁离职）、对**老板个人**（视作背叛、影响关系）都有负面影响——化解思路是降低这些影响，而不是硬刚或玩失踪。
  - 离职难度 = 关键性 × 不可替代性：提前拆雷——推动团队指定 backup、把流程与关键信息文档化分享、推荐接班人（既是职业操守也保护自己；真实案例：资深架构师提前一年多沟通交接，好聚好散）。
  - 法律与现实：劳动合同法规定提前 30 天书面通知即可离职（试用期 3 天），但现实里老板可拖延离职证明、卡流程、影响背调——专栏真实案例：拖了近一年，Offer 黄了还丢了年终奖，最后被迫裸辞重找。
  - 阶段动作：初见不满时先想「对什么不满、和职业发展的关系、我/谁能解决」——跳槽是被底线和大局所迫，不是被几句口角所迫；决定跳时**不裸辞**（在职找工作谈判位置好、避免空窗期质疑）。
  - 离职沟通的目标是「不让辞职成为 surprise」：依赖平时与老板的互信；信任不足时就潜移默化「架空」自己、降低职责集中度，为交接铺路。
  - 与题库联动：离职原因口径（career-hr-leaving-reason）、背调口径一致（career-hr-background-check）、新 Offer 书面化（career-hr-salary-negotiation）在此题串成链。
- 建议追问：
  1. 「老板用涨薪 50% 挽留，接不接？」（提辞后加薪挽留的信任折损与先例风险）
  2. 「新公司催报到、老东家交接没完，两边怎么交代？」
  3. 「离职时竞业协议要注意什么？」（与背景检查题的竞业条目呼应）
- 建议难度：intermediate
- 建议落点：career-growth（题库无「离职执行」正面题；是 leaving-reason 之后、gap-layoff 之前的时间线空白段）

### S9. 负载均衡为什么不是越「匀」越好？——动态算法的指标缺陷与按调用结果调权
- 来源：高阶面经 ·《02 负载均衡：调用结果、缓存机制是怎么影响负载均衡的？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 静态算法（轮询/加权轮询/随机/加权随机/哈希/一致性哈希）靠统计学均匀，不看节点真实负载；动态算法用**单一指标代理负载**：最少连接、最少活跃请求数、最快响应时间。
  - 指标各有缺陷：连接数在**多路复用**下失真（10 个请求共享 1 个连接）；活跃数不区分**大请求**（大商家/千万粉丝 UP 主的请求权重完全不同）；响应时间最综合，但采集要**按时间衰减加权**（只用近期、越近权重越高）。
  - 客户端视角盲区：各客户端独立采集、互相看不见（客户端 1 不知道节点上还压着客户端 2 的 30 个连接）；解决思路是服务端回传指标（响应捎带元数据）或查观测平台——但业界少有框架落地，说明「能讲出缺陷与取舍」比背算法更加分。
  - 亮点方案一：**按调用结果反馈调权重**——连续超时/报错的节点降权，恢复成功后缓慢升权（把熔断/健康度思想揉进负载均衡）。
  - 亮点方案二：**一致性哈希 + 本地缓存**——同一 key 稳定路由同一节点，提高本地缓存命中率、缓解缓存不一致窗口（与缓存一致性题联动）。
  - 小亮点：平滑加权轮询（currentWeight += weight → 选最大 → 减去总权重）避免连续命中同一节点；实践里大规模落地的仍是简单算法，「设计一个贴合业务的算法」是加分叙事。
- 建议追问：
  1. 「你们网关/客户端 LB 用什么算法？出过什么负载均衡相关的事故，根因暴露了算法的什么缺陷？」
  2. 「一致性哈希怎么和 Redis/本地缓存结合？虚拟节点解决什么？」
  3. 「为什么大厂大多数场景仍用轮询类算法？」
- 建议难度：advanced
- 建议落点：其他（backend be-micro 微服务架构节；题库现无负载均衡专题题）

### S10. 怎么用隔离保证核心/VIP 用户体验不受损？
- 来源：高阶面经 ·《06 隔离：怎么保证尊贵的VIP用户体验不受损？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 隔离三目的：故障隔离（可用性）、**性能隔离**（部分方案能带来数量级提升——这是它区别于熔断/降级/限流的点）、安全隔离（合规、权限、独立机房严管控）。
  - 常见误解纠正：不是核心服务扎堆就安全——**核心与核心也要隔离**（同机一宕全宕）；总原则「核心与核心隔离、核心与非核心隔离」。
  - 形态清单：机房隔离（区别于多活：不同服务分散机房 vs 同一服务多城市副本）、实例/物理机隔离、**分组隔离**（B 端/C 端、VIP/普通用户、读写、快慢接口——案例：8 台实例划 3 台给 B 端限流，C 端不限）、连接池/线程池隔离、**第三方依赖隔离**（Redis/MQ/ES 独立集群；持久化实例、当 MQ 用的 Redis 必须独立部署）、进程/容器隔离（容器化是最广义的进程隔离）。
  - 事故案例素材：其他业务往共享 Redis 批量写**大对象**导致全量业务超时、流量打穿到 MySQL——整改动作是 Redis 按核心/非核心分集群 + 严格接入 review + 数据库限流兜底（可自然把话题引到限流，形成体系化回答）。
  - 诚实讲代价：隔离**贵且浪费**（重复集群的建设与维护成本），且易资源不均（一个连接池满负荷另一个闲置）。
  - 组织性干扰要识别：两部门各养一套 Redis 集群可能只是利益割据，不是有意设计的隔离。
- 建议追问：
  1. 「给 VIP 单独集群，流量预估和成本怎么算？值得吗？」
  2. 「Go 这类没有线程池概念的语言怎么做慢任务隔离？」（协程池隔离）
  3. 「隔离粒度怎么选？什么共享、什么必须拆？」
- 建议难度：intermediate
- 建议落点：be-stability（与 be-stability-limits-degrade 互补：那题讲「量/故障/取舍」，本题补上「隔离」这块拼图）

### S11. 怎么保证用户一定能在 1s 内拿到响应？——超时控制与超时传递
- 来源：高阶面经 ·《07 超时控制：怎么保证用户一定能在1s内拿到响应？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 超时两个目标：用户体验（「坏响应也比没响应好」）+ **及时释放线程/连接**——没有超时导致的连接泄漏、线程数飙升是高频事故形态（可用真实事故报告做开场）。
  - 两种形态：调用超时（单次下游调用）与**链路超时/预算制**（链路 1s：B 收到请求时已耗 200ms，则 B 调 C 的超时只剩 800ms）；大厂首页接口有硬性 RT 规定（如 50ms），链路超时是核心服务的标配。
  - 定超时四法（面试热点「你的超时为什么设成这个值」）：用户体验（问产品）→ 被调接口 **P99/P999 线** → 压测取线 → 按代码估算（各 IO 耗时相加 + 余量）；99 线还是 999 线：按可用性要求与两线差距选。
  - 关键细节：**超时 ≠ 取消**——客户端超时后下游通常仍在执行；「第一次请求超时但实际注册成功，用户重试撞上手机号已存在」就是超时与幂等的经典联动 bug（接 be-general-idempotency）。
  - 亮点：框架客户端/服务端**双向监听超时**——发起前已超时就不发请求；响应迟到直接丢弃；服务端发现请求已超时不转交业务代码——把资源省给有效请求。
- 建议追问：
  1. 「全链路超时预算怎么分配？和重试预算怎么配合防重试风暴？」（与 be-stability-limits-degrade 的 retry budget 追问衔接）
  2. 「超时后怎么让业务真的停下来？」（context 取消、步骤间检查点）
  3. 「用户已看到超时页、后台却写成功了，产品上怎么兜？」
- 建议难度：intermediate
- 建议落点：be-stability（现题库只在 limits-degrade 的追问里点到超时收紧，无正面题）

### S12. 依赖的第三方接口不稳定、性能差还推不动对方优化，怎么保证自己可用？
- 来源：高阶面经 ·《08 调用第三方：下游的接口不稳定性能又差怎么办？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 前提认知：内部依赖能推动同事修，**第三方推不动**——容错责任全在调用方；微信登录、支付、短信、实名认证是人人有共鸣的场景（简历写「对接过 XX API」的人几乎都没做容错，做全了就是差异化）。
  - 独立防腐层四职责：**一致性抽象**（屏蔽协议/加解密/报文/回调差异，换供应商业务方无感；扩展新供应商只加实现）；**客户端治理**（按对方配额主动限流，省掉必然失败的调用；只对幂等接口透明重试）；**可观测性**（Prometheus/SkyWalking 接入 + 双通道告警：告自己、也通知业务方评估影响）；**测试支持**（mock 服务能模拟成功/失败/超时/回调——第三方不可能配合你压测）。
  - 容错亮点一：**同步转异步**——第三方崩溃时把请求落库暂存、恢复后补推（时效不敏感的推送/上报类业务）。
  - 容错亮点二：**自动替换第三方**——一致性抽象的红利：健康探测不达标自动切到备用供应商。
  - 叙事模板：接手时前后对比 + 量化（接入周期从一周到两天；故障感知从「用户投诉才知道」到分钟级告警）——「重构叙事」的标准示范，与 career-project-deep-dive 的重构追问呼应。
- 建议追问：
  1. 「第三方的限流配额怎么感知与动态调整？」
  2. 「回调丢了怎么办？」（本地单据 + 定时主动查询对账）
  3. 「多供应商热备的成本和数据一致性怎么权衡？」
- 建议难度：intermediate
- 建议落点：be-stability（备选 be-general；「外部依赖治理」是题库稳定性主题的空缺面）

### S13. 设计一个消息队列，你会怎么做？
- 来源：高阶面经 ·《28 架构设计：如果让你设计一个消息队列，你会怎么设计它的架构？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 答题主线：站在设计者角度解释 Kafka 为何长这样，围绕**生产者/消费者/broker/topic** 四要素展开；同一套内容还能答「Kafka 为什么引入 topic/分区/消费者组」。
  - topic 与分区：topic 是业务隔离单元（天然隔离流量与故障）；不分区的并发瓶颈——所有读写抢一把锁；分区要**分散在不同 broker**（坏一个 broker 只影响该 topic 的一个分区）。
  - 落地化讲法（本题的差异化亮点）：**用 MySQL 封装一个 MQ**——topic = 逻辑表、分区 = 分库分表后的物理表、自增主键 = offset；偏移量表三列（消费组、分区、committed_offset），重消费 = UPDATE offset，拉消息 = `SELECT * WHERE id > offset LIMIT 50`——每步都能说清锁与性能（表小、行锁）。
  - 推拉分工：生产者推（消息产生速率与 broker 无关）、消费者拉（自己掌握消费节奏，如每秒拉 50 条）；批量发送 + `linger.ms` 兜底（凑不满一批也定时发，防消息滞留内存丢失）。
  - 主动认领简化版的边界：用 MySQL 主从替代 ISR 副本协议省掉选举，但说清代价（无多数派提交语义）；消费组再均衡、延迟消息、事务消息怎么做——体现「知道简化在哪、补齐路线是什么」。
- 建议追问：
  1. 「基于数据库的 MQ 性能瓶颈在哪？怎么优化（批量 INSERT、生产者直插免网络跳）？」
  2. 「怎么在自研 MQ 上加延迟消息/事务消息？」
  3. 「什么场景不该自研、直接用现成的？」
- 建议难度：advanced
- 建议落点：system-design（sd-classic；题库 MQ 侧 24 题全是 Kafka/RocketMQ 原理与实战，缺「设计一个 MQ」的架构题）

### S14. MongoDB 是怎么做到高可用的？什么场景选它而不是 MySQL？
- 来源：高阶面经 ·《41 MongoDB：MongoDB 是怎么做到高可用的？》《42 MongoDB高性能：怎么优化MongoDB的查询性能？》
- 真题标记：是（面经直接来源，入库打 tags: ['真题改编']）
- 核心素材：
  - 选型口诀：数据模型稳定 → MySQL；**模型易变（难预料用户输入什么）或分库分表运维成本高 → MongoDB**（自动分片 + 自动再平衡是核心卖点）；中小公司多数场景 MySQL 够用——「为什么用」比「怎么用」更是面试考点。
  - 高可用三层：**副本集**（Primary/Secondary + oplog 同步，oplog 类似 binlog 但有两个坑：操作强制转幂等 set 导致 oplog 可能异常大；oplog 有大小/期限上限，从节点落后太多只能全量重同步）；**config server** 存元数据（主挂了仍可提供读——多数中间件做不到）；**自动再平衡**（chunk 默认 128MB 或文档数达均值 1.3 倍即拆分，rebalance = 挪块，阈值触发 moveChunk 七步迁移：建索引→同步→追增量→改元数据→删源）。
  - 写入语义 Write Concern：w = majority / N / 0 × j（是否落盘）× wtimeout——w=0 性能最好但可能丢数据；与 Kafka acks 语义同构，可对照讲「可靠性是参数选出来的」。
  - 分片查询链路：mongos 读 config server 元数据路由请求——config server 抖动会放大成全集群问题（元数据单点依赖的意识）。
  - 性能篇要点（42）：索引优化、文档结构设计（内嵌 vs 引用）、读写分离的 read preference。
- 建议追问：
  1. 「oplog 和 MySQL binlog 的差异会引发什么实际问题？」
  2. 「w=majority 在网络分区下会发生什么？」（接 be-distributed-quorum / 脑裂）
  3. 「什么数据不适合放 MongoDB？」
- 建议难度：intermediate
- 建议落点：其他（backend 存储方向，题库现无任何 MongoDB 题；NoSQL 面经里 ES 已并入 sd-classic-search，MongoDB 是唯一空白的主流存储）

## 二、既有题增强素材

### E1. 目标题目：career-hr-self-intro（自我介绍）
- 追问素材：①「我们 vs 我」的主语纪律（面试现场 27）：全程「我们」必被追问「你自己做了哪些」，全程「我」会被怀疑没有团队——开场就切分「哪些是我独立做的、哪些是协作完成」；② 定制化的具体做法：同一段经历按 JD 重排匹配点（基础架构岗前置稳定性数据、业务岗前置交付结果），自我介绍的隐藏功能是给整场面试定考察方向。

### E2. 目标题目：career-hr-weakness（你最大的缺点）
- 追问素材：兴趣爱好题（面试现场 16）可作为该题的姊妹追问一并准备——面试官借爱好看**动机**（讲「兴趣点」：发朋友圈 = 渴望认可、健身 = 自我完善、组队 = 社交倾向）与**坚持度**（讲「产出层/引领层」：6 年徒步 40 条路线并把路线分享出去被大量下载；自学游泳钻研发力技巧、回帖获赞）。参考结构：爱好是什么 → 动机 → 产出与如何产出。禁忌：旅游/看书/陪孩子式平淡陈述，无产出无细节。

### E3. 目标题目：career-hr-salary-expectation / career-hr-salary-negotiation（谈薪两题）
- 追问素材：「两个三角形」框架（面试现场 20）：好 Offer = 薪水/成就感/成长三角面积最大，谈 Offer 就是让「公司给的三角形」与「你期望的三角形」靠拢——除了钱，要把成就感和成长的兑现也谈清楚（公司常用成长故事换你少要钱，反向操作是用价值证明换更高薪水）。何时谈：先自评面试官对你经验/技能/潜力三方面的兴趣度，兴趣确认后才是议价窗口。可补三类事后矛盾作警示案例：薪水倒挂、承诺不兑现、钱满意但无成长的温水煮青蛙。

### E4. 目标题目：career-hr-why-us / career-hr-career-plan（动机与规划）
- 追问素材：面试官 vs 应聘者「认知差异」对照表（面试现场 27）：①「想找什么样的工作」——候选人以为要顺着公司说，面试官要听真实目标来判断匹配与稳定性（入职后错配的代价更高）；②「职业规划」——候选人以为进了公司老板说了算，面试官在看你的目标与团队是否同向、以及是否有能力灵活适应其他角色；③技术选型题——候选人追求最新最全的完美方案，面试官要的是约束下「多措施配合的全面有效」。可整理成一组「你以为 vs 考官在想什么」的追问。

### E5. 目标题目：career-project-resume（技术简历）
- 追问素材：「详历」工作法（面试现场 09）：简历每行背后备一份详版底稿，从四个角度找价值——公司（收入/成本/老板的什么问题）、客户（解决了什么、哪里最有用）、团队（使命/资源/质量/他人受益）、个人（成就感和成长）；详历是「经历 → 能力故事」的转化车间，也是面试问答的弹药库。投递细节补充：标题写职位与姓名、PDF、正式邮箱、注意职位发布时间（面试现场 02）。

### E6. 目标题目：career-project-highlights（难点亮点提炼）
- 追问素材：伪亮点的反面清单（面试现场 09）：「大公司工作过 / 10 年经历 / 参加过 10 亿的大项目 / 出国」这类**可见亮点**经不起深挖——挖不出成果与能力素质反而减分（好环境没出成绩）；「张小龙的简历写五个字就够了：我做了微信」——区分度来自支撑成果的**不可见能力素质**。创新的定义可以放宽：新工具引入、流程简化、协作优化、算法小改进都算（不必是发明专利），这类「轻创新」最显持续精进。

### E7. 目标题目：career-project-star（STAR 介绍项目）
- 追问素材：社招技术面「刨根问底」的四个扣分点（面试现场 07，可作讲项目自检清单）：①讲不清需求从哪里来 = 只是执行者不是负责人；②一味听从 PM、不会分析需求合理性；③方案没有调研/对比/论证过程（哪怕简单业务系统也有选型可讲）；④只讲过程不讲成效。与现有 STAR 题的「常见错误」互补：这四条是面试官视角的扣分项原文。

### E8. 目标题目：career-project-deep-dive（项目深挖）
- 追问素材：①「一面定调」效应（面试现场 07）：一面通过率最低且影响后续所有轮次的策略与立场——最硬的项目和最熟的领域要放在第一场；②自评与考官评价差异大的根源是认知差异（面试现场 27）：面试官按「经验/技能/潜力/动机」素质模型采样，候选人按「我做了什么」叙述——深挖准备时把故事显式映射到四要素上。

### E9. 目标题目：career-project-interview-retro / career-project-unknown-questions（表达与「不会」）
- 追问素材：「两个维度八个层面」讲技术框架（面试现场 13）：应用维度（问题 / 技术规范 / 最佳实践 / 市场趋势）+ 设计维度（目标 / 实现原理 / 优劣局限 / 演进趋势）——听到问题先在脑中铺开全维度，再按面试官的角色/知识结构/上下文挑他要的层讲，猜不出就直接问「您对哪方面更感兴趣」。表达五法：结构化（金字塔原理）、画图、举例类比（「火锅喻进程线程」）、对比、绑定项目讲故事；**杀手锏是最佳实践层的真事**——「这个技术上个月正好在 XX 项目用过，当时……」。注意观察厌倦信号（看表/翻简历）及时收束换点。

### E10. 目标题目：career-project-conflict（冲突处理）
- 追问素材：「你在别人需要时说过 No 吗」的认知差（面试现场 27）：候选人以为助人要无条件，面试官认为协作的前提是先保住自己的职责——说 No 的正确姿势：了解对方真实目的、给快速指引、改约时间、指给更合适的人。补进冲突题「协作成熟度」的证据库，与「有实质分歧的案例」形成两类素材。

### E11. 目标题目：career-project-quantify（价值量化）
- 追问素材：无现成指标时的精益找数法（面试现场 09/23）：①盯产品指标的前后对比（PV/DAU/Velocity/缺陷率趋势）；②识别**重复动作**做自动化省人时（Trello 抄看板 → 热敏打印小票的案例：怕「重复执行」的麻烦是创新动力，怕「去除重复」的麻烦是抗拒变革）；③识别**等待**（跨团队构建部署等待是被默认接受的浪费）。浪费三形态「缺陷、重复、等待」可作为量化叙事的检索框架。

### E12. 目标题目：career-project-reverse-questions（反问环节）
- 追问素材：反问是信息采集的正式机会（面试现场 02/04）：终面/主管面「多问多了解」直接影响 offer 决策；可把「好团队判据 = 信息共享程度」（04）转成反问——「团队的方案和事故复盘会公开吗？文档沉淀在哪？新人能看到历史决策吗？」——比泛泛问技术栈更能测出团队成色，也展示你的工程判断力。

### E13. 目标题目：be-stability-limits-degrade（限流熔断降级）
- 追问素材：①熔断抖动治理（高阶面经 03）：阈值留余地（P99 1s → 阈值 1.2s 防偶发尖刺）、**持续超阈值才触发**（30s~1min 经验值，能讲清过长/过短的代价即可）、恢复不裸放——10%→20%→30% 渐进放量，或干脆客户端摘除节点再逐步放量；②特色熔断方案：依赖 Redis 的高并发接口在 Redis 崩溃时熔断 + 后台 goroutine 持续探活、恢复即退出熔断（防缓存击穿打穿到 MySQL 的组合拳）；③「熔断会造成写入失败，如果不允许写入失败怎么办？」（八股 综合.md 原题）：把拒绝改成**入口排队（有界队列 + 有限等待）或同步转异步落库补处理**——断路器题的高级追问，正好衔接限流的排队与第三方题的同步转异步。

### E14. 目标题目：be-mysql「InnoDB 为什么选择 B+ 树作为索引结构？」
- 追问素材：八股 MySQL.md 有「2000W 数据的层高」专节——可加追问「为什么说三层 B+ 树大概能撑两千万行？这个估算怎么来的」（按行大小 → 每页行数 → 非叶节点扇出逐层推，顺带解释分库分表阈值经验的来历，接 be-mysql 分库分表题）。「MySQL 深分页优化」「慢 SQL 优化」两个专节与 be-mysql 深分页/索引失效题互相印证——覆盖确认，不立新题。

### E15. 目标题目：be-redis（数据结构 / 持久化 / 变慢排查）
- 追问素材：八股 Redis.md 与 redis/01、02（42 题 + 99 题清单）标题级比对全部落在 be-redis 20 题覆盖内，无需新题；可吸收的小素材：「fork 子进程时要 2 倍内存会卡、主进程内存改变时怎么处理」→ RDB 持久化题/单线程卡点题的绝佳追问（写时复制、copy-on-write、大页内存影响）；「zrange 全长 n 的复杂度」「跳表画结构」→ zset 编码题的现场推导追问；「大键/热点问题」→ 生产 Redis 变慢题的根因清单补充。

### E16. 目标题目：be-mq「消息大量堆积怎么办？」等消费主题
- 追问素材：八股 消息队列.md 两个好问题：①「n 个 partition、n+1 个消费者/消费组，消费速率怎么变？消费速率取决于什么」——可作堆积/扩容题的追问（分区数与消费者数配比、瓶颈在拉取还是处理还是提交）；②「结合你用过的 Redis、Kafka 讲讲它们体现的 CAP」——可挂 be-distributed-cap（CAP 定理题）作双中间件对照案例。

### E17. 目标题目：sd-methodology-framework（系统设计答题框架）
- 追问素材：「答后自评四问」（高阶面经 模拟面试（一）答案，可并入系统设计轮的练习方法论）：面试前想好**人设**了吗、回答有没有围绕人设？看到问题能否瞬间想到刷亮点？有没有留「引导话柄」把面试官勾进主场？有没有糅合自己项目形成独一无二版本？——「人设 + 引导」是把设计题答成主场的方法论，与既有「澄清约束 → 估算 → 画图 → 深挖」框架互补。考官侧印证（面试现场 06）：架构师面试坚持让候选人边讲边画图——画图既是加分动作也是追问挂点。

### E18. 目标题目：be-general 智能指针（unique_ptr、shared_ptr、weak_ptr 的实现原理）
- 追问素材：真题补充（面试题收集，真题来源）：①「如果让你实现一个智能指针，你会怎么做」（八股 CPP.md）——可加手撕级追问：引用计数块的布局、计数的线程安全级别、weak_ptr 怎么破环；②「手写 string 类」（coolshell 版：构造/析构/拷贝/移动/swap 与异常安全）与「手写 vector」（面试官 hire bar 自述：写对构造/析构/push_back/pop_back 即过，讲清 resize 扩容、allocator/move 是 strong yes）——编码题格式暂无落点，先在此挂真题标记备查，若后续批增设手撕专题可直接取用。
